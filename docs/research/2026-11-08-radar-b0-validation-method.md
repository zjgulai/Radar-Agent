## 0. 结论、边界与既有草案的关系

### 0.1 本文主张

1. B0 的分析单元是**合作决策 episode**（一次从触发到决定 / 搁置 / 放弃的合作判断），不是功能、角色或一句需求。
2. 现状过程捕获必须**先于**任何“主页链接 / brief / 监测”起点假设。
3. 访谈只问**最近实际发生的行为**，不问假设性意愿；访谈、观察、文档三者三角验证。
4. 基线必须写清分子、分母、来源、缺失标记；**本文不给实测值、不给固定阈值、不设接受线**。
5. 价值验证先用**定性证据矩阵**排序，再做**有界纸面 / 礼宾演练**；不做生产验收或技术评测。
6. 退出只有 **advance / reframe / hold / stop**；**发现（finding）、决定（decision）、PoC 授权（authorization）三件事分开**。
7. B0 只准备 D01–D04 / D12 的相关证据，**不要求先关闭全部 12 项决策**。

### 0.2 不做什么

- 不做生产验收、模型评测、准确率 / 召回率、性能 / SLA。
- 不做 live 采集、平台 API、凭证、飞书消息、真实创作者接触。
- 不做付费模型调用、采购、外联、合同、付款。
- 不写代码、不安装、不 Git、不部署。
- 不替代法务 / 数据 / 安全 / 业务审批。
- 不把方法指南当组织批准。
- 不把“没有观察到”写成“不存在”。

### 0.3 与既有 B0 草案的关系

主计划已给出 B0 的节点位置与退出方向：B0 的目标是“访谈并走真实脱敏任务；比较替代流程；确定首发范围、价值与停止信号”，输出 `work/requirements/R-radar-charter.md`，可证伪退出为“真实用户能说明任务 / 产物 / 下一动作；必需数据有可行路径或明确降级； owner 接受问题与停止信号” [SRC-LOCAL-PLAN §3“B0 业务发现，RG-B0”行]。本文补齐的是**怎么做**：如何选案例、怎么问、怎么观察、怎么量、怎么排序、怎么演练、怎么退出。

Main 生命周期研究提出过 B0 的输入、产物与可失败检查，包括“找 3 个真实目标用户 / 业务方，分别复述”“对每个关键数据源做一次真实探测”“业务 owner 在 `B0-问题定义 memo` 上签核” [SRC-LOCAL-MAINLIFE §8.2“B0 的可失败检查”]。交付资源研究建议“至少 3 条近 12 个月脱敏案例” [SRC-LOCAL-DELIVERY P1 行]；设计评审也要求“P1 出口加入基线：同一流程的步骤、耗时、角色、返工、证据缺口；至少 3 条近 12 个月脱敏案例” [SRC-LOCAL-CRITIC §5.6]。这些是 **C 级建议，不是批准阈值**；本文把它们改写为“样本框与目的说明”，不把“3”当作固定门槛。

## 1. 为什么需要 B0，以及 B0 要回答什么

### 1.1 Main 不回答市场是否需要

Main 首页明确写了自己的边界：“它的边界能让你不骗自己，**不能让你不骗市场。产品有没有人要，这套方法答不了。**” [SRC-MAIN-01 首页“它不是什么”段]。同一页还写：“它不是教你写代码。代码由 agent 写。它只解决「你怎么知道它做对了」。” [SRC-MAIN-01 首页“它是什么 / 它不是什么”段]。

本项目主计划据此明确：“B0 是本项目补充，不是 Main 原文。Main 首页明确不能判断市场是否需要；所以先查真实任务与价值。” [SRC-LOCAL-PLAN §3 开头]。因此 B0 不能把 Main 的七阶段再跑一遍来代替业务发现。

### 1.2 B0 的核心问题

用一句话：**在 Momcozy 的真实合作决策中，谁在什么触发下、用什么证据、经过哪些角色和等待、做出什么决定，当前代价和失败模式是什么；哪一个窄任务值得先做，什么证据能证明它真的被采用？**

分解为八个问题：

1. 谁是操作者、审批者、复核者、下游？各自能决定什么、不能决定什么？
2. 真实触发是什么：主页链接、brief、监测提醒、续约 / 到期、材料审查、临时问题？
3. 当前端到端过程是什么，包含哪些工具、线下步骤、等待、返工、例外？
4. 哪些案例被拒绝、搁置、放弃、返工？原因是什么？
5. 当前基线：wall-clock、人工投入、外部等待、复核、返工、成本、决策时延分别是什么？
6. 必需证据能否合法、技术取得？缺失时业务实际怎么做？
7. 哪个任务频率高、后果重、可控、证据可得、复核负担可接受、有 owner、替代方案不足？
8. 什么情况下应该停、缩范围或改题？业务 owner 是否接受问题与停止信号？

### 1.3 B0 不回答的问题

- 不做“用户会不会喜欢 / 愿不愿意用”的意愿调查。
- 不预测 ROI、转化率、营收、节省比例。
- 不评估模型准确率、系统性能、安全实现。
- 不决定技术栈、架构、供应商、预算。
- 不批准数据采集、法务授权、飞书接入、生产发布。
- 不替代 D01–D12 的签核。

## 3. B0 方法总览

B0.0–B0.7 是八个 C 级方法模块，按案例成熟度和实际需要启用，不要求首次探索完整执行。先用简短近期案例还原任务与决定，再按证据缺口增加观察、基线、演练或比较；模块不构成已批准阶段门，也不是生产验收或技术评测实现。

| 步骤 | 目的 | 主要产物 | 可失败检查（不通过则不得进入下一步） |
|---|---|---|---|
| **B0.0 边界与授权** | 明确研究问题、参与者、数据规则、禁止动作 | `B0-scope`、`B0-authorization-log`、角色表 | 没有书面访谈 / 观察许可；没有脱敏规则；有人要求 live 数据 / 付费模型 / 创作者接触 |
| **B0.1 现状过程捕获** | 还原真实合作决策 episode | `B0-episode-ledger`、as-is swimlane 图、artifact register、handoff / wait 清单、exception catalog | 只有观点没有案例；只有成功案例；图未由操作者与审批者分别校验 |
| **B0.2 任务类型学** | 从 episode 归纳任务类型，检验 link / brief / monitor 起点假设 | `B0-task-typology`、job 候选清单、纳入 / 排除规则 | 直接把 PMO 能力名或产品页面当流程；未覆盖拒绝 / 搁置 / 返工；起点假设未检验 |
| **B0.3 基线测量** | 建立 wall-clock、投入、等待、复核、返工、成本、决策有用性、采用的可计算基线 | `B0-baseline-table`、per-episode 表、missingness register | 指标没有分子 / 分母 / 来源；把估计写成观测；只报均值；设固定阈值 |
| **B0.4 证据可得性** | 判断每个 job 所需证据能否合法 / 技术取得 | `B0-evidence-matrix`、unknown / unavailable 清单、替代路径 | 把“平台存在”当“字段可得”；把“公开可见”当“可合法使用”；缺失被静默填平 |
| **B0.5 价值排序** | 用定性证据矩阵排出 Tier 1 / 2 / 3 / Excluded | `B0-job-matrix`、排序理由、dissent log | 使用假加权总分；高频但不可控仍排 Tier 1；没有 owner 仍推进 |
| **B0.6 有界纸面 / 礼宾演练（可选）** | 测试产物可理解性、证据可追溯性、未知处理、复核负担 | `B0-rehearsal-report`、evidence-parity audit、disagreement log | 使用付费模型 / API / live 数据 / 真实创作者；单一评审当金标；从小样本宣称 ROI |
| **B0.7 退出评审** | 形成 advance / reframe / hold / stop 建议并交接 | `B0-exit-memo`、requested decisions、handoff package | 把 finding 写成 decision；把 B0 建议写成批准；未记录 unknown / dissent |

**流程：** 授权 → 选案例 → 还原过程 → 归纳类型 → 量基线 → 查证据 → 排优先级 → （可选）演练 → 退出评审 → 需求交接。**全程不进入开发。**

## 4. 研究边界、角色与授权

### 4.1 B0 角色

| 角色 | 能回答什么 | 不能回答 / 不能代替什么 | 决策权 |
|---|---|---|---|
| 发起人（Sponsor） | B0 是否投入、范围、资源的边界 | 不能代替业务 owner 判断具体合作流程；不能代替法务 | 授权 B0 范围与资源；对 D01 / D12 相关事项有建议 / 决定权（按实际授权） |
| 品牌业务 owner | 问题是否真实、优先级、停止信号、首发团队 / 市场 / 品类 | 不能替操作者描述具体步骤；不能替法务判断权利 | 接受 / 拒绝 B0 问题与范围；D02–D04 的业务建议签核 |
| 操作者 / 分析员（Operator） | 实际怎么做、花多久、在哪返工、缺什么 | 不能代表审批者的标准与否决理由 | 通常无最终合作决定权；可认领 / 起草 |
| 审批者（Approver） | 决策标准、否决原因、风险容忍、等待与复核负担 | 不能替操作者描述手工细节；不能替法务解释合同 | 对合作 / 预算 / 计划有明确批准或否决权 |
| 复核者（Legal / Brand asset / Compliance / Finance） | 权利、claim、材料、预算合规边界 | 不能替业务判断品牌契合；不能代替外部法律意见 | 在各自范围内批准 / 退回 / 要求补料 |
| 需求方（BD / 品牌成员） | 触发、brief、对象、期望产物 | 不能代表审批者；不能把“想要”当“已发生” | 提出需求；通常无最终合作决定权 |
| 下游使用者（Clone / Paid Media / 守衡等） | 产物如何被消费、什么状态会导致返工 | 不能替 Radar 团队定义内部流程 | 按各自流程接收 / 拒绝 |
| 产品 / BA（研究负责人） | 研究设计、访谈、观察、综合 | 不能替业务 owner 接受问题；不能签发批准 | 无业务 / 法务批准权 |
| 数据 / 法务顾问 | 数据最小化、脱敏、允许用途、风险 | 不能替业务判断价值；不能替发起人授权预算 | 对数据 / 法务边界提供意见或批准 |
| PMO | 项目身份、命名、治理、汇报口径 | 不能替品牌业务 owner 判断合作价值 | D01 身份 / 域名 / 治理相关 |
| Agent（本研究的辅助） | 整理问题、归纳笔记、检查引用 | **不能扮演用户、不能代替访谈、不能把 Agent 复核记成人类同意** | 无任何批准权 |

**角色分离规则：** 操作者与审批者必须**分别**访谈、分别记录、分别校验过程图。不能让操作者替审批者回答“为什么批 / 为什么不批”，也不能让审批者替操作者描述“实际怎么找资料”。如果同一人兼任两职，记录两种角色并标注利益冲突 [C：本文建议；与 SRC-LOCAL-DECREG“不能把 Agent 复核记为人类同意”一致]。

### 4.2 B0 最小授权集

B0 只需要以下**研究性授权**，不需要先关闭 D01–D12：

1. 发起人 / 业务 owner 书面同意 B0 范围、访谈对象与时间投入。
2. 每位参与者的知情同意（目的、自愿、可停止、记录方式、保存期限、匿名化）。
3. 脱敏与数据处理的书面规则（谁可访问、保存多久、如何删除）。
4. 如做纸面 / 礼宾演练，单独的**有限演练授权**（案例包、参与者、时间、禁止动作）。
5. 明确的“无 live 动作”确认：不采集、不发消息、不调用付费模型、不接触创作者。

以上记录在 `B0-authorization-log`：授权人、岗位、范围、数据、允许动作、禁止动作、有效期、停止条件。它们是 **B0 研究授权，不是 D01–D12 决策**；不能被解释为数据采购、法务通过或生产许可 [C：本文建议；与 SRC-LOCAL-BOUNDARY“本轮不做”一致]。

### 4.3 参与者与案例选择

- **目的抽样，按角色与结果分层**：操作者、审批者、复核者、需求方、下游分别取样；案例覆盖 **advance / reject / defer / stall / abandon / rework**，并至少包含一个“当前流程运行良好”的案例，避免只找问题。
- **负案例优先**：拒绝、搁置、放弃、返工、越权、补料、退回的案例，往往比成功案例更能揭示决策标准、等待和失败成本。
- **不接触第三方**：不联系创作者、代理、平台、客户；只讨论内部如何处理该案例；案例中的第三方身份一律脱敏。
- **记录选择偏差**：谁拒绝参与、哪个角色无法安排、哪些案例无法取得、为什么；不把便利样本写成代表性样本。
- **样本量是研究参数，不是阈值**：既有笔记的“3 个用户 / 3 条案例”是 C 级建议 [SRC-LOCAL-MAINLIFE §8.2；SRC-LOCAL-DELIVERY P1；SRC-LOCAL-CRITIC §5.6]，不是批准门槛。实际 N 由案例可得性、角色覆盖和饱和程度决定；报告 N、选择标准和覆盖限制，不用 N 制造统计显著性。

## 5. 现状过程捕获与任务类型学

GOV.UK 对 discovery 研究目标的界定是：“The aim of user research in the discovery phase is to find out: who your likely users are and what they're trying to do … how they do it currently (for example, what services or channels they use) … the problems or frustrations they experience … what users need from your service to achieve their goal.” 并强调 “You must do this before you start planning, designing or building your service.” [SRC-B0-GOVUK-02 §开头]。同一页要求从端到端考虑 “all tools, transactions, support and offline steps”，并了解提供服务 / 支持他人的人（如 caseworkers、call centre agents、charity workers），而不仅是最终用户 [SRC-B0-GOVUK-02 §“How to do user research in discovery”]。这正是 B0.1 的范围：先还原现状过程与角色，不先设计服务。

### 5.1 分析单元：合作决策 episode

**定义：** 一个 `decision_episode` 是从**触发**（有人提出一个合作对象 / 合作问题 / 续约 / 材料审查）到**一个可记录的业务状态**（进入下一阶段、拒绝、要求补料、搁置、放弃、或观察截止时仍未决）的完整片段。

**纳入：** 与 IP / 名人 / 创作者合作判断直接相关；有至少一个内部参与者能复述；有可脱敏的产物或记录。
**排除：** 纯内容制作、纯投放执行、纯客服、纯舆情监控（除非它触发合作决策）；无法脱敏或无法取得同意的案例。
**右删失：** 观察截止仍未决的 episode 记为 `open_at_cutoff`，不当作成功或失败；报告删失比例。

**episode ledger 最小字段（研究台账，不是产品 schema）：**

| 字段 | 说明 |
|---|---|
| `episode_id` | 研究用伪 ID，不含姓名 / handle |
| `trigger_type` | 链接 / brief / 监测 / 续约到期 / 材料审查 / 临时问题 / 其他 |
| `object_type` | 创作者 / 名人 / IP / 专家 / 代理推荐 / 联盟 / 混合 / 未知 |
| `decision_type` | shortlist / reject / request_more_info / defer / approve_plan / approve_material / renew / stop |
| `brief_ref` | 有 / 无 / 未知；不记录合同金额 |
| `roles_involved` | 操作者、审批者、复核者、需求方、下游（角色，不写人名） |
| `systems_channels` | 表格、群、私聊、邮件、工作台、线下；只写类别 |
| `t_trigger` / `t_first_action` / `t_ready` / `t_decision` / `t_close` | 时间戳或日期；无记录写 `unknown` |
| `active_hours_by_role` | 各角色主动投入人时；标注 observed / artifact / estimated |
| `wait_internal_hours` / `wait_external_hours` | 内部审批 / 外部等待；分开 |
| `rework_hours` / `rework_causes` | 返工人时与原因 |
| `artifacts` | brief、表格、背调、审批单、材料登记、拒绝说明等 |
| `evidence_items` | 决策实际依赖的证据项 |
| `unknowns` | 当时明确不知道的字段 / 权限 / 权利 |
| `outcome` / `outcome_reason` | 结果与原因；拒绝也要写理由 |
| `alternative_used` | 没有 Radar 时实际用了什么 |
| `evidence_grade` / `sanitization` | 该条记录的来源等级与脱敏状态 |

### 5.2 捕获顺序：先过程，后起点假设

1. **收集可用产物**：在授权范围内取得脱敏的表格、brief、清单、审批单、拒绝说明、材料登记骨架；记录来源、日期、版本、许可、脱敏方式。
2. **访谈重建**：让操作者与审批者分别按时间顺序走同一个 episode；问“实际做了什么”，不问“应该怎么做”。
3. **情境观察**：在同意与安全边界内观察真实工作表面；不能观察的步骤记为 `not_observed`。
4. **画 as-is 图**：角色 × 步骤 × 系统；标出手递、等待、返工回路、线下步骤、未记录的工作、例外路径。
5. **回访校验**：把图分别给操作者与审批者看，记录修正与分歧；不把两方说法强行平均。
6. **建任务清单**：从 episode 归纳任务，不从产品页面归纳。
7. **做任务类型学**：见 5.5；先完成类型归纳，再判定起点假设。
8. **最后才检验起点假设**：见 5.3；未完成过程捕获与类型学之前，不选 link / brief / monitor 作为默认起点。

### 5.3 起点假设必须被检验，不能先验采用

本节只登记**待检验假设与检验方法**；实际判定在 5.5 任务类型学完成之后进行，不能反过来用起点假设裁剪案例。

主计划的产品草案以“主页链接 / 账号输入”为 MVP 起点：“BD/品牌成员在飞书群精确 @Radar，或 P2P 输入主页 / 账号与合作问题；资料缺失时追问目标市场、品类、brief。” [SRC-LOCAL-PLAN §2.1]。这是 **C 级建议**，不是已验证事实。领域场景笔记也明确列出关键不确定性：“用户日常是否真的从主页链接发起背调？授权登记是否属于同一次任务？首发合作对象类型是否共享此流程？需要业务访谈验证。” [SRC-LOCAL-SCEN §2“关键不确定性”]。

B0 必须把以下起点作为**待检验假设**，逐一记录观察结果：

| 假设 | 描述 | 需要观察 / 询问 | 若未观察到 |
|---|---|---|---|
| H1 link-start | 需求方从主页 / 账号链接发起背调 | 最近一次链接是谁发的、发到哪、后面发生了什么 | 记为“本样本未观察到”，不是“不存在”；扩大样本或改题 |
| H2 brief-start | brief 驱动候选搜索 / 比较 / 计划 | brief 从哪来、谁写、是否先有候选、预算是否已知 | 同上；检查是否与 H1 共用流程 |
| H3 monitor-start | 监测名单 / 异动提醒触发复核 | 谁维护名单、多久看一次、异动后做什么 | 同上；注意“监测”可能只是内部周报 |
| H4 renewal / material / other | 续约、到期、材料审查、临时问题触发 | 触发频率、审批链、与 H1–H3 的差异 | 同上；不要强行归入 link / brief / monitor |

**判定规则：** 只有当某一起点在多个案例中重复出现、有明确角色与产物、并能与其它起点区分时，才可建议作为首发切片。若多个起点共享同一决策流程，可以合并；若流程、证据、审批不同，必须拆开。**不得因为产品草案写了 link-start，就在 B0 中把它当默认起点。**

### 5.4 过程图与产物

- **Swimlane 图**：横轴为步骤，纵轴为角色 / 系统；每一步标输入、输出、工具、等待、决策点、例外。图中必须有“线下 / 未记录”泳道，避免把聊天或口头步骤消失。
- **Artifact register**：每个产物的名称、用途、来源、日期、版本、许可、脱敏状态、保管人；区分“业务记录”与“研究笔记”。
- **Handoff / wait 清单**：每次角色或系统切换，记录交接物、等待时长、等待对象、是否可并行。
- **Exception catalog**：缺料、错对象、来源失效、权利不明、审批退回、重复认领、跨群 / 私聊复制、临时改 brief 等；每条给一个真实案例或明确“本样本未覆盖”。
- **Workaround 清单**：现有工具不够时人们实际怎么做（私聊问人、手工搜、复制到表格、跳过审批、先做后补）。这些是需求证据，不是“坏习惯”。

### 5.5 任务类型学

类型学必须从 episode 归纳，不从 PMO 能力名或产品页面演绎。PMO 的“粉丝分析 → 合作计划 → 动态监测 → 机会推荐，共四个环节”是 **C 级能力描述** [SRC-LOCAL-PLAN §1.1]，可以作为候选标签，但不能当作已观察流程。

**候选轴（用于确保覆盖，不是最终 schema）：**

| 轴 | 取值示例 | 为什么要分 |
|---|---|---|
| 触发 | 链接 / brief / 监测 / 续约到期 / 材料审查 / 临时问题 | 决定起点、时限、证据需求 |
| 对象类型 | 创作者 / 名人 / IP / 专家 / 代理推荐 / 联盟 / 混合 | 可能对应不同合同、审批、权利链 |
| 决策类型 | shortlist / reject / request_more_info / defer / approve_plan / approve_material / renew / stop | 决定“完成”与“失败”的定义 |
| 证据状态 | 完整 / 部分缺失 / 来源不可达 / 来源冲突 / 权利不明 / 过期 | 决定未知处理与复核负担 |
| 结果 | 推进 / 拒绝 / 搁置 / 放弃 / 返工 / 截止未决 | 负案例是价值与风险的主要证据 |
| 角色模式 | 操作者独做 / 操作者 + 审批者 / 多级审批 / 外部等待 | 决定周期与责任 |
| 紧迫性 / 可逆性 | 高 / 中 / 低；可逆 / 不可逆 | 决定错误代价与复核强度 |
| 渠道 | 飞书群 / P2P / 工作台 / 邮件 / 表格 / 线下 | 决定入口与审计边界 |

**归纳规则：**

1. 两个 episode 只有在**流程、决策标准、证据需求、审批角色**至少一项不同时，才拆成不同任务类型；否则合并。
2. 每个任务类型必须有定义、真实案例、角色、输入、输出、完成 / 失败状态、未知处理、证据来源。
3. 未能覆盖的类型标 `uncovered`，不推测其流程。
4. 任务类型不是产品功能清单；一个任务类型可以对应多个未来功能，一个功能也可以服务多个类型。
5. **Job 候选**来自任务类型中“值得优先解决的具体决策任务”，不是“做一个背调卡 / 看板 / 机器人”。

## 6. 访谈与情境观察

GOV.UK Service Manual 将 “Contextual research and observation” 与 “Using in-depth interviews” 列在 “User research methods” 下 [SRC-B0-GOVUK-01 §“User research methods”]，并在 discovery 页把 “observe people to see how they do things now and what problems or barriers they face”“use interviews and visits to explore relevant aspects of their lives and work”“examine existing data (for example analytics, back-office workflow and support logs)” 列为典型活动 [SRC-B0-GOVUK-02 §“How to do user research in discovery”]。因此 B0 不只用访谈，而是“访谈 + 观察 + 既有记录”三角。

### 6.1 访谈原则

- **问最近一次，不问一般情况。** NN/g 明确建议：“Jog the memory by asking about specific events rather than about general processes. Remembering a particular incident will nudge the user's memory and enable them to give you meaningful details.” [SRC-B0-NNG-01 §“2. Prepare a Guide”]。好的开放式问题包括“Tell me about the last time you [did something].” [同上]。
- **问行为、产物、时间、角色、等待、返工，不问意愿。** NN/g 明确写道：“Since interviews are an attitudinal method, they collect reported behaviors (rather than observed behavior).” [SRC-B0-NNG-01 §“Limitations of Interviews”]。其列出的自述数据限制包括 “Poor or faulty recollection”“Missing details”“Social-desirability bias” [同上]。因此必须用产物和观察三角验证。
- **追问具体化。** “When did this happen?” “How long did it take you?” “Has this happened to you before?” [SRC-B0-NNG-01 §“2. Prepare a Guide”]。不要接受“经常”“很快”“大概”。
- **非诱导。** 访谈质量高度依赖访谈者技巧；“If the interviewer asks many leading questions, the validity of the data will be compromised.” [SRC-B0-NNG-01 §“Limitations of Interviews”]。问题中不嵌入答案，不评价对方做法。
- **分开角色。** 操作者与审批者分开访谈；同一问题分别问，比较差异，不替对方回答。
- **记录可追溯。** 每条笔记带 `episode_id`、角色、日期、来源类型（自述 / 产物 / 观察）、证据等级；不写人名、handle、合同金额。

### 6.2 最近行为问题库

以下问题按访谈阶段分组；每次只选与当前 episode 相关的 6–10 个，不逐条念完。问题是**中文示例**，可按参与者语言调整。

**A. 开场与同意**

1. “我想了解你们现在实际怎么做合作判断，不是评估你个人，也不是推销工具。可以吗？”
2. “我会记笔记 / 录音（如同意），只用于本研究；你可以随时停止或跳过问题。可以吗？”
3. “你在这个流程里主要做什么？最近一次参与是什么时候？”

**B. 最近案例重建**

4. “请选最近一次你亲自参与的合作评估 / 拒绝 / 搁置，带我按时间顺序走一遍：最早是什么触发了它？”
5. “当时你手上有什么材料？第一眼看到的是什么？”
6. “你第一步做了什么？打开了哪个文件 / 问了谁 / 发了什么消息？”
7. “这件事最后停在哪？谁在什么时候做了什么决定？”

**C. 触发与起点**

8. “这次是别人发链接给你、给你 brief、系统提醒、还是你自己发现的？”
9. “最近一个月，这种触发大概有几次？最近一次是哪天？”（用最近行为锚定，不要求精确统计）
10. “有没有一次是从 brief 开始、而不是从某个人开始的？那次流程有什么不同？”

**D. 信息与证据**

11. “你做判断时实际看了哪些信息？哪一条是必须的？”
12. “这条信息你从哪里拿到的？最后一次更新是什么时候？”
13. “有没有你需要的但拿不到的信息？你当时怎么处理？”
14. “如果信息缺失，你会补料、降级判断、还是放弃？最近一次是哪样？”
15. “你有没有遇到过两个来源说法不一致？你怎么处理？”

**E. 角色与决定权**

16. “哪些部分你能自己决定？哪些必须谁批？”
17. “最近一次审批是谁做的？他 / 她看了什么才批 / 不批？”
18. “最近一次被退回 / 要求补料，退回意见是什么？”
19. “你有没有在没批的情况下先做过什么？后来怎么处理？”

**F. 等待、返工与例外**

20. “这一步你等了多久？在等谁 / 等什么？”
21. “这次有没有返工 / 重做？因为什么？花了多久？”
22. “有没有一次因为信息错了 / 对象认错了 / 数据过期了，导致重做？”
23. “最近一次跨群 / 私聊 / 表格复制信息是什么场景？为什么不在一个地方做？”

**G. 负面 / 拒绝 / 搁置案例**

24. “最近一次被拒绝的合作，拒绝理由是什么？谁提出的？你当时同意吗？”
25. “最近一次被搁置 / 放弃的案例，卡在哪？后来有没有再启动？”
26. “有没有一次你事后觉得判断错了 / 后悔了？当时缺了什么？”
27. “有没有一次流程本身没问题，但结果还是不好？为什么？”

**H. 替代方案**

28. “上次没有这个工具时，你用了什么替代？哪个最有用？”
29. “现有表格 / 群 / 平台 / 第三方看板，哪里最不够用？最近一次具体怎么不够？”
30. “如果明天工具消失，你会怎么完成同样的事？”

**I. 信任与停止信号**

31. “什么情况下你会不信任这个产物 / 不会拿它做决定？”
32. “如果这个产物错了，最坏会发生什么？谁会受影响？”
33. “什么样的错误你可以接受？什么样的一次都不能有？”
34. “什么情况下你会停止使用 / 要求下线？”

**J. 收尾**

35. “还有哪件事是我没问、但你觉得重要的？”
36. “我可以把整理后的过程图发给你校验吗？你希望怎么收到？”
37. “你建议我还应该找谁了解哪个角色 / 哪个案例？”

**明确不要问（would-you-use wishlist）：**

- “如果有这个功能你会用吗？”
- “你觉得能省多少时间 / 多少钱？”
- “你愿意为它付多少钱？”
- “你喜欢哪个方案 / 哪个界面？”
- “你觉得 AI 能不能解决？”
- “这个想法好不好？”
- “你们未来会不会需要？”

理由：这些是假设性意愿或社会赞许回答，不能作为行为证据；NN/g 也提醒访谈是自述行为，需与观察 / 行为数据互补 [SRC-B0-NNG-01 §“Limitations of Interviews”]。如果参与者主动谈未来，记录为 `stated_expectation`，不当作 adoption 证据。

### 6.3 情境观察

GOV.UK 将 contextual research 定义为“visiting people in their everyday environment (like their home, work or school) to observe how they do an activity.” [SRC-B0-GOVUK-03 §开头]。其价值在于“Watching someone complete a task in familiar surroundings with their own equipment (and usual distractions) can help you understand what they need from your service.” [同上]。它适合“understand the wider problem”“see how people use your service in a real-life context using real data, documents and devices”“learn more about any barriers or problems people experience, and how they try to overcome them” [SRC-B0-GOVUK-03 §“When to do contextual research”]。

**观察计划：**

- 每次 1–3 小时；一天不超过 4 次 1 小时或 2 次 3 小时；观察消耗注意力，不排满 [SRC-B0-GOVUK-03 §“Plan the research”]。
- 两人一组：一人记录 / 拍照 / 录音，一人主持与照看参与者；也便于分工观察 [SRC-B0-GOVUK-03 §“Work in pairs”]。
- 准备 discussion guide：介绍脚本、访问结构、清单；保证多场覆盖同一主题、参与者体验一致 [SRC-B0-GOVUK-03 §“Create a discussion guide”]。
- 观察方式三选一，并记录选择：静默观察（自然但可能不懂原因）、偶尔提问（平衡真实与理解）、边做边解释（理解最深但会改变行为）[SRC-B0-GOVUK-03 §“Design the visits”]。
- 让活动尽量自然，保持安静、减少影响；不懂时在过程中或结束后追问 [SRC-B0-GOVUK-03 §“Do the research”]。
- 取得所有参与者（包括后来加入者）的知情同意；拍摄 / 录音新增内容前再次确认 [SRC-B0-GOVUK-03 §“Do the research”]。

**Radar 适配边界：**

- 只观察**内部工作表面**；敏感窗口关闭；不读取私聊、合同、个人资料、第三方 PII。
- 只用**已提供的脱敏案例**；观察中若出现真实第三方信息，立即停止、跳过、记录 `not_observed`，不复制。
- 不录屏私聊 / 合同；不 covert 观察；不进入个人设备中与工作无关的区域。
- 不能观察时，明确写 `observation_not_permitted`，用产物 + 访谈补足，并声明“未观察到的行为不等于不存在”。

### 6.4 伦理与脱敏

- **知情同意**：目的、自愿、可停止、记录方式、谁可访问、保存期限、删除方式、是否匿名引用；参与者可在事后撤回 [SRC-B0-GOVUK-03 §“Do the research” 要求 informed consent]。
- **最小化**：只收集判断任务所需信息；角色、决策、时间、证据类型足够，姓名 / handle / 联系方式 / 合同金额 / 健康 / 家庭 / 儿童信息不需要。
- **脱敏在收集时发生**：用伪 ID；姓名 / handle / 联系方式 / 金额替换或删除；如必须保留结构，用“某创作者 / 某市场 / 某价位段”代替。
- **第三方不接触**：不联系创作者、代理、平台、客户；不查个人创作者主页；不发私信 / 邮件 / 好友申请；不提交合作申请。案例中的第三方只作为“对象类型”被讨论，不作为可识别个人被研究。
- **不收集秘密**：不要求参与者展示合同全文、报价、个人信息；只要求结构、脱敏样例、决策理由。若敏感信息意外出现，停止记录、不复制、报告 owner。
- **安全保存**：研究笔记与原始产物分开；访问列表最小化；到期删除；不在模型输入、公共仓库、聊天群中放置原始案例 [C：本文建议；与 SRC-LOCAL-BOUNDARY“不读取飞书私聊、群聊、用户资料”一致]。
- **升级**：若发现潜在违法 / 伤害 / 权利冲突，停止研究动作，交业务 owner / 法务处理；研究者不自行调查或定性。

### 6.5 操作者 vs 审批者：问什么不同

| 维度 | 操作者（Operator） | 审批者（Approver） |
|---|---|---|
| 关注 | 实际步骤、工具、找资料、补料、返工、耗时 | 决策标准、风险、否决理由、证据信任、复核负担 |
| 典型问题 | “你第一步打开什么？”“这条信息从哪来？”“这次返工因为什么？” | “你看到什么才批？”“上次为什么拒？”“哪些证据你不信？” |
| 产出 | 过程图、artifact register、effort / rework 证据 | 决策标准、stop signal、review burden、责任边界 |
| 不能替代 | 不能替审批者说“为什么批 / 不批” | 不能替操作者说“实际怎么找 / 怎么补” |
| 记录 | `operator_note` | `approver_note` |
| 分歧 | 操作者认为“已经够了” | 审批者认为“还缺 X” → 记录为 handoff / evidence gap，不强行调和 |

**复核者（法务 / 品牌资产 / 合规 / 财务）**是第三类角色：他们不一定做合作决定，但会退回材料、限制用途、要求补证。B0 必须单独问他们的**退回理由、审查依据、等待时间、对下游的约束**；不能把“审批者”与“复核者”混成一个人。

## 7. 基线测量：公式、分母与缺失

### 7.1 原则

- **同一个 episode、同一个定义**： baseline 与后续比较必须用同一任务类型、同一结果定义、同一时间窗；否则不比较。
- **本文不写任何实测值**；所有公式等待 B0 实测填充。
- **不设固定阈值 / 接受线 / 目标值**；阈值必须由业务 owner / D11 在需求阶段批准。
- **报分布与逐例**，不只报均值；小样本不做统计推断。
- **标注来源**：`observed`（观察）/ `artifact`（记录）/ `estimated`（访谈估计）/ `unknown`；不把估计写成观测。
- **失败、拒绝、搁置、返工都进分母或单独报告**；不静默剔除。

### 7.2 时间与投入公式

设一个 episode `e`：

| 指标 | 公式 / 定义 | 分母 / 单位 | 数据来源 | 备注 |
|---|---|---|---|---|
| `T_total(e)` | `t_close(e) - t_trigger(e)` | 日历小时 / 天 | 记录、访谈、观察 | 端到端 wall-clock；不是人工投入 |
| `T_active_elapsed(e)` | 所有主动工作区间的并集 | 日历小时 | 观察、时间记录、估计 | 并行工作不重复计时 |
| `E_active_role(e)` | 角色 `r` 的主动人时 | 人时 | 观察、记录、估计 | 分角色报告 |
| `E_active_total(e)` | `Σ_r E_active_role(e)` | 人时 | 同上 | 可用并行工作相加 |
| `T_review_elapsed(e)` | 人工复核 / 审批实际占用区间并集 | 日历小时 | 观察、记录、访谈 | 与等待分开；复核不一定返工 |
| `E_review_role(e)` | 角色 `r` 的复核 / 审批人时 | 人时 | 观察、记录、估计 | 与操作人时分开 |
| `T_wait_internal(e)` | 内部排队 / 调度等待区间并集 | 日历小时 | 记录、访谈 | 不含主动工作与复核 |
| `T_wait_external(e)` | 等外部对象 / 数据 / 批准区间并集 | 日历小时 | 记录、访谈 | 与内部等待分开 |
| `T_queue_other(e)` | 其他内部队列 / 阻塞区间 | 日历小时 | 记录、访谈 | 不能归入上述类别时使用 |
| `T_rework_elapsed(e)` | 因缺陷 / 变更 / 退回重做区间并集 | 日历小时 | 记录、访谈、观察 | 可与主动 / 复核重叠；需说明 |
| `E_rework(e)` | 返工人时 | 人时 | 同上 | 分原因 |
| `T_unclassified(e)` | `T_total - 上述已分类区间` | 日历小时 | 计算 | 不强制归零；报告 |
| `handoff_count(e)` | 角色 / 系统切换次数 | 次 | 过程图 | 切换越多，协调成本越高 |
| `review_rounds(e)` | 进入人工复核的轮次 | 轮 | 记录 | 与 `rework` 区分：复核不一定返工 |
| `first_pass_accept(e)` | 首次提交即被接受（无实质返工） | 布尔 | 记录 | 与 `rework_rate` 配套 |

**时间恒等式（仅当区间按“主要原因”互斥划分时成立）：**

`T_total = T_active_elapsed + T_review_elapsed + T_wait_internal + T_wait_external + T_queue_other + T_rework_elapsed + T_unclassified`

如果复核或返工与主动工作重叠，不能用上述恒等式强行相加；应改用时间分配台账（每个区间一个主因，次要原因另记标签），并报告重叠，不制造虚假恒等。

**派生比例：**

- `active_ratio = T_active_elapsed / T_total`
- `review_time_share = T_review_elapsed / T_total`
- `internal_wait_share = T_wait_internal / T_total`
- `external_wait_share = T_wait_external / T_total`
- `rework_time_share = T_rework_elapsed / T_total`
- `handoff_per_episode = handoff_count`
- `review_rounds_per_episode = review_rounds`

**报告规则：** 分别报“日历时间”“人工投入”“复核”“等待”“返工”，**不要用一个“耗时”混在一起**。例如“这个任务要两周”可能主要是外部等待，不等于人工投入两周，也不等于复核两周。

### 7.3 成本公式

| 指标 | 公式 | 分母 | 备注 |
|---|---|---|---|
| `C_person(e)` | `Σ_r E_total_nonoverlapping_role(e) × hourly_rate_r`；`E_total_nonoverlapping_role` 为该角色去重后的实际投入，复核/返工/协调仅作分类或子集，不重复相加 | 互斥人时 × 已批准费率 | 费率未批准时只报人时，`cost=unknown` |
| `C_direct(e)` | 该 episode 直接发生的数据 / 工具 / 供应商 / 差旅费用 | episode | 不含分摊；无记录写 unknown |
| `C_overhead_allocated(e)` | 按已批准分摊规则计入的固定成本 | episode | 分摊规则未批准则单列，不混入 |
| `C_total(e)` | `C_person + C_direct + C_overhead_allocated` | episode | 三项分开报告更可靠 |
| `C_per_episode` | `Σ C_total(e) / N_episodes` | 全部纳入 episode | 含拒绝 / 搁置 / 返工 |
| `C_per_decided_episode` | `Σ C_total(e) / N_decided` | 有决定的 episode | 拒绝也是决定；失败 / 放弃单报 |
| `C_per_attempt` | `Σ C_total(e) / N_attempts` | 所有尝试 | 含重试 / 取消；分母不是成功请求 |

**规则：**

- `E_coordination_role` 是协调 / 排期 / 催办 / 交接人时；无法单独取得时并入 `E_active_role` 并注明，不静默遗漏。
- 没有批准的费率 / 报价，**不编造成本数字**；只报人时、费用项与未知 [SRC-LOCAL-PLAN §8.7：“模型与数据价格从实际报价日期取得，不硬编码本轮未核验价格”]。
- 采购固定成本、订阅、基础设施与每任务边际成本分开；不把固定成本摊成“每任务很便宜”。
- 失败 / 重试 / 取消的消耗计入成本，不只算成功任务 [SRC-LOCAL-EVAL §3：“单任务成本：完成/失败一项任务的模型、数据及基础设施边际费用；分母为业务任务，不只成功请求”]。
- 不做 ROI、回收期、净现值；B0 只建立成本结构，不承诺收益。

### 7.4 决策有用性

“有用”不是单一分数。B0 用以下结构化指标，分别由操作者与审批者记录：

| 指标 | 定义 / 公式 | 分母 | 备注 |
|---|---|---|---|
| `decision_latency(e)` | `t_decision - t_ready` | 有决定的 episode | 证据就绪到决定的时间 |
| `evidence_coverage(e)` | 决策时已具备的必需证据项 / 该决策类型定义的必需证据项 | 每类决策的定义项 | 分母由业务 / 法务提出，B0 只测试可行性；缺失≠0 |
| `traceability_rate(e)` | 有来源与定位单元的事实主张 / 被检查的事实主张 | 被检查主张 | 只挂 URL 不等于可追溯 |
| `unknown_disclosure(e)` | 明确记录未知 / 限制的 episode / 存在未知的 episode | 存在未知的 episode | 不把未知伪装成已知 |
| `decision_reversal_rate` | 在定义窗口内被推翻 / 修改的决定 / 已做决定 | 已做决定 | 窗口由业务 / D11 定义；本文不设默认值 |
| `rework_cause_mix` | 按原因计数的返工 episode：缺证据 / 错对象 / 过期数据 / 权利不明 / brief 变更 / 审批偏好 / 流程错误 / 其他 | 返工 episode | 多标签时分别计数 |
| `review_burden(e)` | 审批者 / 复核者主动审阅分钟数 + `review_rounds` | 被审阅产物 | 与“审批者人数”分开 |
| `operator_approver_disagreement` | 操作者与审批者对“证据是否足够 / 决定是否合理”的不一致次数 | 共同评审的 episode | 记录分歧点，不强行一致 |
| `usefulness_rating(e, role)` | `changed_decision / accelerated / confirmed / no_effect / misled / not_used` + 理由 | 每个角色每 episode | 自述判断，不等于 adoption；附证据 |

**禁止：** 把上述指标加权成一个“决策质量分”；在没有人审金标的情况下宣称“准确率”；把“审批者说有用”当成“实际采用”；把 `decision_reversal_rate` 低当成“决策正确”（也可能是不敢改）。

### 7.5 实际采用

| 指标 | 公式 | 分母 | 定义 / 备注 |
|---|---|---|---|
| `eligible_episodes` | 任务清单中符合首发范围的 episode 数 | — | 分母来自 inventory，不来自工具日志 |
| `offered_episodes` | 向业务提供产物 / 服务的 episode 数 | `eligible_episodes` | 提供不等于接受 |
| `accepted_episodes` | 产物被用于真实决策记录的 episode 数 | `offered_episodes` | “使用”定义见下 |
| `actual_adoption` | `accepted_episodes / eligible_episodes` | `eligible_episodes` | 主采用指标；分母含未提供 / 未接受 |
| `offer_acceptance` | `accepted_episodes / offered_episodes` | `offered_episodes` | 次指标；区分拒绝 / 无响应 / 不合格 |
| `coverage` | 首发范围内被纳入的 episode / 同类型全部 episode | 任务清单 | 检查是否只挑了容易的任务 |
| `reuse_rate` | 第二次在新 episode 使用的人数 / 至少使用过一次的人数 | 使用过一次的人 | 观察窗由研究计划定义 |
| `shadow_work_rate` | 需要工具外手工补做的 episode / 全部 episode | 全部纳入 episode | 工具外工作越多，真实采用越低 |
| `abandonment_rate` | 开始后放弃的 episode / 开始的 episode | 开始的 episode | 放弃原因单列 |

**“使用”的操作定义（必须在 B0 计划中写明并经业务 owner 确认）：** 产物或其证据被写入真实决策记录 / 审批记录，或被审批者在决定时明确引用；**不是**“登录过”“打开过”“在群里收到过”。如果无法取得决定记录，用审批者事后确认 + 产物引用作为较弱证据，并标注 `self_report`。

**PMO 约束的处理：** PMO 的 SOP 候选记录为“4 次/周、1 次打回、35% 返工”，且按 PMO 自己的 Stage 3 规则“三项都不满足” [SRC-LOCAL-PMO §4.5]；PMO 还记录 Radar 没有 `measuredActions`，因此“20% 不能说明业务已采纳” [SRC-LOCAL-PMO §4.6]。这些是 **PMO 口径，不是本项目实测或目标** [SRC-LOCAL-PLAN §1.5]。B0 **不得为了凑提问数 / 打回数而制造需求**，也不得把 PMO 的 4 / 1 / 35% 当作新项目的基线或验收线；实际采用必须从真实 eligible episodes 观察。

### 7.6 测量协议与偏差控制

- **回顾 + 并行观察**：先对近期 episode 做回顾重建，再在有限窗口内做并行观察 / 跟岗；回顾依赖记忆，观察依赖同意与可得性，两者互补。
- **优先用产物时间戳**：表格状态变更、审批记录、邮件 / 日历时间、材料登记时间；没有时间戳才用访谈估计，并标 `estimated`。
- **缺失登记**：每个指标记录 `observed / artifact / estimated / unknown`、缺失原因、是否影响分母；不把缺失当 0。
- **选择偏差**：按结果分层选案例；记录拒绝参与、无法安排的角色、无法取得的案例；不把“愿意接受访谈的人”当全体。
- **回忆 / 社会赞许偏差**：问最近具体事件、要产物、交叉验证；NN/g 明确列出 poor recollection、missing details、social-desirability bias [SRC-B0-NNG-01 §“Limitations of Interviews”]。
- **观察者效应**：记录观察方式、在场人数、参与者是否改变行为；与产物 / 访谈对照，不把观察当完全自然。
- **分母漂移**：先冻结任务清单与范围；中途变更要版本化并说明影响，不悄悄扩大 / 缩小分母。
- **不静默剔除**：失败、拒绝、搁置、放弃、未知全部报告；可以分层，但不能只报成功。
- **小样本**：逐例表 + 范围 + 选择标准；不做显著性检验、不推断总体、不宣称因果。

### 7.7 Baseline 与后续比较（只定义方法，不填值）

B0 的 baseline 不是为了凑一个“改善百分比”，而是为了在后续需求 / 试点阶段能问同一个问题、用同一个分母。比较规则：

| 比较量 | 公式 | 前提 | 禁止 |
|---|---|---|---|
| 时间差 | `ΔT_total = T_total_post - T_total_baseline` | 同一任务类型、同一结果定义、同一时间口径 | 把不同任务类型 / 不同对象类型混在一起比较 |
| 人工投入差 | `ΔE_active_total = E_active_total_post - E_active_total_baseline` | 同一角色范围、同一记录方式 | 用“工程空闲”代替业务 / 法务人审 |
| 外部等待差 | `ΔT_wait_external = T_wait_external_post - T_wait_external_baseline` | 等待对象与外部条件可比 | 把外部审批变快归功于产品 |
| 复核差 | `ΔT_review_elapsed` / `ΔE_review_role` / `Δreview_rounds` | 同一审批层级与复核标准 | 用“少复核”冒充“效率提升”而忽略风险 |
| 返工差 | `Δrework_rate` / `ΔE_rework` / `Δrework_cause_mix` | 同一返工定义与原因分类 | 只报返工下降，不报漏检 / 错误上升 |
| 成本差 | `ΔC_total` / `ΔC_per_episode` | 同一成本边界、同一费率版本 | 把一次性建设成本摊成每任务节省 |
| 决策时延差 | `Δdecision_latency` | 同一定义窗口与决策类型 | 把“更快”当“更好” |
| 采用差 | `Δactual_adoption` / `Δoffer_acceptance` | 同一 eligible 分母与观察窗 | 把“提供更多”当“采用更多” |

**规则：**

- 先配对：同一任务类型、同一结果分层、同一角色范围；不能配对就只做描述，不做前后比较。
- 报告逐例差值与分布，不只报平均差；小样本不报显著性。
- 任何“改善”都要同时报告：任务组合是否变化、选择偏差、外部条件变化、复核质量是否下降、失败 / 拒绝是否被转移。
- **不做因果归因**：没有对照 / 随机化 / 足够样本时，只能说“在本样本中观察到差异”，不能说“Radar 带来了改善”。
- 不设“改善多少才算成功”的固定阈值；接受线由 D11 在需求阶段批准。

## 8. 证据可得性与 job 优先级

### 8.1 证据矩阵

对每个 job 的每个必需证据项，记录：

| 字段 | 说明 |
|---|---|
| `evidence_item` | 具体字段 / 材料 / 判断依据，不写“粉丝数据”这种笼统词 |
| `decision_supported` | 支持哪个决策类型 |
| `source` | 具体来源 / 系统 / 人工提供 |
| `permission_basis` | 公开 / 授权 / 合同 / 采购 / 内部记录 / 未知；法律依据与平台条款分开 |
| `freshness` | 可得时点、更新频率、历史深度 |
| `access_method` | API / 导出 / 人工 / 文档 / 无法取得 |
| `failure_semantics` | 空结果、超时、限流、删除、撤回时业务看到什么 |
| `cost` | 直接费用 / 配额 / 人力；未知写 unknown |
| `owner` | 谁负责取得与维护 |
| `status` | `available / partial / unknown / unavailable` |
| `notes` | 替代路径、降级、风险 |

**规则：**

- “平台存在”不等于“字段可得”；“公开可见”不等于“可合法使用 / 可存储 / 可派生”。每个字段独立核验来源、许可、时效与失败语义；校准笔记明确“Source 报告仅为他项目快照；每个 MVP 字段独立验来源、许可、时效与实际可得性” [SRC-LOCAL-CALIB CAL-05]。
- `unknown` 是独立状态，不能自动变成 `unavailable` 或 `available`；未知要写清“向谁、用什么方法可以变成已知”。
- `minimum_evidence_set` 按决策类型提出，由业务 / 法务在需求阶段批准；B0 只测试“能否取得、缺失时业务怎么做”，不擅自定稿。
- 证据可得性不是价值本身：一个 job 即使证据可得，也可能频率低、后果轻、不可控或无 owner。

### 8.2 定性优先级矩阵

对每个 job 候选，逐列填写**证据指针 + 判断**；不用加权总分。

| 维度 | 判断问题 | 取值 / 证据要求 |
|---|---|---|
| **频率** | 在观察窗口内实际出现多少次？跨角色是否都提到？ | `recurring / occasional / rare / unknown`；证据：episode 计数或案例列表，不用“感觉很多” |
| **严重性** | 错误 / 延迟 / 返工的实际后果是什么？可逆吗？ | `high / medium / low`；证据：真实案例、损失类型、是否阻塞决定；不写假设金额 |
| **可控性** | Radar 的拟议范围能否实质改变这一步？是“ inform 决定”“支持决定”还是“执行动作”？ | `high / partial / low / outside_scope`；外部依赖与权限边界写清 |
| **证据可得性** | 必需证据能否合法 / 技术取得？ | `available / partial / unknown / unavailable`；引用 8.1 矩阵 |
| **复核负担** | 人工审阅时间、轮次、注意力、自动化偏差风险？ | `high / medium / low`；证据：观察 / 记录；没有就写 unknown |
| **所有权** | 是否有具名业务 owner / DRI 与可用容量？ | `named_owner_with_capacity / named_owner_capacity_unknown / no_owner / shared_unclear` |
| **替代覆盖** | 现有工具 / 流程是否已经足够？缺口是什么？ | `no_adequate_alternative / partial_with_gaps / adequate_alternative`；证据：替代方案案例 |

**可选补充列（不是必需）：** 决策关键性、数据敏感性、时间紧迫性、跨团队依赖、可测量性。补充列也必须给证据指针，不能只打分。

**分层规则（不做加权）：**

- **Tier 1（可进入需求候选）**：频率 recurring、严重性至少 medium 且有真实后果、可控性 high / partial（在拟议范围内）、证据 available 或有明确 bounded path、复核负担可接受、有具名 owner、替代方案不足。允许一个明确弱点，但必须写明 trade-off 与补偿研究。
- **Tier 2（研究 / 重构）**：问题真实，但有一个关键缺口：证据路径未知、owner 容量未知、可控性 partial、替代方案可能已足够。先做指定研究，不进入需求冻结。
- **Tier 3（Hold / Not now）**：频率低、后果轻、不可控、无 owner、替代方案足够、或证据不可得。记录原因，不硬做。
- **Excluded**：不属于合作决策、违法 / 不伦理、无可允许数据、需要自动对外动作、无人承担结果。

**禁止假精确：**

- 不把 7 个维度乘权重求和；不把 H/M/L 转成 1–5 分再平均；不画“价值 / 复杂度”四象限来代替证据。
- 如果会议需要一个数字排序，明确标注“任意讨论辅助，不是测量”，展示原始单元格、权重假设与敏感性；不得写入验收或对外报告。
- 高频但不可控的 job 不能因为“痛”就排 Tier 1；高严重但无证据路径的 job 只能是 Tier 2 研究；无 owner 的 job 一律 Hold。

## 9. 有界纸面 / 礼宾演练

### 9.1 目的与定义

**目的：** 在写代码 / 接模型 / 接平台之前，用**内部、纸面、人工**方式测试：拟议产物是否可理解、证据是否可追溯、未知是否被保留、复核负担是否可接受、角色与流程是否匹配。它验证的是**工作流与产物形态**，不是模型准确率、系统性能或生产可用性。

**两种形式：**

- **纸面演练（paper rehearsal）**：静态 mock（纸 / 幻灯片 / 表格），参与者按拟议流程阅读、判断、标注；不运行任何系统。
- **礼宾演练（concierge rehearsal）**：研究者在参与者知情的前提下，**手工**从提供的脱敏案例包中整理出一份模拟背调 / 决策 memo / 材料清单，供内部操作者与审批者评审；参与者知道这是演练，不是生产服务。

### 9.2 明确禁止

- **不运行付费模型 / API**；不调用任何模型供应商。
- **不做 live 采集 / 抓取 / 平台 API / 浏览器自动化**。
- **不使用 token / WebSocket / 飞书消息 / 卡片回调**；不向任何群或个人发送消息。
- **不联系真实创作者 / 代理 / 客户**；不请求材料、不询价、不提交合作申请。
- **不做真实合作决定、合同、付款、素材使用**；演练产物不得用于对外沟通或真实投放。
- **不做生产验收、技术评测、模型质量声明**；演练结果不能写成“准确率”“达标”“可上线”。
- **不写代码 / 不安装 / 不 Git / 不部署**。

### 9.3 输入包与案例 manifest

每个案例包包含：

- 脱敏 brief（目标、市场、品类、已知约束；预算未知就写 unknown）。
- 对象 / 账号描述（只来自**提供的材料**，不做外部查找；不写真实姓名 / handle）。
- 证据集：每条证据带来源、日期、权限标签、定位单元；缺失项明确列出。
- 当前流程产物：表格骨架、审批单骨架、拒绝说明、材料登记骨架（已脱敏）。
- `case_manifest`：case ID、来源、脱敏方式、完整度、允许用途、有效期、保管人。
- 明确 `unknowns`：哪些字段缺失、为什么、对判断有什么影响。

**证据 parity（公平性）：**

- 所有生产者 / 评审者拿到**同一案例包、同一说明、同一时间预算**；不允许外部搜索、不允许问同事、不允许用模型。
- 如果某案例包对某角色不可见（如报价只给审批者），记录为**角色可见性差异**，不假装所有人看到同样信息。
- 记录**选择性缺失**：缺了哪些案例 / 字段、为什么（不可得 / 不允许 / 脱敏去掉）、这对结论的限制；不把缺失填平。

### 9.4 流程

1. **冻结案例包与问题**：演练前不改材料；问题写清“要模拟哪个决策、用什么产物、谁来评审”。
2. **独立产出**：两名生产者（或一名生产者 + 一名独立复核者）在相同时间预算内，各自从案例包整理产物；不互相看。
3. **操作者评审**：操作者按真实工作方式阅读产物，think-aloud：先看什么、信什么、疑什么、下一步做什么、花多久、哪里卡住。
4. **审批者评审**：审批者单独评审：决策标准、缺什么证据、会不会拒、复核多久、责任边界。
5. **证据审计**：把产物中的每条事实主张映射到案例包来源；统计无来源主张、错误引用、未知是否保留、是否越权推断。
6. **复盘**：操作者与审批者分开说，再一起对照；记录分歧、误解、角色冲突；问“什么会改变你的决定”。
7. **报告**：逐案例、逐角色；不合并成单一“满意度”分数。

### 9.5 评审质量控制

- **至少两名评审者**（操作者 + 审批者；如涉及权利，加一名法务 / 品牌资产复核者）。**单一评审者不能当金标。**
- **独立首轮**：先各自评，再合议；合议规则事先写明（如何记录分歧、谁裁决、裁决依据）。
- **盲评 / 顺序随机**：可行时隐藏生产者身份 / 条件，随机化评审顺序，减少顺序与期望效应。
- **校准**：用一例练习案例统一评审语言；练习案例不计入结果。
- **记录角色 / 资历 / 利益冲突**：评审者是否参与该案例、是否与生产者同一团队；有冲突的评审单独标注。
- **演练保真度**：对比演练任务与真实 episode 的时间、利害关系、工具、信息差异；差异写入限制，不把演练当真实。
- **评审者负担**：记录审阅分钟数、轮次、疲劳 / 中断；复核负担本身就是价值验证的一部分。

### 9.6 分析与禁止推断

- 报告 **N、选择标准、逐案例结果、评审者分歧、缺失字段、演练保真度差异**。
- **禁止**：从少量案例宣称 ROI、生产力提升、转化率、PMF、因果效应；禁止把演练时间外推为生产节省；禁止把“评审者说有用”写成“实际采用”。
- 可以说：“在本演练的 N 个案例、这些评审者、这些材料下，产物是否可理解、证据是否可追溯、未知是否保留、复核负担如何。” 这是**限定范围内的观察**，不是总体结论。
- 如果必须报告时间，写“演练中位审阅时间”，并注明“非生产时间、非效率提升证据”。
- **退出：** 产物可理解、证据可追溯、未知保留、复核负担可接受、角色匹配 → 作为需求输入；否则 reframe；不确定 → hold / 补充研究。

## 10. 退出状态：advance / reframe / hold / stop

### 10.1 四种状态

| 状态 | 含义 | 需要的证据条件 | 它授权什么 | 它不授权什么 |
|---|---|---|---|---|
| **Advance** | 问题、范围、基线、证据路径、owner 足够进入需求阶段 | 至少一个真实 episode 端到端可复述；操作者与审批者分别确认；必需证据有可行路径或明确降级；业务 owner 接受问题 / 范围 / 停止信号；无致命法律 / 伦理问题 | 进入需求阶段，起草 `R-radar-charter` / `R-radar-mvp` | 不授权开发、live 数据、付费模型、消息发送、采购、发布 |
| **Reframe** | 问题真实，但拟议任务 / 起点 / 对象 / 决策 / 细分错了 | 案例显示真实痛点与草案不匹配；或 link / brief / monitor 起点不成立；或对象类型流程差异大 | 回到 B0.1–B0.2 重新选案例 / 归纳类型 | 不授权按旧草案继续需求冻结 |
| **Hold** | 缺少 owner、访问、证据、决策权或资源 | 关键角色无法参与；必需证据未知且无路径；无人接受问题；法律 / 数据边界不清 | 保留研究开放，记录解除条件 | 不授权开发、采购、承诺日期；不把“暂时做不了”写成“不需要” |
| **Stop** | 问题不重要、替代方案足够、无合法证据路径、风险 / 成本不可接受 | 真实案例显示影响小；现有流程已足够；必需证据不可得；无人承担；风险不可接受 | 停止 / 归档 B0，记录原因 | 不授权“以后再说”的隐性继续；不把 stop 写成失败 |

**判定原则：**

- 四种状态都是**研究建议**，最终由业务 owner / 发起人按授权记录；Agent 不能签署。
- 不允许“基本可用”“先做做看”作为第五种状态；缺证据就是 hold / reframe，不是 advance。
- Advance 只代表“值得进入需求”，不代表 MVP 冻结、预算批准或技术可行。

### 10.2 发现、决定、PoC 授权必须分开

| 类型 | 定义 | 谁记录 | 能授权什么 | 不能授权什么 |
|---|---|---|---|---|
| **Finding（发现）** | “在 N 个案例中观察到 X；证据等级 C；替代解释 Y；未知 Z” | 研究负责人 | 作为讨论 / 下一轮研究输入 | 不能当批准、不能当需求冻结、不能当验收 |
| **Decision（决定）** | 具名人类 / 角色接受某个范围、优先级、退出或决策项 | 业务 owner / 发起人 / 法务 / PMO（按 D 项） | 在记录范围内改变项目方向 / 范围 | 不能自动授权 live 数据、付费、消息、发布；不能由 Agent 代签 |
| **PoC authorization（PoC 授权）** | 对某个有界演练 / 技术探测的明确许可：数据、动作、时间、成本、停止条件 | 数据 / 法务 / 业务 / 技术 owner 按范围 | 仅限写明的有界活动 | 不能外推为生产许可；不能覆盖未写明的动作 |

**记录格式：** 每条 finding 带 `claim / evidence_grade / source_locator / confidence / alternative_explanation / unknown`；每条 decision 带 `decision_id / scope / approver_role / date / constraints / expiry / affected_requirements`；每条 PoC authorization 带 `scope / data / actions / duration / cost_cap / stop_conditions / approver`。没有这些字段，不称“已决定”或“已授权”。

### 10.3 B0 退出 memo 模板

`B0-exit-memo` 至少包含：

1. B0 范围、研究问题、未覆盖范围。
2. 案例清单：ID、角色、对象类型、决策类型、结果、证据等级、脱敏状态。
3. As-is 过程图与任务类型学。
4. 基线表：公式、分母、来源、缺失、逐例分布。
5. 证据可得性矩阵：available / partial / unknown / unavailable。
6. Job 优先级矩阵：Tier 1/2/3/Excluded、理由、dissent。
7. 演练报告（如有）：N、选择、逐例、分歧、缺失、保真度限制。
8. Findings：每条带来源定位、等级、置信、替代解释、未知。
9. Unknowns / dissent / 利益冲突。
10. 建议：advance / reframe / hold / stop。
11. **Requested decisions**：只列需要人类决定的 D01–D04 / D12 相关子问题；明确“本 memo 不批准这些决定”。
12. Handoff package 清单。
13. 业务 owner / 发起人 / 产品 BA 的接收记录（如已发生）；未接收写 `not_accepted`。

## 11. B0 与 D01–D04 / D12：只准备相关证据，不强求 12 项全批

### 11.1 原则

决策登记表的状态是“**全部未批准**。这里登记‘谁在何时依据什么证据决定’，不代替 ADR 或业务签核。” [SRC-LOCAL-DECREG 开头]。B0 不能把“研究做完”写成“决策已批”，也不能因为 D05–D11 未批就不做业务发现。正确关系是：

- **B0 需要的最小条件**：研究授权、访谈 / 观察同意、脱敏规则、业务 owner 可参与；不需要 D05–D11 全部关闭。
- **B0 能做的**：为 D01–D04 / D12 的相关子问题提供证据、建议、unknown 与风险。
- **B0 不能做的**：代替发起人 / 业务 owner / 法务 / PMO 签核；不能批准数据采购、技术栈、预算、评测线。
- **B0 不应做的**：为了“凑齐 12 项”而做无关的架构 / 预算 / 技术评审；那会拖死业务发现。

### 11.2 逐项关系

| 决策 | B0 可回答的子问题 | B0 产物 | B0 不能决定 | 签核角色（建议） | 交接到需求的内容 |
|---|---|---|---|---|---|
| **D01 项目身份 / 名称 / 域名** | 研究对象是不是 PMO 的 IP / 名人 Radar，而不是 Echo / VOC；工作身份是否足够支持研究 | 身份假设、来源定位、未决问题 | 最终名称、域名、仓库、是否复用旧站点 | 发起人 / PMO / 技术负责人 | 项目章程中的身份假设与待确认项；不在 B0 改域名 |
| **D02 首发品牌 / 市场 / 品类 / 团队** | 哪个团队 / 市场 / 品类有真实案例、owner 与证据路径；哪个先做 | 案例分布、owner 可用性、范围建议、未知 | 最终业务范围、预算、组织授权 | 品牌业务 owner | 窄范围建议 + 案例证据；需求阶段冻结 |
| **D03 合作对象范围** | IP / 名人 / 专家 / KOL / 联盟 / 代理是否共享同一决策流程；先选哪类 | 对象类型 × 流程差异矩阵、案例 | 合同 / 法务 / 权利链的最终范围 | 品牌 / BD / 法务 | 首发对象类型建议 + 例外清单 |
| **D04 MVP 业务闭环与完成条件** | 用户真实起点是 link / brief / monitor / renewal 还是混合；什么算完成；无 brief 的背调算不算机会 | 起点假设检验、任务类型、完成 / 失败候选、未知 | MVP 冻结、验收线、产品规格 | 业务 owner / 产品 | 已验证的任务切片、完成候选、非目标；需求阶段冻结 |
| **D12 团队 / 排期 / 运行责任** | 实际角色、投入、等待、复核负担、owner 容量；谁可能做 DRI | 角色 / 容量证据、review burden、handoff 清单 | 工期承诺、headcount、值班安排、预算 | PMO / 发起人 / 技术 | 角色与容量输入；排期在 D12 另定 |
| **D05–D11** | 可能暴露数据、法务、技术、评测问题 | 问题清单、证据缺口、风险 | 不能关闭任何一项 | 各自节点 owner | 作为需求 / 设计阶段的开放问题，不在 B0 假装关闭 |

### 11.3 最小 B0 授权 vs D01–D12

| 事项 | 属于 B0 研究授权 | 属于 D01–D12 决策 |
|---|---|---|
| 访谈业务成员 | 是（owner 同意 + 参与者同意） | 否 |
| 观察内部工作表面 | 是（同意 + 脱敏 + 停止规则） | 否 |
| 使用脱敏案例 | 是（数据规则批准） | 否 |
| 纸面 / 礼宾演练 | 是（单独有限授权） | 否 |
| 读取真实平台数据 / API | 否 | D05 / D06 / D09 |
| 调用付费模型 | 否 | D10 |
| 发送飞书消息 / 接真实群 | 否 | D06 / D07 |
| 确定 MVP / 验收线 | 否 | D04 / D11 |
| 采购 / 合同 / 预算 | 否 | D05 / D10 / D12 |

**结论：** B0 只需要“研究许可 + 数据规则 + 参与者同意 + 可选演练许可”，**不需要先关闭 12 项决策**。但 B0 也不能越界做 D05–D11 管辖的动作；发现的问题登记后交给对应节点。

## 12. 交给需求阶段什么

### 12.1 Handoff package

需求阶段接收：

- `B0-exit-memo`（含 finding / unknown / dissent / recommendation）。
- `B0-episode-ledger`（逐例，脱敏）。
- `B0-as-is-map`（swimlane + handoff / wait + exception）。
- `B0-task-typology`（定义、案例、覆盖 / 未覆盖）。
- `B0-baseline-table`（公式、分母、来源、缺失、逐例）。
- `B0-evidence-matrix`（available / partial / unknown / unavailable）。
- `B0-job-matrix`（Tier 1/2/3/Excluded + 理由）。
- `B0-rehearsal-report`（如有；含限制；不得当验收）。
- `B0-source-register`（本文 2.2 的扩展）。
- `B0-open-questions`（含最强未解问题）。

### 12.2 需求阶段的转化规则

| 需求产物 | 从 B0 接收什么 | 不能从 B0 接收什么 |
|---|---|---|
| `R-radar-charter` | 问题、角色、范围建议、owner、停止信号、案例证据 | “已批准”结论；预算 / 排期承诺 |
| `R-radar-mvp` | 任务切片、完成 / 失败候选、非目标、未知处理 | MVP 已冻结；验收线；技术方案 |
| 指标字典 | 基线公式、分母、来源、缺失规则 | 实测值；固定阈值；ROI |
| 验收条件 | 真实案例、失败 / 拒绝 / 搁置形态、证据要求 | 演练结果当验收；小样本因果 |
| 开放问题 | unknowns、证据缺口、dissent | 被静默删除的负面证据 |

**Traceability 规则：** 需求中的每条任务 / 指标 / 非目标，必须能追溯到 B0 的案例、观察或证据；不能追溯的，标为 `hypothesis`，进入下一轮研究或明确假设，不伪装成已验证需求。

**Handoff 评审：** 一次一问；业务 owner 确认“问题、范围、完成、停止信号”；产品 BA 记录；未确认的项标 `not_accepted`，不进入需求冻结。

## 13. 讨论顺序：一次一问

### 13.1 规则

- **一次只问一个问题**；每个回答记录：回答者角色、日期、来源、证据等级、对下一轮研究的影响。
- **不问已知选择**：品牌是 Momcozy、产品形态是 Agent + 工作台、方法路线是 Main、入口是飞书群 @ / P2P，这些已由用户给定，不在 B0 重复问。项目边界原文：“面向跨境电商出海品牌，当前品牌为 **Momcozy**”“构建 **Radar Agent + Radar 工作台**”“飞书是会话入口：群内 @Radar 与 P2P 消息”“从需求调研到交付迭代，参照 https://main.luteos.com/ 的全栈开发路线推进” [SRC-LOCAL-BOUNDARY“用户明确给定的需求”第 1–5 条]。
- **不问假设性意愿**；问最近行为、案例、产物、角色、等待、返工。
- **不把研究问题问成批准**；“你同意这个方案吗”不是 B0 问题。
- **回答为 unknown 时**，记录 unknown 与“谁可能知道”，下一问再追；不替对方猜。
- **每问必须改变下一步研究**：换案例、换角色、补产物、改类型、补证据、调优先级；否则不问。

### 13.2 第一个问题

> **“请指定最近一个真实、可脱敏、且包含拒绝 / 搁置 / 返工其中一种情况的合作决策案例。”**

**为什么是这个问题：**

- 它改变下一轮研究：直接选定第一个 `episode`、第一组角色、第一份产物；没有案例就无法开始 B0.1。
- 它不重复已知的品牌 / 产品形态 / Main / 飞书入口选择，也不问“你愿不愿意用”。
- 它要求负案例，避免只选成功故事。
- 它只问一件事；拿到案例后，**下一问**才问“谁可以授权我们分别访谈它的操作者和审批者”。不在同一轮同时索要案例与授权，避免把两个未知混在一起。

### 13.3 后续顺序（一次一问）

| 顺序 | 问题 | 谁来答 | 产物 | 如何改变下一轮研究 |
|---|---|---|---|---|
| Q1 | 请指定最近一个真实、可脱敏、且包含拒绝 / 搁置 / 返工其中一种情况的合作决策案例 | 业务 owner / 发起人 | `B0-case-01` | 决定第一个 episode；没有案例则 hold |
| Q2 | 谁可以授权我们分别访谈这个案例的操作者和审批者？ | 业务 owner / 发起人 | 授权记录 | 决定参与者；没有授权则 hold，不绕开 |
| Q3 | 这类决策最近一个月实际发生几次？哪类结果最多？ | 操作者 / 审批者 | 频率与结果分布 | 决定样本分层；避免只研究一个稀有案例 |
| Q4 | 这个案例里谁做什么、谁能决定什么？ | 操作者、审批者分别 | 角色 / 决策权表 | 决定后续访谈对象；发现“操作者以为审批者看 X，审批者实际看 Y” |
| Q5 | 你手上有什么产物 / 表格 / 记录？哪些可以脱敏？ | 操作者 / 数据 / 法务 | artifact register | 决定能否重建时间线；不能脱敏就换案例 |
| Q6 | 这个案例从触发到决定，实际时间花在哪？ | 操作者 / 审批者 | episode ledger、初步基线 | 决定是否需要并行观察 / 跟岗 |
| Q7 | 做这个判断必需的证据，哪些能合法 / 技术取得？ | 数据 / 法务 / 操作者 | evidence matrix | 决定 job 是 Tier 1 还是 Tier 2 研究 |
| Q8 | 什么情况下你会拒 / 退回 / 停止使用这个产物？ | 审批者 / 复核者 | stop signals、review burden | 决定复核设计与演练评审标准 |
| Q9 | 按矩阵，哪个 job 应先做？为什么不是另一个？ | 业务 owner | job matrix、Tier | 决定需求候选；记录 dissent |
| Q10 | 是否授权一次有界纸面 / 礼宾演练？用哪些脱敏案例？ | 发起人 / 业务 owner / 法务 | PoC authorization | 决定是否演练；不授权则直接需求交接 |
| Q11 | 谁接受 B0 退出建议？需要哪些人类决定？ | 发起人 / 业务 owner | exit memo、requested decisions | 决定 advance / reframe / hold / stop |

**讨论停止条件：** 如果 Q1 无法给出案例，或 Q2 无法取得授权，B0 进入 **hold**；不继续写抽象方案。如果 Q3–Q6 显示问题不存在 / 频率极低 / 不可控，进入 **reframe / stop**，不硬推到需求。

## 14. 质量控制与反模式

| 反模式 | 为什么错 | 替代做法 |
|---|---|---|
| “如果有这个功能你会用吗？” | 假设性意愿，社会赞许偏差；不是行为证据 | 问最近一次实际怎么做的 [SRC-B0-NNG-01 §“2. Prepare a Guide”] |
| “能省多少时间 / 多少钱？” | 要求参与者做未经验证的推算；容易变成 wishlist | 先测当前基线，再做有界演练；不要求受访者预测 |
| “你最喜欢哪个方案？” | 方案偏好不等于任务价值；过早进入设计 | 问任务、决策、证据、失败；方案后置 |
| 只访操作者 | 漏掉审批标准、等待、否决理由 | 操作者与审批者分开访谈；必要时加复核者 |
| 只选成功案例 | 漏掉拒绝 / 搁置 / 返工的真实原因 | 负案例优先；按结果分层 |
| 直接假设 link-start | 产品草案不是流程事实；可能整个 MVP 起点错误 | 用 episode 检验 H1–H4；未观察到写“未观察到” |
| 把 PMO 能力名当流程 | PMO 是 C 级登记，不是已观察工作流 | 从 episode 归纳任务类型；PMO 只作标签 |
| 观察 = 真实 | 观察者效应、同意偏差、场景限制 | 记录观察方式；与产物 / 访谈三角验证 |
| 缺失 = 0 / 不存在 | 把未知伪装成已知；错误分母 | 标记 unknown；记录检索路径；不静默填平 |
| 单一评审者当金标 | 个人偏好 / 角色偏差；不是 human gold | 至少两名评审者、独立首轮、分歧记录 |
| 7 维加权总分 | 权重任意，制造假精确 | 定性矩阵 + Tier 规则 + 原始证据 |
| 小样本 ROI | 不能外推；把演练当生产 | 逐例报告；限定范围；禁止因果 / ROI |
| 看板点击 = 采用 | 测量污染；不是决策使用 | 定义“用于真实决策记录”才算 adoption |
| 研究活动 = 业务任务 | 自欺；分母污染 | 研究记录单列，不进入 adoption / 任务计数 |
| 方法指南 = 批准 | 指南不是组织 / 法律授权 | 方法 C；项目批准单独取得 |
| 用 live 数据做“小演练” | 越权；可能违法 / 违约 | 纸面 / 礼宾；仅用提供的脱敏材料 |

**质量检查（B0 自查）：**

- 每个 material claim 有来源 / 定位 / 等级；没有来源的写 `C: 本文建议`。
- 每个指标有分子、分母、来源、缺失规则。
- 每个 job 有证据指针；没有“感觉”。
- 每个案例有角色、结果、负案例覆盖。
- 每个退出建议有 owner、unknown、dissent。
- 没有实测值、固定阈值、ROI、因果、生产验收声明。
- 没有把 Agent 复核写成人类同意；`human_gold_claim_count = 0`。
