## 0. 结论摘要（供讨论，不是批准）

1. **计划必须条件式**：每个工作段的启动由决策关闭触发，不由日历日期触发。当前可给出的是区间、依赖和证据要求，不是交付承诺。
2. **MVP 建议只做窄闭环**：飞书入口 → 达人主页链接背调 → 人工判断/认领 → 授权材料登记；监测与合作计划放在后续增量。该建议来自领域笔记的场景 A，尚待业务访谈验证（D02–D04）。
3. **关键路径不在编码**：业务范围、数据/法务可行性、飞书应用权限和评测人审是主要关键路径。外部等待必须显式进入 elapsed 情景，不能用加班、跳过测试或“先开发再说”吸收。
4. **容量假设**：建议 5–7 名核心成员、岗位容量约 5.7–7.4 FTE，按共享/部分投入折算为 P4 峰值约 3–4 FTE、全周期平均约 2.0–2.5 FTE 的直接工作当量；业务 SME、法务、飞书管理员和人审另计。低于峰值 2.5–3.0 FTE 时，本文区间失效。
5. **MVP 条件式区间**：约 27–46 周 elapsed、55–117 直接人周；外部审批/权限等待另设 0–6 周/关键项的暴露带，未并入上限。该区间只用于容量与风险讨论，任何对外日期须经 D12 与发起人批准。
6. **三能力路线**：M1 场景 A → M2 全渠道动态监测 → M3 IP 合作计划制定 → M4 整合与持续改进；不是一次交付，也不承诺营收 ROI、全渠道实时覆盖或自动外联。
7. **发布门禁**：业务、技术、安全三方 go/no-go；回滚/恢复演练是发布证据的一部分；外部消息不能保证撤回，只能更正、标记失效并保留审计。
8. **进度度量**：以决策关闭、门禁证据、外部依赖老化、切片验收和测试证据衡量，不以代码行数、消息数、模型调用数或演示次数衡量。
9. **Main 对齐**：P0–P6 是本笔记的临时工作段名称，不是 Main 阶段名。后续交付“Main 阶段映射表 v0.1”，逐条引用原文定位单元，禁止先改名后找依据（DC-01）。
10. **成本口径**：人力、模型、数据、基础设施、合规、安全评估、人审、采购和运维分开计量；不写任何供应商价格或总预算数字，全部由 D10 的报价/预算流程取得并记录。

## 1. 规划口径：把三种数字分开

### 1.1 定义

| 口径 | 定义 | 用途 | 不能用来做什么 |
|---|---|---|---|
| elapsed（日历周） | 从工作段入口条件满足，到退出证据被接受之间的日历时间，包含正常评审、等待、返工和上下文切换 | 资源占用、依赖讨论、风险情景 | 不能当成交付日期承诺；不能与工时混写 |
| person-effort（人周） | 直接参与工作的人×周；本文指产品、设计、工程、QA、安全、运维的直接交付人周 | 人力成本、容量规划、排期弹性 | 不含外部等待；不含业务 SME/法务/管理员/人审工时（另计） |
| external waiting（外部等待周） | 飞书管理员、数据平台、法务、采购、安全评估等外部主体的排队、审批和补件时间 | 解释 elapsed 与 person-effort 的差异；设置依赖老化指标 | 不能静默排除；不能用团队加班抵消；不能伪装成“开发中” |

**一句话：** elapsed 是日历，person-effort 是人力，external waiting 是外部排队；三者必须分开报，不能合成一个“工期”。

### 1.2 区间怎么读

- **低区间成立条件**：D01 在 P0 关闭、D02–D04 在 P1 内关闭；首发只覆盖 1 个市场、1 个平台、1 类合作对象；复用现有基础设施和身份体系；外部审批在 P2 结束前启动并基本并行；无重大范围变更或安全返工。
- **高区间成立条件**：首发跨 2 个以上平台/对象类型；数据权限或法务审查延迟；飞书应用需要重新申请或权限不足；安全评估发现需要架构调整；关键角色不足或频繁切换；评测人审资源未就位。
- 区间不是统计置信区间，也不是供应商报价；它是“在列明假设下用于讨论的资源包络”。任一假设改变，需重估并记录原因。
- 工作段之间可并行，但受同一团队容量约束；**不能把各段人周简单相加后声称总工期**，也不能把并行段的 elapsed 重复计算。

### 1.3 外部等待如何进入区间（不静默排除）

| 外部项 | 典型等待来源 | 规划暴露带（仅情景假设，不是预测） | 若延迟的后果 |
|---|---|---|---|
| 飞书应用权限/长连接/卡片回调/可用范围 | 管理员排期、应用审核、权限申请、安全复核 | 0–6 周/项；多项可能串行 | P3/P4 无法真实接入，MVP 不能验收 |
| 平台数据 API/授权/条款 | 平台审核、合同、字段权限、删除机制确认 | 0–6 周/项；历史数据可能更久 | 字段覆盖缩水，背调价值下降或不可用 |
| 法务/隐私/授权模板 | 法务排期、模板澄清、撤回/到期规则 | 0–6 周/项；首次审查通常更长 | 不能处理真实资料，授权登记不能上线 |
| 采购/供应商合同 | 询价、比价、合同、数据驻留条款 | 0–6 周/项；采购流程可能更长 | 付费 PoC 或正式使用延迟 |
| 安全评估/渗透测试 | 评估范围、排队、修复复测 | 0–6 周/项；发现高危时更久 | 不能生产发布 |
| 人审评测资源 | 业务专家排期、标注、争议处理 | 0–6 周/项；样本越大越久 | 无法证明质量，不能发布 |

**规则：**

1. 上述 0–6 周是**显式的不确定性占位**，不是对任何审批时长的承诺或预测；D05/D06/D08/D10 取得实际流程记录后必须替换。
2. 工作段表中的 elapsed 已包含“段内正常评审和等待”，但**不包含**外部审批整体排到关键路径之后的额外排队。若外部项未提前启动，默认使用高情景并顺延，不能引用低区间。
3. 外部等待不消耗人周，但会占用日历、造成上下文切换和返工；因此 **elapsed 可能增加而 person-effort 不减少**，甚至因返工增加。
4. 若两个以上关键外部项串行且都达到暴露带上限，MVP elapsed 会超过本文上限；本文不给出一个虚假的“含全部等待”的单一数字，D05/D06/D08/D10 关闭后更新。
5. 任何工作段不得通过跳过法务、数据授权、安全测试或人审来压缩 elapsed。合法压缩手段只有：缩小范围、提前启动外部流程、复用已批准资产、增加有决策权的并行评审者。

### 1.4 未定事项的处理规则

- 本文不写空白日期或空占位符。所有未定事项写成**决策工作**：`决策 ID + 问题 + 所需证据 + DRI + 批准者 + 关闭标志 + 阻塞工作段`。
- 未关闭的决策不得用“默认同意”推进；默认建议只用于讨论，不构成批准。
- 关闭记录写入决策登记表；关键不可逆架构选择再转 ADR。决策必须记录批准范围、批准主体、时间和失效条件。

### 2.2 工作段容量与责任（条件式区间）

| 工作段 | DRI（岗位建议） | 批准者（岗位建议） | elapsed 区间（周） | 直接人周区间 | 外部等待敏感性 |
|---|---|---|---|---|---|
| P0 | 项目负责人（PMO/PO） | 项目发起人 | 2–4 | 2–4 | 低；但 D01 未关闭则全部阻塞 |
| P1 | 产品/BA | 品牌业务 owner | 4–7 | 4–8 | 中；访谈排期、业务专家可用性 |
| P2 | 数据负责人 | 数据 owner + 法务 | 3–7 | 3–7 | 高；平台授权、法务审查 |
| P3 | 技术负责人 | 技术负责人 + 安全 | 4–6 | 6–12 | 高；飞书管理员、沙箱、安全评审 |
| P4 | 技术负责人（交付）/产品（范围） | 产品 owner + 技术负责人 | 8–14 | 24–56 | 中；环境、依赖、接口就绪 |
| P5 | QA/评测负责人 | 业务 owner + 安全 | 4–6 | 10–18 | 中；试点审批、人审资源 |
| P6 | 运维/业务运营 | 业务 owner + 技术负责人 | 3–6（首轮） | 6–12（首轮） | 低–中；真实试点任务供给 |

**责任规则：**

- DRI 对计划、依赖、风险、证据和升级负责；批准者对授权范围内的签核、资源和残余风险负责。DRI 不自动拥有批准权，批准者不能只挂名。
- 同一决策的 DRI 与批准者原则上不得为同一人。若组织只有一人可承担，登记为治理风险，由上一级管理者代行批准或设置独立复核。
- 生产发布至少需要业务、技术、安全三方签署；预算与采购由财务/发起人批准；法务意见不能由产品经理代签。

### 2.3 MVP 区间合成（仅用于容量讨论）

| 工作段 | elapsed（周） | 直接人周 |
|---|---|---|
| P0 | 2–4 | 2–4 |
| P1 | 4–7 | 4–8 |
| P2 | 3–7 | 3–7 |
| P3 | 4–6 | 6–12 |
| P4 | 8–14 | 24–56 |
| P5 | 4–6 | 10–18 |
| P6（首轮） | 3–6 | 6–12 |
| **MVP 合计（非简单相加）** | **约 27–46** | **约 55–117** |

- 合成假设：P1/P2 部分并行；P3 与 P2 尾部并行；P4–P6 顺序；不含外部等待单独暴露带；不含业务 SME、法务、飞书管理员、人审和采购工时。
- 若外部等待按高情景发生，elapsed 取上限并可能超出；人周不因等待自动减少，返工可能增加。
- 若只做一个平台、一个市场、一类对象，且复用现有基础设施和身份体系，取低区间；否则取高区间或重新拆分。
- **这不是“3 个月上线”或“6 个月交付”的承诺。** 任何对外日期必须经过 D12 与发起人批准，并绑定范围、资源、外部条件和验收证据；没有这些绑定的日期一律不成立。

|---|---|---|---|---|
| **S1 入口与任务受理** | 飞书群 @ 与 P2P 事件 → 平台身份映射 → 工作区/品牌 RBAC → 持久化任务 → 回执 | 普通成员/授权成员分别提问；重复投递同一消息；未 @ 的群消息；机器人自身消息 | 任务只创建一次；越权有服务端拒绝；回执与任务状态可追踪 | 不能证明背调质量或业务效用 |
| **S2 证据与背调卡片** | 批准平台链接 → 规范化资源 ID → 受控 connector → 证据快照 → 背调卡片（事实/未知/风险线索/下一步） | 支持的主页；缺粉丝画像的页面；不支持/危险链接；来源故障；过期证据 | 每条事实有来源和观察时间；未知字段明确；危险链接被安全拒绝 | 不能证明身份真实、无风险或合作价值 |
| **S3 认领与授权材料登记** | 人工认领 → 并发/重复点击 → 授权材料登记 → 工作台状态 → 审计 | 有权限/无权限成员分别点击；两人并发认领；材料缺失/过期/撤回 | 认领状态确定；登记不宣告合同生效；审计可追溯；工作台与飞书一致 | 不能证明法务通过、授权有效或可立即使用内容 |

切片原则：每条切片都贯穿入口、权限、证据、状态和审计，不是“先做后端再做前端”的横向分层；演示使用批准的 fixture 或已授权测试数据，不用真实敏感资料。

## 3. DRI、批准者与治理

### 3.1 角色定义

| 角色 | 职责 | 不做什么 |
|---|---|---|
| DRI（直接负责人） | 制定工作计划、协调依赖、维护风险、整理门禁证据、按需升级；对结果直接负责 | 不自动拥有预算、法务、安全或发布批准权 |
| 批准者（Accountable） | 在授权范围内签核范围、预算、风险、发布或验收；为决定提供资源 | 不能只挂名；不能绕过证据；不能让 DRI 代签 |
| 咨询（Consulted） | 安全、法务、财务、飞书管理员、数据 owner 等按节点提供书面意见 | “已读”不等于书面意见；不能事后补签 |
| 知会（Informed） | 接收阶段结果、风险、变更和发布通知 | 不参与日常决策，但不能被排除在重大风险知会之外 |

### 3.4 决策与升级规则

- 每个工作段入口/出口各做一次决策评审；未关闭的阻塞决策进入“老化清单”，按周向发起人升级。
- 决策关闭标志：登记 `decision_id`、业务问题、证据链接、批准范围、批准主体、批准时间、失效条件、影响的需求/测试/发布版本。
- 争议处理：业务范围由业务 owner 裁决；数据/法务边界由法务与数据 owner 裁决；安全阻断由安全负责人裁决；预算由发起人/财务裁决；技术实现由技术负责人裁决。跨域争议升级到发起人。
- 变更控制：范围、数据源、模型、权限、发布范围的变化必须重新评估依赖、测试和成本；不能以“顺手做”绕过门禁。

## 4. 依赖与关键路径

### 4.1 关键路径（提案）

```text
D01 项目身份
  → D02/D03 业务范围与对象类型
    → D04 MVP 闭环
      → D05 数据可行性 + D08 授权语义
        → D09 架构/PoC
          → P4 垂直切片
            → D11 评测/发布
              → P6 验收与运营
```

可并行项：

- D06 飞书配置与 D07 交互边界可与 D02–D04 并行，但 P3 PoC 需要 D06 的沙箱条件。
- D05 数据可行性可与 P1 访谈并行，但 P4 前必须关闭。
- D09 架构 PoC 可与 D05 并行，但 D04 范围未定前不得冻结架构。
- D10 预算可与 P2/P3 并行，但付费 PoC/采购前必须关闭。
- D11 评测计划应在 P4 前启动，不能等到发布前才找人审。

**关键路径的性质：** 业务决策、外部授权、法务意见和安全评估是串行或半串行的；增加工程师不能缩短这些节点。P4 内部可以并行，但集成、安全和恢复测试是门禁，不能绕过。

### 4.3 压缩规则

**可以压缩：**

- 缩小首发平台、市场或对象类型；把非关键能力移出 MVP。
- 提前启动外部流程，把等待与其他工作并行。
- 复用已批准的基础设施、身份体系和安全控制。
- 增加有决策权的并行评审者，减少串行审批。

**不可以压缩：**

- 跳过法务、数据授权、安全测试或人审。
- 用演示数据代替真实验收，或用“基本可用”包装未开权限。
- 把安全测试、恢复演练放到发布后。
- 用加班吸收外部等待，或把 24/7 工作当作计划假设。
- 在 D09 未关闭前大规模编码，在 D10 未批准前产生付费承诺。
- 把“试点可用”写成“生产就绪”。

## 5. MVP 与三能力路线

### 5.1 能力映射（提案，不是 PMO 官方优先级）

据 `2026-11-08-radar-domain-scenarios.md` 第 2 节对 PMO 首页的转述，Radar 的三项能力为“IP 合作计划制定”“全渠道动态监测”“合作机会识别”。该转述尚待 PMO 专题研究核对；以下增量排序是本方案建议，不是 PMO 官方路线。

| PMO 能力（转述） | 本方案增量 | 依赖 | 明确不包含 |
|---|---|---|---|
| 合作机会识别 | M1 的背调/认领/授权登记提供“可复核机会输入”；M2 的监测线索提供持续机会来源 | 证据、对象、人工复核、授权状态 | 自动判定造假、不可验证的“真实性分数”、自动外联 |
| 全渠道动态监测 | M2 | 批准监测名单、数据刷新权限、降噪规则、成本控制 | 无授权全渠道覆盖、实时保证、替代 Source/Signal/Echo/Vicky |
| IP 合作计划制定 | M3 | M1 证据/对象 + M2 线索 + 内部活动/转化数据 | 自动签约、付款、预算承诺、伪精确 ROI |

### 5.2 M1：MVP（场景 A）

**建议范围：**

- 飞书群 @ 与 P2P 入口；受控测试群；一个平台链接；一个市场/一类合作对象（待 D02/D03）。
- 任务受理与状态：`completed_with_evidence`、`needs_user_input`、`needs_human_review`、`source_unavailable`、`permission_denied`、`failed`、`cancelled`。
- 证据快照与背调卡片：事实、来源、观察时间、未知字段、可复核风险线索、下一步。
- 人工认领：有资源权限的主体才可认领；并发/重复点击结果确定。
- 授权材料登记：主体、地域、渠道、用途、期限、文件引用、审核/撤回状态；登记不等于法务通过或合同生效。
- 工作台最小视图：任务、对象、证据、责任人、授权状态；读操作不触发采集或指标自增。
- 审计、幂等、持久化任务、恢复入口；私聊/群聊/品牌作用域隔离。

**明确非目标：**

- 全渠道监测、自动比较排名、合作计划生成。
- 自动外联、谈判、付款、签约、对外发布。
- 营收 ROI 归因、粉丝画像推断、敏感健康/孕产/儿童信息推断。
- 通用多 Agent 平台、内容工厂、全网 VOC、完整营销归因。

### 5.3 M2/M3/M4 增量（条件式，不与 M1 简单相加）

| 增量 | 目标 | 前置条件 | 增量 elapsed（周） | 增量人周 | 主要风险 |
|---|---|---|---|---|---|
| **M2 全渠道动态监测** | 监测名单 → 有限渠道快照 → 变化检测 → 去重/降噪 → 机会复核 | D05 刷新/覆盖确认；监测名单治理；成本上限；来源故障展示 | 10–18 | 25–45 | 数据覆盖被误读为全渠道；刷新成本失控；变化被误判为风险 |
| **M3 IP 合作计划制定** | brief → 候选比较 → 可解释评分 → 计划草案 → 法务/品牌/预算复核 → 结果登记 | M1/M2 证据与对象；内部活动/转化数据；评分规则批准；法务复核 | 8–16 | 20–35 | 缺少结果数据时伪精确 ROI；评分规则不可解释；计划被误当合同 |
| **M4 整合与持续改进** | 三能力共享对象/权限/证据/审计；反馈回流；运营指标；持续评测 | M1–M3 验收；运营责任；成本模型；季度重估 | 持续 | 持续投入（0.5–1.5 FTE） | 范围蔓延；指标漂移；运营责任不清 |

- 增量区间受同一团队容量约束；M2/M3 可部分并行，但不能假设团队翻倍。
- “完整三能力”指三项能力在同一对象/权限/证据/审计契约下通过验收，不是功能数量堆满，也不等于营收成功。
- M4 的“持续”没有结束日期；以季度重估和发布周期管理，不设虚假的“完成日”。

### 5.4 路线图不承诺什么

- 不承诺全渠道实时覆盖、无授权数据可得、或“所有平台都能查”。
- 不承诺营收 ROI、合作转化率、节省工时或品牌提升；这些需要内部转化数据和独立评估。
- 不承诺自动签约、自动付款、自动外联或替代法务/PR/采购判断。
- 不承诺在未批准数据、未授权环境或未通过安全门禁的情况下运行。

## 6. 测试分层、发布、恢复与回滚

### 6.1 测试分层

| 层级 | 范围 | 必需证据 | 入口 | DRI | 退出条件 |
|---|---|---|---|---|---|
| L1 单元/契约 | schema、状态机、幂等键、权限规则、错误码 | 自动化测试、contract fixtures、状态转换表 | P4 开始 | 技术负责人 | 必需用例通过；状态机无未定义转移 |
| L2 组件/集成 | 飞书沙箱、connector mock/批准沙箱、数据库、outbox | 集成日志、重试/超时记录、消息轨迹 | P3/P4 | 技术负责人 | 无关键集成缺口；失败可解释 |
| L3 安全/权限 | SEC-T01–T10（见安全笔记）、提示注入、SSRF、跨作用域、卡片篡改、并发批准 | 真实工具调用轨迹、策略决定、状态差异、出站目的地 | P3/P5 | 安全 | 无未解决高危；误拒绝与合法完成率一起报告 |
| L4 端到端业务 | 飞书群/P2P + 工作台一致性；任务全状态；私聊/群聊隔离 | 任务脚本、状态记录、跨入口对比 | P4/P5 | QA | 所有任务退出状态覆盖；权限不同可见字段正确 |
| L5 数据质量/字段 | 字段可得性、未知处理、时间戳、来源故障、删除/过期 | 字段矩阵 vs 实际观测；来源故障记录 | P2/P5 | 数据负责人 | 未知不被写成已知；过期不被写成实时 |
| L6 人审评测 | 开发集、冻结测试集、抽样框、标注指南、争议处理 | 人审标签、裁决记录、指标分母、样本清单 | P4/P5 | QA/业务 owner | D11 接受线满足或残余风险被明确接受 |
| L7 恢复/回滚 | 重启、重复投递、提供方停机、数据库恢复、outbox 对账、卡片版本 | 演练报告、恢复时间、数据一致性检查 | P5 | 运维 | 在批准的 RPO/RTO 内恢复；外部影响有对账 |
| L8 受限 live 试点 | 批准测试群、批准任务、真实但受控的使用 | 试点验收备忘录、事件记录、业务反馈 | P5/P6 | 业务运营/QA | 业务 owner 接受范围与残余风险 |

**规则：**

- 测试数据分层按评测笔记：手写 fixture、机器整理样本、人审开发集、人审冻结测试集、授权 live 验收集；不能用机器草案冒充人工金标。
- “最终回复拒绝”不是安全通过；必须观察工具调用、授权决定和业务状态变化。
- 模型、提示词、connector、权限策略或评分规则变化，必须重跑受影响的质量/安全/业务测试，不能沿用上次 passed 标志。
- 本地 fixture 通过只证明本地 fixture 范围；预发可访问不等于真实写入获授权。

### 6.2 发布门禁

| 门禁 | 必须回答的问题 | 必需证据 | DRI | 批准者 | 不通过条件 |
|---|---|---|---|---|---|
| G0 范围/决策 | 范围、非目标、数据、架构、预算是否已关闭？ | 决策登记、需求基线、架构记录、预算包络 | 项目负责人 | 发起人 + 业务 owner | 有阻塞决策未关闭；范围靠口头理解 |

- 发布门禁不允许单人批准；任一门禁不通过即不得进入下一阶段。
- 允许“明确降级”的项必须记录降级范围、影响、补偿控制和到期复核条件；不得用“基本可用”替代。
- 所有发布证据绑定同一 `release_id`、commit/build 指纹、schema、connector、模型、提示词、工具、评分、权限和卡片版本（Git/构建存在后执行）。

### 6.3 恢复与回滚

| 场景 | 回滚/恢复动作 | 必需证据 | 限制 |
|---|---|---|---|
| 代码/配置缺陷 | 回退到上一 `release_id`；关闭 feature flag；重建环境 | 部署日志、版本清单、配置差异 | 已发送的外部消息不能撤回 |
| Schema/数据迁移 | 前向修复或从备份恢复；执行逆向迁移脚本（如已批准） | 恢复演练报告、数据一致性检查、RPO/RTO | 备份后产生的数据可能丢失；需业务确认 |
| Connector/来源故障 | 停用 connector；使用最后可信快照；显示数据时间 | 来源状态、快照版本、故障记录 | 旧数据不能伪装实时；覆盖范围可能缩小 |
| 模型/提示词回归 | 固定回上一模型/提示词版本；降级为“仅证据、不分析” | 版本 manifest、回归测试、质量对比 | 降级期间功能受限，需业务知会 |
| 飞书卡片/回调变更 | 发布向后兼容卡片；旧卡片保留；发送更正说明 | 卡片版本映射、回调日志、用户通知 | 不能编辑已送达消息；不能保证撤回 |
| 权限/凭证事件 | 撤销 token/角色；暂停任务；轮换凭证；审计 | 审计记录、权限变更记录、影响清单 | 进行中的动作需对账；不能宣称零影响 |
| 定时任务/监测 | 暂停任务；按幂等键重放；人工核对重复 | 任务日志、幂等键、对账结果 | 跨飞书与数据库不宣称 exactly-once |

**明确说明：** 外部消息（飞书群/私聊）不能保证撤回或编辑；只能发送更正、标记失效并保留审计。回滚代码不等于回滚已发生的业务影响；不得对外宣称“已完全回滚”。

### 6.4 验收与持续改进

- **验收单位**：完成一项可复核的业务任务，包含证据、人工决定、责任人和授权状态；不是功能清单、消息数量或模型流畅度。
- **验收记录**：范围、样本、指标分母、已知限制、残余风险接受者、版本；业务 owner 签署后才能扩展试点。
- **试点扩展**：按“测试群 → 一个业务团队 → 一个市场”逐级扩展，不跳级；每次扩展重新评估数据、权限、成本和支持能力。
- **持续改进**：每个发布周期复盘事件、质量、成本和采用；每月审查决策老化与外部依赖；每季度重估范围、数据、模型和成本。
- **变更控制**：新增能力、数据源、平台或自动化动作必须走决策登记和门禁；不能以“试点需要”绕过。
- **不把试点采用当 ROI**：消息量、活跃用户、演示次数、模型调用量都不是营收贡献；没有内部转化数据就不宣称 ROI。

### 7.2 容量失效条件

- P4 峰值直接工作当量低于 2.5–3.0 FTE；或 Tech Lead、数据/connector、飞书集成、QA 中任一关键角色缺口超过 50%。

- 团队频繁切换优先级、多人共享超过 50%、或无备份关键人。
- 使用外包/供应商但未计入交接、安全审查和合规成本；不能把外部人周当作内部容量。

### 7.3 人周与 elapsed 的关系

- 增加人手可以缩短部分可并行工作，但受决策、评审、外部等待和协调成本限制；**不能按线性比例压缩**。
- P4 之后加入未熟悉领域的人，可能增加返工；优先补数据、QA、安全，而不是无差别加后端。
- 任何“压缩排期”的请求必须说明范围变化、质量风险、外部等待处理方式和残余风险接受者，并由 D12 批准者记录。
- 关键角色备份：Tech Lead、数据/connector、飞书集成、QA 至少各有 1 名备份或文档化交接；否则登记为高风险（R08）。

### 11.3 建议讨论次序

1. D01 项目身份与 D12 团队容量。
2. D02/D03 首发品牌、市场、品类、对象类型。
3. D04 MVP 闭环与场景 A 验证。
4. D05 数据/字段可行性与 D08 授权语义。
5. D06/D07 飞书接入、权限与会话边界。
6. D09 架构/PoC 与 D10 预算包络。
7. D11 评测/接受线，再回到 D12 确认发布与运营责任。
8. DC-01–DC-12 按阻塞工作段逐步关闭。

技术风险 PoC 可以提前，但不得绕过业务范围、数据授权、法务意见和真实动作批准。
