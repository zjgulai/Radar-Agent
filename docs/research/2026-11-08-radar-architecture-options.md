## 0. 结论摘要

拟议的默认架构是 **“模块化单体 + 三个运行角色 + 一个事务型事实库”**：

1. **Feishu Gateway** 是常驻、轻量的长连接入口，只负责接收、校验、持久化收件箱、快速确认和入队；不执行模型、采集或长任务。
2. **API/BFF** 服务工作台与飞书卡片深链，负责会话、RBAC、资源级保密、领域命令与查询；初期与领域服务同一部署单元，逻辑模块边界清晰。
3. **Worker** 从持久化队列领取任务，执行连接器、证据快照、模型分析与出站消息投递；可独立重启和水平扩展。
4. **PostgreSQL** 是唯一业务事实源；对象存储保存原始证据字节；飞书和工作台都是投影/通道，不是事实源。MVP 不引入 Kafka、独立向量库、图数据库或多 Agent 自治循环。
5. **所有跨边界动作**（入站事件、任务、外部调用、消息发送、批准）都有持久化状态、幂等键、预算和审计；“模型不是权限边界”，批准必须绑定具体动作、目标版本和参数。
6. **MVP 是一条纵向业务切片**：主页/账号链接 → 可追溯背调 → 人工判断 → 候选认领 → 授权材料登记。全渠道动态监测与 IP 合作计划制定分别作为后续两个 PMO 能力迭代；机会识别在 MVP 中只做最小候选识别，后续由监测信号增强。该映射是建议，PMO 原文与 Main 门禁需后续逐项对照。

## 1. 架构原则

| 原则 | 具体含义 | 依据/说明 |
|---|---|---|
| 先做纵向切片，不做平台大而全 | 每个阶段以一个可复核业务任务为验收单位，不为“未来所有能力”预建抽象 | 评测笔记第 1 节建议以业务任务为验收单位 |
| 模块化单体优先 | 一个代码库、一个事务库、清晰模块边界；只有出现可测量的独立扩展/隔离需求才拆服务 | C；决策登记 D09 建议“模块化单体 + 常驻事件网关/后台任务” |
| 通道与事实分离 | 飞书是入口/出口，工作台是持续操作界面；业务事实只写事实库 | 领域笔记第 3 节“两个入口，一个业务系统” |
| 入站先持久化再处理 | 事件先落收件箱并快速确认，长任务异步执行；重启不丢已接受请求 | 安全笔记 §2.5 建议 |
| 模型不是权限边界 | 权限、批准、参数校验、预算与副作用控制都在执行组件中完成 | 安全笔记 §2.1（B：OWASP） |
| 外部内容不可信 | 达人主页、视频描述、评论、外部报告只作为证据/数据，不成为指令或工具授权 | 安全笔记 §2.2（B） |
| 未知是一等状态 | 未观测、未授权、无数据、过期、估计必须显式区分，不用 0 或空值伪装 | 领域/评测笔记；C |
| 版本先于承诺 | 证据、时间、模型、提示词、连接器、政策、schema、卡片动作均有版本并可追溯 | 安全笔记 §2.4/§2.5；评测笔记第 5 节 |
| 读不产生采集 | 只读页面、搜索、导出不得触发新的外部采集或分析任务 | 评测笔记第 4 节“工作台查看页面不会触发新的采集” |
| 默认拒绝、默认禁用 | 未批准的数据源、未授权的资源、未启用的高影响动作一律拒绝 | 安全笔记；决策登记 D05/D08 |

## 2. 系统上下文与运行拓扑

### 2.1 逻辑拓扑

```text
                        飞书开放平台
                 （群 @、P2P、卡片回调）
                              │ 长连接
                              ▼
                    ┌──────────────────┐
                    │  Feishu Gateway  │  常驻、轻量、单活跃连接
                    │  校验/去重/入队  │
                    └────────┬─────────┘
                             │ 写 inbox / 读 outbox
                             ▼
┌──────────────┐      ┌──────────────────────────────┐
│  Web 工作台  │─────▶│  API / BFF                   │
│  React SPA   │ HTTPS│  会话、RBAC、领域命令/查询    │
└──────────────┘      └──────────────┬───────────────┘
                                     │
                                     ▼
                    ┌──────────────────────────────────┐
                    │  PostgreSQL（唯一业务事实库）     │
                    │  inbox / jobs / outbox / 业务表  │
                    │  证据元数据 / 批准 / 审计 / 版本 │
                    └──────────────┬───────────────────┘
                                   │ 持久化队列
                                   ▼
                    ┌──────────────────────────────────┐
                    │  Worker 池                        │
                    │  连接器 / 模型网关 / 证据快照      │
                    │  outbox dispatcher / 对账          │
                    └───────┬───────────────┬──────────┘
                            │               │
                            ▼               ▼
                   批准的数据源/模型    对象存储（原始证据）
```

### 2.2 运行单元与责任

| 运行单元 | 负责 | 明确不负责 |
|---|---|---|
| **Feishu Gateway** | 维持长连接与重连；校验应用/租户/事件封装；事件去重；写 inbox；快速 ACK；卡片回调入队；健康检查与租约 | 不调用模型/连接器；不执行长任务；不直接写业务对象；不在回调里等待分析 |
| **API / BFF** | 工作台会话与 CSRF；服务端 RBAC/资源 ACL；领域命令与查询；响应聚合；OpenAPI 契约；把任务入队；卡片深链落地 | 不持有长连接；不在 GET 请求中触发采集；不信任前端角色/金额/授权真值 |
| **Worker** | 领取 job；执行连接器、快照、模型分析、产物写入；预算/取消/重试；outbox 投递与对账 | 不持有飞书长连接；不以“服务账号”绕过用户/资源权限；不假设外部动作可回滚 |
| **Scheduler（可并入 Worker，M1 再引入）** | 监测规则定时触发、对账、过期清理；单主租约 | 不承载业务决策；不直接对外发送 |
| **PostgreSQL** | 事务事实、队列、inbox/outbox、审计、版本、批准 | 不保存明文密钥；不保存无访问控制的原始敏感内容 |
| **对象存储** | 原始证据字节、授权材料文件、导出物；内容哈希、私有桶、短时签名 URL | 不作为可查询业务事实源；不公开可枚举 |
| **Model Gateway（模块）** | 供应商适配、结构化输出校验、预算计量、版本记录 | 不做权限决定；不直接执行副作用；不把模型输出当事实 |
| **连接器适配器** | 批准来源的认证、限流、分页、规范化、错误分类、删除/撤回钩子 | 不做通用网页抓取；不把用户 URL 直接透传；不跨授权依据回退 |

### 2.3 为什么网关与长任务分离

| 风险 | 分离后的处理 |
|---|---|
| 长连接需要持续在线，分析任务可能运行数分钟 | 网关只做短事务；Worker 崩溃/重启不影响连接 |
| Worker 扩缩容可能造成重复消费 | 同一飞书应用建议仅一个活跃长连接（租约/主备，**具体多连接语义待飞书官方文档与 PoC 确认**）；事件投递仍以 inbox 去重兜底 |
| 回调超时导致平台重试 | 网关先落库再快速确认；业务处理异步，重复事件由 `(app_id, event_id)` 唯一约束吸收 |
| 部署/发布互相牵连 | Gateway、API、Worker 使用同一代码库但不同入口/进程，可独立发布；初期仍是一个镜像的三种运行角色 |

> 工程假设（待验证）：飞书长连接的事件格式、ACK 语义、重连行为、卡片回调超时与消息状态查询能力，均以官方 SDK/文档和 D06 的 PoC 为准。本文不冻结具体 SDK API，也不宣称跨系统 exactly-once。

## 3. 唯一事实源与数据分层

### 3.1 事实源定义

| 数据类别 | 事实源 | 说明 |
|---|---|---|
| 业务对象、任务、关系、状态 | PostgreSQL | 唯一可写业务事实；所有入口最终落到同一组领域表 |
| 原始证据字节 | 对象存储 | 以内容哈希寻址；元数据在 PostgreSQL；访问受资源 ACL 控制 |
| 审计与状态迁移 | PostgreSQL 追加表 | 只追加，不更新历史；脱敏，不含凭证/源文本 |
| 飞书消息/卡片 | 飞书平台 + 本地 inbox/outbox | 通道与投递记录，不是业务事实源 |
| 工作台读模型 | 由事实库查询/投影生成 | 可重建；不得反向成为事实源 |
| 模型上下文/记忆 | 任务级、可丢弃 | 不作为长期事实；跨任务复用须经证据/权限过滤 |
| 搜索索引 | 派生 | MVP 用 PostgreSQL 全文/模糊检索；不引入独立向量库 |

### 3.2 数据族与不变量

| 数据族 | 主要内容 | 关键不变量 |
|---|---|---|
| 身份与访问 | principal、成员关系、角色、资源授权、会话 | 外部身份不直接等于内部角色；每次读写都带 workspace 与资源范围 |
| 任务与作业 | task、task_event、job、job_attempt | 状态迁移只能由领域服务执行；并发用版本号比较交换；尝试有上限与死信 |
| 入站/出站 | inbox_event、outbox_message、idempotency_key | 入站按来源事件唯一；出站与业务写入同事务；发送超时进入“未知”而非盲目重发 |
| 合作对象 | creator/subject、platform_account、identity_link、account_observation | 对象与账号分离；身份关联有状态/证据/审核；不因名称相似自动合并 |
| 证据 | evidence_snapshot、artifact、claim、citation | 快照只追加；修正产生新版本并 `supersedes` 旧版；事实主张必须能定位到证据与时间 |
| 业务决定 | candidate、claim_record、authorization_material、review | 任务完成 ≠ 业务决定；认领 ≠ 对外代表权；材料登记 ≠ 法务通过 |
| 批准与审计 | approval、audit_event | 批准绑定具体动作/目标版本/参数哈希/政策版本；一次性原子消耗 |
| 版本与配置 | version_set、release_manifest、connector_config、policy_version | 每个任务/产物/批准记录版本集；发布绑定同一 `release_id` |
| 后续能力 | monitoring_rule/change_event（M1）、brief/plan（M2） | 不提前建表；复用证据、任务、身份、权限与版本模型 |

### 3.3 规范化边界

- 所有业务表带 `workspace_id`（必要时 `brand_id`）；缺失作用域的查询直接拒绝，不提供“全局视图”后门。
- 模块拥有自己的表；跨模块只通过应用服务/领域接口读写，不做跨模块 SQL 拼接。
- 证据快照写入后不可编辑；纠错通过新快照 + 差异说明 + 审计完成。
- 个人数据/受限材料的保留、删除、撤回在数据设计节点批准（D05/D08）；删除需保留最小审计与合规证明，不保留可复原的敏感正文。
- 金额、预测回报、粉丝画像等字段各自携带来源、时间与证据等级；不因同屏显示而共享可信度。

## 4. 入站、出站、幂等与恢复

### 4.1 入站事件流

| 步骤 | 动作 | 失败/重复处理 |
|---|---|---|
| 1 | Gateway 接收长连接事件，校验应用/租户/事件封装 | 校验失败记录脱敏审计，不进入业务 |
| 2 | 写 `inbox_event`，唯一键 `(app_id, event_id)` | 重复事件只增加重复计数，返回已接受，不重复建任务 |
| 3 | 快速 ACK；回调中不执行模型/采集/长任务 | ACK 超时按平台机制重试，仍由唯一键吸收 |
| 4 | Dispatcher 领取 inbox，解析命令：群内是否 @、是否 P2P、是否机器人自己、是否线程、是否支持的命令 | 非命令/自己消息/未 @ 的群消息标记 `ignored`，不进入分析 |
| 5 | 以业务幂等键创建/复用 task，写 task_event，标记 inbox 已处理（同一事务） | 同一 `message_id` 重复只关联同一任务 |
| 6 | 入队 job；通过 outbox 发送“已接受/需补料”回执（可选） | outbox 与状态同事务；发送失败不改变业务接受事实 |
| 7 | Worker 执行；产物、证据、状态、outbox 在同一事务边界内落库 | 崩溃后按租约恢复；已完成的副作用步骤不重复执行 |

### 4.2 幂等键分工

| 键 | 作用域 | 解决的问题 | 存储/约束 |
|---|---|---|---|
| `(app_id, event_id)` | 飞书入站事件 | 平台重复投递/网关重连重复 | inbox 唯一约束 |
| `message_id` | 单条消息 | 同一消息触发多次命令 | task 关联唯一或命令去重表 |
| `action_id` / `nonce` | 卡片动作 | 双击、重放、并发批准 | action 记录唯一；一次性消耗 |
| `Idempotency-Key`（客户端） | 工作台变更请求 | 网络重试造成重复创建/认领 | 幂等表 + 请求指纹；同键不同体返回冲突 |
| `job_id` / `attempt` | 后台作业 | 重试同一作业 | 作业表 + 租约 + 尝试次数 |
| `outbox_id + channel` | 出站消息 | 同一业务通知重复入队 | outbox 唯一；发送状态独立 |

> 安全笔记 §2.5 明确指出：`event_id`、`message_id` 与业务动作幂等键解决不同重复问题，不能合并为一个笼统 ID。本文据此拆分；不宣称跨飞书与数据库 exactly-once。

### 4.3 发送“结果未知”

飞书 API 超时不等于消息未发出。拟议状态机：`pending → sending → sent | unknown | failed`；`unknown` 进入对账队列，按平台可用的消息查询/回执能力确认；在能力未确认前，不做无条件重发，不把“未收到回执”写成“发送失败”。对外只显示“已提交/待确认”，并保留人工处理入口。

### 4.4 恢复与重试

| 场景 | 行为 |
|---|---|
| Gateway 重启 | 重新建立长连接；inbox 中未处理事件继续消费；期间不宣称持续在线 |
| Worker 崩溃 | 租约过期后 job 可被其他 Worker 领取；`job_attempt` 记录；已完成步骤通过幂等键/检查点跳过 |
| 模型/连接器超时 | 有界重试 + 退避；仍失败则给 `source_unavailable` 或 `failed`，保留原因与重试时间 |
| 发送超时 | 标记 `unknown` 并对账；不重跑整个任务，不重复不可重复动作 |
| 用户取消 | 设置取消标记；步骤边界检查；已发生外部副作用如实记录，**不伪装回滚** |
| 预算耗尽 | 默认暂停为 `needs_human_review` 并说明预算；不自动追加预算 |
| 数据库不可用 | 网关无法持久化时不宣称已接受；健康检查/背压；恢复后由平台重试与 inbox 去重兜底 |

## 5. 身份、账号与合作对象的不确定性

### 5.1 身份层次

| 层次 | 标识 | 处理规则 |
|---|---|---|
| 飞书外部身份 | `app_id` + `tenant_key` + `open_id`（是否可用 `union_id` 跨应用待 D06 验证） | 不信任昵称、群名片、聊天成员列表作为角色依据 |
| 内部用户 | 稳定 `user_id` | 通过登录/管理员绑定建立；未绑定时进入“待绑定”，不自动创建影子账号 |
| 工作区成员 | `workspace_id` + `user_id` + 角色 | 每次请求由服务端解析；角色变更需审计；离职/禁用即时生效 |
| 服务身份 | gateway/worker/service principal | 只拥有任务所需最小范围；后台作业携带 `on_behalf_of` 与 `purpose`，不得越权 |
| 资源授权 | `resource_type + resource_id + grantee` | 与角色正交；受限材料、私聊上下文、合同/报价需要单独授权 |

### 5.2 业务实体模型

| 实体 | 含义 | 关键不确定性 |
|---|---|---|
| Creator / Subject | 可能合作的自然人、专家、创作者、名人或 IP 主体 | 同一主体可能有多个账号；代理人不等于权利主体 |
| PlatformAccount | 一个具体渠道的规范账号 | 改名、出售、停用、链接失效；账号历史需观察事件 |
| IdentityLink | 账号与主体之间的候选/确认关系 | 状态：`proposed / human_confirmed / rejected / expired`；带证据、审核人、时间；**不自动合并** |
| RightsHolder / AuthorizationSubject | 授权材料的权利主体 | 可能与联系人/代理人不同；必须单独登记与核验 |
| Contact | 联系人 | 不等于主体、不等于授权人；联系方式的可见性单独控制 |
| ChatScope | 群、线程、P2P 的会话作用域 | 不是知识共享边界；同一用户在不同作用域的内容不得自动互通 |

### 5.3 不确定性与合并规则

- 名称相似、头像相似、简介互相引用只产生**候选关联建议**，不产生合并。
- 账号更名/链接失效记录为 `account_observation`，保留旧标识别名；对象 ID 不变。
- 合并/拆分必须人工复核、记录理由与影响范围；历史证据保留原归属，不用“覆盖式更新”改写过去。
- 字段值状态至少区分：`observed`（来源直接观测）、`estimated`（估计）、`inferred`（推断）、`not_observed`（未观测）、`not_available`（来源不支持）、`unknown`（未知）、`expired`（过期）。
- 对粉丝画像、地理、年龄等字段，来源不支持时明确 `not_available/unknown`，不生成“母婴用户占比”等无证据结论（领域笔记 §5 压力测试）。

## 6. 证据、时间与版本

### 6.1 证据快照的概念字段

| 字段组 | 拟议字段（概念，不冻结 schema） |
|---|---|
| 身份 | `evidence_id`、`workspace_id`、`source_id`、`platform`、`resource_type`、`resource_id` |
| 定位 | `canonical_url`、`locator`（字段路径/页码/时间戳/片段）、`raw_artifact_hash` |
| 时间 | `observed_at`（来源侧）、`fetched_at`（采集侧）、`processed_at`、`valid_until`/新鲜度 |
| 权限 | `permission_basis`（公开/授权/内部）、`consent_or_contract_ref`、`region`、`retention_class` |
| 覆盖 | `coverage`（分页/时间窗/字段）、`missing_fields`、`partial_reason` |
| 版本 | `connector_version`、`extractor_version`、`schema_version`、`release_id` |
| 生命周期 | `supersedes_id`、`status`（active/stale/revoked）、`deleted_at`（仅合规删除） |

### 6.2 事实主张与引用

- 每个事实主张（claim）必须关联至少一个证据快照和可定位单元；只挂主页 URL 不等于引用准确（评测笔记第 3 节）。

- 引用进入飞书卡片、工作台、导出物前分别做安全渲染；不允许任意 HTML、隐式外链或泄漏签名 URL。
- 过期证据必须显示“截至时间”和过期提示；过期不等于“没有变化”。

### 6.3 版本集与发布清单

| 版本维度 | 记录位置 | 变更影响 |
|---|---|---|
| DB schema / 事件 schema / API schema | 迁移文件、契约包、release manifest | 契约测试、兼容性窗口、回滚方案 |
| Connector / extractor | 快照与 job 记录 | 已采数据的解释边界；重跑影响 |
| 模型 / 提示词 | 每次模型调用与产物 | 质量/安全回归；输出可复现性 |
| Policy（授权/批准/保密） | 审计、批准记录、请求上下文 | 批准失效/重新校验；拒绝原因可解释 |
| Scoring（M2） | 评分记录 | 排序解释与版本对比 |
| Card/action contract | 卡片模板与动作注册表 | 旧卡片动作拒绝或升级路径 |
| Release | `release_id` + commit/build 指纹（Git/构建存在后） | 证据包、测试、回滚与签核绑定 |

> 评测笔记第 5 节要求证据包关联同一 `release_id` 与构建指纹，并包含 schema、connector、模型、提示词、工具、评分、权限与卡片版本。本文将其作为架构不变量；具体清单在实施计划中细化。

## 7. 任务状态机与业务决定分离

### 7.1 任务状态

| 状态 | 含义 | 是否消耗预算/可恢复 |
|---|---|---|
| `received` | 事件已持久化，尚未解析为业务任务 | 否 |
| `accepted` | 已校验并创建任务，等待入队 | 否 |
| `queued` | 等待 Worker | 否 |
| `running` | 执行中 | 是 |
| `needs_user_input` | 缺少必要输入/授权/链接 | 否，等待用户 |
| `needs_human_review` | 等待有权限的人类复核（含预算扩展、风险线索、材料） | 否 |
| `completed_with_evidence` | 达到约定业务退出条件，带证据、覆盖与未知项 | 否 |
| `source_unavailable` | 关键来源不可用且批准的回退已用尽；可恢复 | 否 |
| `permission_denied` | 服务端策略拒绝；权限变更前不可重试 | 否 |
| `failed` | 不可恢复错误/预算耗尽/配置错误；带原因码 | 否 |
| `cancelled` | 用户或系统取消；已发生副作用单独记录 | 否 |
| `expired` | 超过等待/有效期 | 否 |

> 这些退出状态采纳评测笔记第 1 节的建议：`completed_with_evidence`、`needs_user_input`、`needs_human_review`、`source_unavailable`、`permission_denied`、`failed`、`cancelled`。`received/accepted/queued/running` 为内部过程状态。

### 7.2 迁移规则

- 只允许显式迁移表；非法迁移返回 `409 invalid_transition`，并返回当前状态与版本。
- 每次迁移追加 `task_event`：`from_state`、`to_state`、`reason_code`、`actor`、`policy_version`、`version_set`、`created_at`；不更新历史事件。
- 并发控制用 `version` 比较交换；同一任务同一时刻只有一个活跃执行租约。
- 外部动作（发送、登记、认领）各自有幂等键；状态迁移与副作用写入尽量在同一事务边界；跨系统动作记录“已执行/未知/失败”，不假装原子。
- 任务完成 ≠ 业务决定：候选是否认领、材料是否通过、合作是否成立是独立对象与独立状态。

### 7.3 业务决定对象（与任务分离）

| 对象 | 拟议状态 | 说明 |
|---|---|---|
| 候选/机会 | `new → under_review → claimed | rejected | archived` | 认领是内部责任分配，不是对外代表权 |
| 授权材料 | `draft/missing → submitted → under_review → verified | limited | rejected | expired | revoked` | 登记不代表法务通过或合同生效；状态含义待 D08 按真实模板确认 |
| 合作计划（M2） | `draft → in_review → approved_for_execution | rejected | superseded` | 批准绑定 brief/预算/评分版本；材料/范围变化可失效 |
| 监测线索（M1） | `new → triaged → opportunity | risk | irrelevant | closed` | 线索不是事实断定；负面新闻只能转交，不自行发布结论 |

| 创建背调/刷新任务 | — | ● | ● | — | — | ● | — | — |
| 查看受限报价/合同/私聊 | — | — | ○ | ○ | ○ | — | — | ○ |
| 认领候选 | — | — | ● | — | — | — | — | — |
| 登记授权材料 | — | ○ | ○ | — | ● | — | — | — |
| 业务复核/采纳 | — | — | — | ● | — | — | — | — |
| 法务/材料复核 | — | — | — | — | ● | — | — | — |
| 管理成员/角色 | — | — | — | — | — | ● | — | — |
| 查看审计 | — | — | — | — | — | ○ | ● | — |
| 执行高影响动作 | — | — | — | — | — | — | — | — |

说明：

- 角色是岗位模板，**资源授权**另行判定；有角色不代表能看所有对象。
- 管理员不能给自己授予未批准的资源权限；高影响动作需双人复核（D08/D11 待定）。
- 服务身份不继承人类角色；后台任务以 `on_behalf_of` + 任务范围运行，查询仍受资源 ACL 限制。
- 前端可以隐藏按钮，但**隐藏按钮不是安全控制**；服务端必须独立拒绝并写审计。

### 8.2 资源级保密

| 边界 | 规则 |
|---|---|
| 工作区/品牌 | 请求必须绑定；跨工作区默认拒绝；切换工作区需重新授权 |
| 群/线程/P2P | 群卡片只返回该群作用域允许的内容；P2P 报价/合同不得因同一用户提问而出现在群里 |
| 受限材料 | 合同、报价、未公开计划、联系人、授权文件单独 ACL；列表接口默认不返回正文 |
| 字段级 | API 返回最小字段；敏感字段按权限裁剪；下载用短时签名 URL 并记录访问 |
| 模型上下文 | 只检索调用者/任务有权访问的证据；模型输入/输出日志脱敏；不把秘密放入提示词 |
| 审计 | 记录主体、资源、动作、结果、原因、policy_version；不记录凭证、完整合同、原始私聊正文 |
| 缓存/搜索 | 派生索引继承源权限；不得通过搜索摘要绕过字段级限制 |

### 8.3 批准完整性

批准记录至少包含：

`approval_id`、`principal_id`、`action_type`、`target_type`、`target_id`、`target_version`、`params_hash`、`scope`、`policy_version`、`expires_at`、`nonce`、`status`、`consumed_at`、`consumed_by_job`、`reason`。

执行时不变量：

1. 批准只能由已认证、具备对应角色且未被禁用的主体创建。
2. 批准绑定**具体动作 + 目标 + 目标版本 + 参数哈希 + 作用域 + 政策版本**；任一变化即失效。
3. 批准一次性原子消耗（数据库条件更新/唯一约束）；并发双击只有一个成功。
4. 卡片 action 只携带不透明引用与版本，不携带可信角色、金额、授权真值；服务端重新鉴权。
5. 批准过期、撤回、政策变更、目标版本变化均需重新校验；是否自动失效按动作风险分级。
6. 高影响动作默认禁用；将来启用需精确动作类型、双人复核与独立开关，不因“用户说过可以自动化”而全局开放。
7. 批准不等于执行：执行仍需单独的授权检查；执行结果与批准记录关联审计。

> 依据：安全笔记 §2.1（B：OWASP 要求权限检查在执行组件、`user_confirmed` 布尔值不足、批准绑定当前主体/工具/目标/参数并原子消耗）与 §3 的 SEC-T02/T03 用例。

## 9. 工具面、预算、取消与恢复

### 9.1 最小工具注册表（MVP）

| 工具 | 类型 | 调用方 | 副作用 | 批准/权限 | 默认预算 |
|---|---|---|---|---|---|
| `link.resolve` | 读取外部 | Worker/API | 无业务写 | 只接受批准平台/资源类型 | 1 次解析，禁通用 fetch |
| `source.fetch_profile` | 读取外部 | Worker | 无业务写 | 来源授权 + 资源范围 | 有限请求/字节/超时 |
| `source.fetch_content` | 读取外部 | Worker | 无业务写 | 同上；分页上限 | 有限页数/字节 |
| `evidence.search` | 读取内部 | Worker/API | 无 | 继承调用者 ACL | 结果数/时间上限 |
| `dossier.generate` | 模型+证据 | Worker | 写内部产物 | 任务范围；输出校验 | 模型 token/成本/时长 |
| `candidate.create` | 内部写 | Worker/API | 创建候选 | 工作区写权限；幂等 | 单任务次数 |
| `candidate.claim` | 内部写 | API | 责任人变更 | 资源授权 + 版本检查 | 并发一次成功 |
| `authorization.register` | 内部写 | API | 创建待审材料 | 登记权限；幂等 | 单对象次数 |
| `message.enqueue` | 内部写 | Worker | 写 outbox | 作用域/模板校验 | 每任务条数 |
| `outreach.send`（未来） | 外部写 | 默认禁用 | 对外联系 | 精确批准 + 双人复核 | 严格上限 |
| `plan.submit`（M2） | 内部写 | API | 提交复核 | 计划权限 + 版本 | 单计划次数 |

工具契约要求：输入/输出 JSON Schema、超时、最大负载、重试类别、幂等要求、授权范围、审计字段、错误码。模型只能从**当前任务允许的工具集**中选择，执行器再次校验参数与权限；工具输出视为不可信数据。

### 9.2 禁止的工具面

- 通用 HTTP 抓取、无头浏览器、任意 URL 打开、SQL 执行、Shell、文件系统任意读写。
- 以 Cookie/账号密码模拟登录或绕过平台限制。
- 把飞书卡片回调值、外部网页文本、模型输出直接作为工具参数真值。
- 自动外联、自动付款、自动签约、自动发布；这些在 MVP 与后续迭代均默认禁用，需单独批准。

### 9.3 预算、取消、恢复

| 控制 | 建议 |
|---|---|
| 预算维度 | 每任务/每 job：外部请求数、字节数、墙钟时间、模型 token、模型/数据边际成本、重试次数 |
| 默认策略 | 硬上限 + 预警；超限进入 `needs_human_review`（可申请扩展），不静默继续 |
| 计量 | 每个 job 记录实际用量与估算成本；按业务任务聚合；采购固定成本单列 |
| 取消 | 用户/管理员可取消；步骤边界检查取消标记；外部调用设超时；已完成的副作用记录，不宣称回滚 |
| 恢复 | 租约/心跳/死信；检查点；幂等键；发送未知对账；恢复后从持久化状态继续 |
| 重试 | 区分可重试（超时/429/5xx）与不可重试（权限/参数/政策拒绝）；退避 + 抖动 + 上限 |
| 失败分类 | `permission_denied`、`source_unavailable`、`needs_user_input`、`needs_human_review`、`failed`、`cancelled`、`unknown` 分开统计，不混为“安全通过”或“无风险” |

> 依据：安全笔记 §2.5（B：限制链深、重试、token、费用；异常/超时/熔断/批准纳入测试）与 §3 的 SEC-T06/T07/T08/T09。

## 10. 数据连接器：授权、降级与回退

### 10.1 连接器契约

每个连接器必须声明：

| 维度 | 内容 |
|---|---|
| 来源身份 | `source_id`、平台、资源类型、官方/授权依据、适用地域 |
| 认证 | 认证方式、令牌范围、刷新/过期、撤销方式；密钥只存密钥管理 |
| 能力 | 可读字段、分页、时间窗、刷新频率、历史深度、是否支持删除同步 |
| 限制 | 速率限制、并发、最大响应、超时、配额与费用 |
| 规范化 | 输出的账号/内容/指标 schema 与 `connector_version` |
| 错误 | `auth_expired / rate_limited / not_found / unsupported / upstream_error / timeout / partial / policy_denied` |
| 生命周期 | 保留、删除、撤回、下架、审计要求 |

### 10.2 授权状态与回退阶梯

来源授权状态：`approved / limited / denied / unknown`。只有 `approved/limited` 且字段范围匹配才可调用；`unknown` 视为不可用。

建议回退顺序：

1. 同一批准连接器的有界重试/退避。
2. 使用**同一授权依据**下的缓存快照（必须标注 `stale`、`observed_at`，不得冒充实时）。
3. 使用另一个**已单独批准且权限依据匹配**的来源（不得因“都是公开网页”而互换依据）。
4. 返回部分结果 + 明确 `missing_fields/partial_reason`。
5. 关键证据仍缺失 → `source_unavailable` 或 `needs_user_input`，保留补料/重试入口。

禁止：静默降级为网页抓取、Cookie 登录、第三方未授权镜像、把“无数据”写成“无风险/无变化”。

### 10.3 SSRF 与链接安全

- 只接受批准的社媒平台资源类型；从 URL 提取规范化平台与资源 ID，拒绝非 HTTPS、userinfo、IP 字面量、非批准端口、`file/data` 等协议。
- 由连接器用固定 API/域名构造请求，不把用户原始 URL 透传为通用 fetch。
- 短链接逐跳解析并复验目标；防止 DNS rebinding：解析地址与实际连接绑定；重定向重新校验。
- 禁止环回、私网、链路本地、云元数据、内部业务服务；网络层出口白名单作为补充。
- 响应大小、超时、类型、重试次数有上限；验证失败返回“不支持/无法安全获取”，不转为隐蔽浏览器抓取。

> 依据：安全笔记 §2.3（B：OWASP SSRF 防护；仅校验域名不足，需连接时校验与网络层隔离）。

## 11. Schema 迁移与契约兼容

| 主题 | 建议 |
|---|---|
| 迁移形式 | 版本化 SQL 迁移，纳入仓库与 CI；按模块归属；禁止手改生产 schema |
| 变更策略 | `expand → migrate/backfill → contract`；先加列/表/索引，再切读写，最后删除旧结构 |
| 破坏性变更 | 需架构/数据评审与发布门禁；生产不做自动 destructive down migration |
| 回填 | 幂等 job；可暂停/恢复；分批限速；记录进度与校验和 |
| 兼容窗口 | API/事件契约版本化；消费者容忍新增字段；旧版本至少保留一个迭代窗口 |
| 验证 | 空库迁移、脱敏快照迁移、契约测试、回滚演练（前向修复/恢复备份） |
| 发布绑定 | 迁移版本进入 `release_manifest`；上线证据包含迁移结果与校验 |
| 数据修复 | 通过受审计的管理命令/一次性 job，不直接在生产 SQL 手工改业务数据 |

领域模型尚未冻结（D03/D04），因此本文只建议**可演进的骨架**：不使用重型事件溯源作为默认；保留追加式 `task_event/audit_event` 足以支持追溯。若未来审计/回放需求显著增加，再评估事件溯源，不在 MVP 预建。

## 12. API 契约与前端集成

### 12.1 API 风格

- REST/JSON + OpenAPI 作为契约源；TypeScript 客户端由契约生成；BFF 与后端初期同一部署单元，但逻辑上分离。
- 工作台会话：批准的 SSO/企业身份（具体方案 D06/D07 未定）；Cookie `Secure/HttpOnly/SameSite`，CSRF 防护；不在 URL 放令牌。
- 异步任务：创建返回 `202 + task`；进度用轮询（ETag/版本）或后续 SSE；MVP 不引入工作台 WebSocket。
- 变更请求使用 `Idempotency-Key`；资源更新使用 `If-Match`/版本号；冲突返回 `409` + 当前版本。
- 错误封装：`code`、`message`、`details?`、`trace_id`；稳定错误码如 `permission_denied`、`version_conflict`、`invalid_transition`、`source_unavailable`、`budget_exceeded`、`idempotency_conflict`。
- 分页用游标；列表默认最小字段；受限资源 `Cache-Control: no-store`。

### 12.2 核心资源（概念契约，不是最终 OpenAPI）

| 资源/端点 | 方法 | 副作用 | 幂等/并发 | 权限要点 |
|---|---|---|---|---|
| `/v1/tasks` | POST | 创建任务、入队 | `Idempotency-Key` | 工作区写权限；请求体声明品牌/brief/链接 |
| `/v1/tasks/{id}` | GET | 无 | ETag | 任务/对象读权限；字段裁剪 |
| `/v1/tasks/{id}/inputs` | POST | 补充输入、恢复任务 | `Idempotency-Key` + 版本 | 任务参与者或授权角色 |
| `/v1/tasks/{id}/cancel` | POST | 请求取消 | 版本 + 幂等 | 任务所有者/管理员 |
| `/v1/creators/{id}` | GET | 无 | ETag | 对象/账号/证据可见性分别判定 |
| `/v1/accounts/{id}` | GET | 无 | ETag | 同上；身份关联不确定性显式返回 |
| `/v1/evidence/{id}` | GET | 无 | ETag | 证据来源/字段权限；受限内容单独授权 |
| `/v1/candidates/{id}/claim` | POST | 认领 | `If-Match` + 幂等 | 资源授权；并发只有一个成功 |
| `/v1/authorization-materials` | POST | 创建待审材料 | `Idempotency-Key` | 登记权限；不宣告法务通过 |
| `/v1/approvals/{id}/decision` | POST | 批准/拒绝 | 版本 + 一次性 nonce | 指定复核角色；禁止自批（高影响） |
| `/v1/admin/connectors` | GET | 无 | — | 管理员/审计；仅状态与配置摘要 |
| `/v1/admin/audit` | GET | 无 | 游标 | 审计角色；脱敏 |
| `/v1/me/capabilities` | GET | 无 | — | 返回 UI 提示；服务端仍二次校验 |

### 12.3 前端集成规则

| 规则 | 说明 |
|---|---|
| 服务端能力提示 | `can_claim/can_approve/...` 只用于 UI；任何动作服务端重新鉴权 |
| 读页面只发 GET | 任务列表、对象档案、证据浏览、管理页加载不触发采集、分析、指标自增或外部请求 |
| 显式刷新 | “刷新/重新背调”是明确的 POST 任务，带权限、速率限制、预算与审计；不得在页面 `useEffect` 中隐式触发 |
| 新鲜度 | 所有证据/指标显示 `observed_at/fetched_at/coverage`；过期显示横幅；无数据与错误分开 |
| 冲突 | 版本冲突展示当前状态与操作建议，不静默覆盖 |
| 空/错/未知 | 不把空数据画成全 0 正常看板；保留补料/重试/联系管理员入口 |
| 卡片深链 | 卡片只带不透明引用与作用域；点击后登录并按工作台权限展示；群卡片不泄漏私聊/受限内容 |
| 契约测试 | OpenAPI 生成客户端；BFF 响应 schema 测试；前端 fixture 覆盖 `permission_denied/unknown/stale/conflict` |

## 13. 工作台信息架构（场景优先，不图表优先）

### 13.1 导航层级

```text
工作台
├─ 我的待办（任务收件箱）
├─ 任务
│  └─ 任务详情（状态/时间线/证据/未知/输入/操作）
├─ 合作对象
│  └─ 对象档案（身份不确定性/平台账号/证据时间线/候选/授权材料）
├─ 候选与认领
├─ 授权材料
├─ 监测（M1）
├─ 合作计划（M2）
└─ 管理（成员/角色、来源与连接器、预算、审计、保留策略）
```

### 13.2 页面与业务问题

| 页面 | 回答的业务问题 | 主要数据 | 允许动作 | 只读约束 |
|---|---|---|---|---|
| 我的待办 | 现在需要我处理什么？ | 我的任务、待复核、待补料、即将过期材料 | 打开、补输入、取消 | GET only；不触发采集 |
| 任务详情 | 这项任务做了什么、证据是什么、还缺什么？ | 状态、时间线、证据、未知、预算用量 | 取消/重试/补输入/发起复核 | 查看不产生新快照 |
| 合作对象档案 | 这个对象是谁、有哪些账号、可信到什么程度？ | 主体、账号、身份关联、证据时间线、候选 | 发起背调、登记材料（按权限） | 查看不合并身份、不刷新 |
| 候选与认领 | 哪些机会值得跟进、谁负责？ | 候选、来源证据、状态、负责人 | 认领、转交、标记无关 | 列表不触发评分/采集 |
| 授权材料 | 材料是否齐全、是否过期、谁在审？ | 材料类型、主体、地域、渠道、期限、审核状态 | 登记、提交复核、撤回（按权限） | 不宣告法务通过 |
| 监测（M1） | 批准名单里发生了什么变化？ | 监测规则、变化事件、证据、处理状态 | 建规则、分诊、转交 | 规则变更需权限；查看不发请求 |
| 合作计划（M2） | 针对 brief 应比较谁、计划是什么？ | brief、候选比较、评分版本、计划、复核 | 编辑草案、提交复核、登记结果 | 不自动外联/报价 |
| 管理 | 谁有什么权限、来源是否可用、钱花在哪？ | 成员、角色、来源状态、预算、审计 | 成员/角色、来源启停（高影响） | 审计只读；配置变更需批准 |

### 13.3 反模式

- 首页堆指标卡/漏斗图，却没有“我现在该做什么”。
- 用不可解释的“匹配分/真实性分”驱动排序；MVP 只展示证据、规则和未知。
- 把“查看对象”设计成自动刷新/自动采集。
- 群卡片展示超出群作用域的报价、合同、私聊内容。
- 用全 0 看板表示“没有数据”；必须区分无权限、无数据、来源故障、尚未采集。

## 14. 技术栈方向（有条件推荐，不冻结供应商）

### 14.1 推荐默认

| 层 | 拟议默认 | 理由 | 条件/替代 |
|---|---|---|---|
| 语言 | **TypeScript 优先**（Node.js LTS） | 网关/API/Worker/前端共享类型与契约；小团队维护成本低；异步 I/O 适合网关与连接器 | Python 仅在明确 SDK/数据处理优势时作为隔离 Worker |
| API | Fastify 或同类轻量 HTTP 框架 + JSON Schema/Zod 校验 + OpenAPI | 契约明确、依赖少、易测试 | 团队已有成熟框架可替换；不改变分层 |
| 前端 | React + TypeScript + Vite；查询缓存可选 | 工作台交互密集；静态部署简单 | 若企业已有设计系统/框架，沿用 |
| 数据库 | **PostgreSQL（可自托管）** | 事务、约束、行级安全可选、队列可用 `SKIP LOCKED`、全文检索足够 MVP | 托管 Postgres 仅在数据区域/安全/预算批准后（D09） |
| 队列 | PostgreSQL 持久化队列（如 pg-boss/Graphile Worker 类方案） | 少一个基础设施；事务内入队；足够初期吞吐 | 吞吐/多团队隔离有实测需求再评估专用队列；**不默认 Kafka** |
| 对象存储 | S3 兼容私有桶 | 原始证据/材料文件；签名 URL；生命周期策略 | 按公司现有云/区域选择；不绑定单一厂商 |
| 身份 | 企业 SSO/飞书身份（待 D06/D07） | 不造密码体系；减少账号风险 | 具体 OIDC/SAML/飞书 OAuth 由安全与平台确认 |
| 模型 | **ModelGateway 端口 + 供应商适配器** | 不把供应商 SDK 写入领域；可替换、可计量、可降级 | 供应商/区域/预算未批准前不选型、不采购 |
| 可观测性 | 结构化日志 + OpenTelemetry traces/metrics | 任务追踪、延迟、失败分类、成本 | 具体后端按公司设施；日志脱敏 |
| 测试 | Vitest/Playwright + fixture 连接器 + 契约测试 | 无外部副作用即可测大部分逻辑 | live 验证只在批准测试租户 |
| 部署 | 容器；单区域；Gateway 单活跃 + Worker N；API N | 简单、可恢复、成本可控 | 不默认 Kubernetes；规模/合规需要再评估 |

### 14.2 Python Worker 的正当理由

仅在以下情况引入独立 Python Worker：

- 某个**已批准数据源/模型/媒体处理**只有成熟 Python SDK，且 TypeScript 适配成本/风险明显更高；
- OCR、视频/音频分析、复杂数据处理需要 Python 生态；
- 该 Worker 消费**同一持久化队列**，通过版本化产物 API 写回，不拥有独立事实库、不复制权限逻辑、不绕过 outbox。

否则不引入第二语言，避免两套契约、两套部署与两套安全测试。

### 14.3 明确不采用（MVP）

| 选项 | 不采用理由 |
|---|---|
| 微服务拆分 | 单业务域、小团队；分布式事务/联调/运维成本大于收益 |
| Kafka/独立消息总线 | PostgreSQL 队列足够；引入后需额外运维、监控、幂等与回放治理 |
| 独立向量数据库 | MVP 证据检索以结构化过滤 + 全文检索为主；无批准的数据规模/召回需求 |
| 图数据库 | 对象关系有限；PostgreSQL 关系表 + 递归查询足够 |
| 多 Agent 自治循环 | 权限、预算、批准与可解释性风险高；MVP 用确定性工作流 + 单次模型调用 |
| 重型事件溯源 | 追加式任务/审计事件已足够追溯；全量事件溯源增加迁移与投影复杂度 |
| 自建 BFF 独立服务 | 初期与 API 同进程，逻辑模块分离即可；没有独立扩缩容证据 |
| 供应商锁定 | 模型、队列、存储、托管均通过端口/标准接口隔离；选型待 D09/D10 |

### 14.4 重新评估的触发条件

- 两个以上团队需要独立发布/独立故障域；
- 队列吞吐或延迟超过 PostgreSQL 实测上限；
- 证据检索需要语义召回且离线评测证明收益；
- 数据量/保留/区域合规要求独立存储；
- 工作台需要实时协作/推送且轮询无法满足；
- 模型/数据成本需要独立预算与配额系统。

## 15. 拟议仓库结构（最小）

```text
/
├─ apps/
│  ├─ gateway/          # 飞书长连接、inbox、卡片回调
│  ├─ api/              # BFF + 领域应用服务（HTTP）
│  ├─ worker/           # 队列消费、连接器、分析、outbox
│  └─ web/              # 工作台前端
├─ packages/
│  ├─ contracts/        # OpenAPI、事件 schema、生成客户端
│  ├─ domain/           # 实体、状态机、策略（纯逻辑，无 I/O）
│  ├─ adapters/         # 飞书、连接器、模型、存储、队列适配
│  ├─ db/               # 迁移、仓储、查询
│  └─ testing/          # fixture、契约/安全测试工具
├─ fixtures/            # 合成/脱敏固定样本，不含真实秘密
├─ docs/
│  ├─ research/         # 本研究与同批笔记
│  ├─ adr/              # 批准后的架构决策
│  └─ runbooks/         # 值班、恢复、迁移、对账
└─ ops/                 # 本地编排、CI、部署模板（后续）
```

约束：

- 一个 workspace、一个锁文件、一套 CI；不按“微服务”拆仓库。
- `domain` 不依赖框架/网络；`adapters` 实现端口；`api/gateway/worker` 只做编排。
- `contracts` 是 API/事件的单一契约源；生成物不入库或明确标记。
- 仓库根目录不得出现凭证、真实个人数据、生产导出。

## 17. MVP 核心与后续两个 PMO 能力迭代

> 说明：PMO 能力原文、Main 阶段门禁与验收条款由其他专题研究；下表是**架构分层建议**，不是对 PMO 原文的复述或已批准范围。场景 A/B/C 来自 `2026-11-08-radar-domain-scenarios.md`。

|---|---|---|---|---|
| **MVP 核心** | 场景 A：主页/账号链接 → 可追溯背调 → 人工判断 → 候选认领 → 授权材料登记 | 飞书入口（群 @/P2P）、任务、证据、对象/账号、认领、材料登记、工作台核心、RBAC/批准/审计、fixture 评测 | 全渠道持续监测、批量规则、合作计划比较、自动外联/签约/付款、向量检索、多 Agent | D01–D08、D11（范围/数据/身份/飞书/保密） |
| **M1：全渠道动态监测** | 场景 B：批准监测名单 → 有限渠道变化 → 解释/去重 → 机会或风险复核 | 监测规则、调度、增量快照、变化检测、分诊、来源覆盖/新鲜度、成本控制 | 未授权渠道覆盖、全品牌声量、消费者 VOC、PR 危机判断 | D02/D03/D05/D07/D11 |
| **M2：IP 合作计划制定** | 场景 C：brief → 候选比较 → 合作计划 → 复核与结果回流 | brief、比较、可解释评分版本、计划草案/复核、结果登记 | 自动外联/谈判/财务承诺/签约、无内部数据时的营收归因 | D02/D03/D05/D08/D11 |

**机会识别**：MVP 提供最小候选识别（背调后有证据的候选 + 人工认领）；M1 的变化信号用于增强机会发现；M2 将机会纳入计划比较。这个“三项能力 → MVP/M1/M2”的映射是建议，必须与 PMO 原文及业务 owner 确认（D01/D04）。

## 20. 来源与输出契约

**conclusion：** 建议采用 TypeScript 优先的模块化单体，配常驻 Feishu Gateway、独立 Worker、PostgreSQL 事实库与对象存储；MVP 只交付场景 A 纵向切片，监测与计划分别作为 M1/M2。该建议满足“尽可能简单但可生产化”，并保留后续能力演进空间。

**evidence：** 仅来自本轮指定五份笔记：项目边界与空目录检查；领域场景/对象/状态压力问题；安全笔记中的 OWASP 权限、提示注入、SSRF、持久化/幂等建议（B）；评测笔记的业务任务退出状态、只读不采集、版本化证据包建议；决策登记 D01–D12。未使用未指定专题或网络新研究。

**assumptions：** 首发使用者为 BD/品牌团队；飞书是主要会话入口；工作台为持续操作界面；MVP 先一个市场/品类/数据源；团队规模适合单体 + 少量进程；模型/数据供应商与部署区域尚未批准。

**uncertainty：** 飞书平台具体能力、PMO/Main 原文与门禁、数据授权与字段可得性、内部角色/批准流、预算/成本、托管区域、真实任务样本与质量基线均未确认。

**confidence：** 对“权限在模型外执行、外部内容不可信、入站先持久化、读页面不采集、批准绑定具体动作”有指定笔记的直接支持；对本项目具体拆分、技术选型与阶段映射仅为 C 级建议，需逐节点评审。
