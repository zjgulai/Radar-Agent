# Main / Agent Native Builder 全链路生命周期与 8+3 数据层契约研究

> 研究对象：`https://main.luteos.com`（Agent Native Builder，下称 Main）。
> 本笔记只做研究、对照与方案草案，不实施、不部署、不发送飞书消息、不使用任何凭据、不初始化 git。
> 站点页脚标注建站于 2026-10-24；本笔记读取于 2026-11-08。
> 校准提示：八层/读侧历史规则、站点脚本与Radar适配建议以[研究校准](2026-11-08-radar-research-calibration.md)和[主计划](../superpowers/plans/2026-11-08-momcozy-radar-zero-to-one.md)为讨论口径；读侧规则不替代所有schema迁移，站点声明的检查器不代表本项目已有脚本。VOC/声量归因建议不纳入首发范围。

## 0. 一页结论

1. **Main 不是写代码教程，而是一套“判断自己做的东西是真能用，还是只是看起来能用”的验收方法。** 首页把目标写得非常窄：七个阶段、一组能亲手做的检查、每个阶段可能怎么骗你；并明确边界：“能让你不骗自己，不能让你不骗市场。产品有没有人要，这套方法答不了。”（https://main.luteos.com/）
2. **七阶段顺序是固定的：需求 → 设计 → 开发 → 验收 → 交付 → 运营 → 迭代；管理不是第八阶段，而是横跨七阶段的记录层。** 验收是整条链路唯一的硬门：“这里不过，不许往下走。”（https://main.luteos.com/verify.html）
3. **每个阶段的核心不是“做什么功能”，而是“用什么动作证明这一步真的过了”。** 七页都给出“谁来验，怎么验”表；动作必须是本人能亲手做的，做不了就记未通过，不许用近似动作代替。
4. **Main 的验收哲学可以压缩成一句话：一条从来没有失败过的检查，不是检查。** 必须亲眼看到它红过一次；断网/密钥错时必须返回“无法判断”，不能返回“通过”；跳过必须计入并让总体结论变成“不完整”。
5. **8+3 数据层契约把数据产品拆成 8 个工序层（采集、存储、打标、指标、分析、呈现、结论、报告）和 3 个横切义务柱（口径、质量、血缘）。** 每一层要么有一个可执行的命令级检查器，要么它只是一句愿望；三条不变量是 `first_seen_at` 读侧 `min()`、空抓必须留显式日志、迁移只在读侧追加。（https://main.luteos.com/data-layers.html）
6. **8×8 矩阵是一张“契约 vs 检查器”的现实对账单。** 49 格有内容，15 格本来该空；验收行 8 格里只有 6 格是“验”，开发行 8 格全是“约”。这说明“知道怎么检查”比“真的建出来了”进展更快，也说明打标层与呈现层还存在“命名了检查器但没有落地脚本”的缺口。（https://main.luteos.com/matrix.html）
7. **Main 自己承认方法有边界并且有未修复的洞。** 第二次完整实测六步走完，三步没有完全通过，两步的验收动作做不到，且“产品仍然没有被人用过一次”。失败图鉴另有一节专门讲“有些验收，你做不到”，正确做法是记未通过，不是跳过。（https://main.luteos.com/originals/anb2-full.html；https://main.luteos.com/originals/failure-atlas.html）
8. **站点内部存在若干口径不一致，必须在 Radar 采用前钉死版本。** 需求页同时出现“五句话”“六句”“第四句/第五句”三种说法；设计页页首说“六问”，正文与管理页按“四问”校验；Agent 图谱说“14 条路线”，表里只有 11 条；G1–G5 五道交付硬门只有名字，没有任何一页给出定义。详见第 9 节。
9. **Main 的“全栈”是验证全栈，不是技术栈全栈。** 五层架构（入口、双引擎、契约/适配/评测、ANB 治理与数据矩阵、本地工具链）用单向依赖和单一真源约束；工具链是 Lody × Magpie × Nowledge Mem 的开发态组合；生产部署不在其范围内。（https://main.luteos.com/architecture.html；https://main.luteos.com/toolchain.html）
10. **对 Radar 的正确用法：把 Main 的 7+1 阶段当作“验证骨架”，不要把它当作市场发现方法或组织审批模型。** 业务发现必须补一个前置阶段 B0，并明确标注为 **OUR extension（我们的扩展），不是 Main 的方法论声明**。Main 首页和运营页都明说它答不了“有没有人要”。（见第 8 节）
11. **Radar 的第一条端到端窄路应当是“一条真实飞书消息 → 机器人回执 → 真实数据 → 可核对结论 → 用户可用的回复/卡片”，而不是先做工作台大而全。** 这是 Main 开发阶段“不做功能，只做一条最窄的路”的直接推论；Radar 的飞书长连接、3 秒回执、事件幂等属于我们的工程扩展，Main 只提供验收纪律，不提供实现规范。
12. **本笔记没有验证任何“已实现功能”。** 我能验证的是页面可打开、文本/表格/锚点存在；不能验证 Main 仓库里的脚本、177 个 skill 是否可调用、66 条检查是否可复跑、两次实测是否可复现。这些一律按网站声明（C 级）处理。

### 2.2 需求阶段（01）

**核心问题**：把“我想做个 X”变成一句话：谁在什么情况下用、用完他能做什么以前做不到的事、打开之后拿到手的是什么、什么情况说明不该做。

**分支（按代价排序）**：

| 如果 | 去哪 | 处理 |
| --- | --- | --- |
| 你说的是功能清单（“要有登录、能导出”） | `need.html#b-func` | 功能是解决方案不是问题；每个功能追问“它让用户能做什么以前做不到的事” |
| 你说的是品类（“用 AI 做内容”） | `need.html#b-cat` | 问：谁、在什么情况下、他今天没有更好的办法是因为什么 |
| 说不清“什么情况说明不该做” | `need.html#b-falsify` | 写一个可被测量的事件，不能写“如果没人用” |
| 说得清用途和对象，说不清“它给你什么” | `need.html#b-hands-back` | 写成一个能用手的名词，例如“一份每句都标了依据哪条政策的回复草稿” |
| 否定条件写着“做不出来就别做”，而你说“人能判断出来” | `need.html#b-human-vs-product` | 问“他凭哪一条信息判断”：指向另一个系统→换输入；指向问人→产品只能做一半；指向经验→停机 |
| 一句话清晰且否定条件可测 | `need.html#b-next` | 进入设计 |

**强制产物**：`work/requirements/` 下的 `R-`（一句话承诺），以及单独的“能力清单”表（一项能力一行）。`tables-need.html` 的需求表 17 个字段包括：需求编号、要解决的问题、业务方确认了吗、交付什么、交付成什么形态、产品名称、产品线、做完能多做什么、开始日期、涉及哪几层、状态、现在怎么疼、能力清单摘要、要做的事、谁会用、里程碑、预计完成日期。能力清单 7 个字段：能力编号、名称、优先级、对应设计、属于哪一层、属于哪条需求、解决什么问题。

**可失败检查**：

- 把六句念给一个不做这行的人，他能复述用途、对象、以及它会还给他什么。
- 否定条件是一个可被测量的事件，不是“如果没人用”。
- 否定条件说的是“产品能做到”，不是“人能做到”；问“这个判断凭哪一条信息”，只能答“经验”就已经触发停机。
- 写下了“这一步需要谁参与”；需要别人而找不到，现在就记未通过。

**Skills**：`anb-idea`（五句话+可证伪否定条件）、`interview-me`（把一句话问成可验收意图）、`grilling`/`grill-me`/`grill-with-docs`、`wayfinder`、`agent-delivery-router`、`sharpen`、`in-your-own-words`。来源：https://main.luteos.com/skills.html#anb-idea 等。

**注意到的内部不一致**：页面同时出现“五句话”（`anb-idea`）、“六句”“六句里最容易漏的一句”（`need.html#b-hands-back`）、“第五句问的是他能做什么”（`need.html#branches`）与“第四句问的是他能做什么”（同一页正文）。这三种计数不能同时成立；Radar 采用前必须钉死“到底是五句还是六句、产物句是第几句”。这不影响方法方向，但会影响模板与验收表。

### 2.3 设计阶段（02）

**核心问题**：把“以后改起来很痛”的事先定下来。页面页首说“六问方法论”，正文与管理页实际按“四问”校验：

1. **流程形状**：哪些步骤固定、哪些要临场判断。测试只有一个：你能不能把决策树画出来？能画就是管线；画不出来才需要 agent。判断点 0–1 处应退回管线。
2. **拒绝清单**：每条按“一个具体输入 → 它必须改做什么”重写；写不出具体输入的是价值观，会在验收时被安静删掉。实测 11 行里只有 3 行是真正禁令，其余 8 行是“这种情况该怎么答”，两块形状不同必须分开。
3. **动作权限**：按“能不能撤销”分三档，不按重要性：可撤销→放行；会被看见或花钱→放行但记账并设数字额度；不可撤销→先问人。中间档最容易被跳过，损失都在那里。
4. **交接契约**：每个工具三行：做什么、什么时候别用、失败时返回什么；第二行是重点。

**实测又补的两块**（页面称“最后两块是实测加上的”）：把前四块交给 agent 实现最窄路径时，它集中猜“产出到底长什么样”，而四块里没有一块回答它；原来的“拒绝清单”一块装了两样东西。因此实际要写的是 4 个核心块 + 产物形态 + 禁令/应答分表。页面说“六问”，但 `work check` 与验收动作仍按四块检查；这是需要钉死的版本差异。

**分支**：`b-agent`（该不该用 agent）、`b-refuse`（拒绝清单写成价值观）、`b-perm`（按重要性排权限）、`b-contract`（交接契约只写“它做什么”）、`b-done`（四问答完用数问题验收）、`b-prohibitions`（拒绝清单越写越长）、`b-scattered`（输入存在但散在好几处）、`b-skip`（只读/一次性可跳过但要写下理由）。

**强制产物**：`work/designs/D-xxx`，包含四块答案；标 `confirmed` 时必须写“什么情况说明这个设计错了”（重议条件）。难回退选择写 `docs/adr/` 的 ADR；术语写进 GLOSSARY。样例表见 https://main.luteos.com/tables-design.html。

**可失败检查**（`design.html#verify`）：

- 四块都写了，跳过的块写明理由；“跳过：只读，没有动作”算写完，空白不算。
- 判断点写下来并命名了，不是只有一个数；“三处”必须能指出是哪三处。
- 应答规则每一行的“该怎么答”都落在动作权限表允许的动作里；三轮实测里三处硬矛盾全是跨块的。
- 把记录交给一个 agent 后，它报的“哪几块互相冲突”是空的；光猜测量降到零不算完。
- 拒绝清单每一条都有具体输入和一个改做什么。
- 动作清单按“能不能撤销”排，不按重要性；中间档写了数字额度。
- 把四块交给 agent，它问你的问题在三个以内；两轮正常，超过三轮说明缺一整块。

**Skills**：`anb-design`、`architecture-decision-records`、`domain-modeling`、`codebase-design`、`spec-driven-development`、`to-spec`、`writing-plans`、`to-tickets`、`api-and-interface-design`、`database-schema-designer`、`auth-implementation-patterns`、`architect`、`arena`、`principle-exhaust-the-design-space` 等。

### 2.4 开发阶段（03）

**核心纪律**：不做功能，只做一条最窄的路；一条真实输入从头走到尾，出一个真实结果；不许有任何假数据。开工前跑 `node scripts/design.mjs constraints`：判断点要保持为判断，动作权限要实现成边界。

**分支**：`b-fake`（结果来自样例/固定数据）→ 换一个自己随手找的真实输入；`b-narrow`（只对一种输入有效）→ 换第二个没预想过的输入；`b-error`（错误看不懂）→ 错误必须说清哪一步失败、为什么、用户能做什么；`b-next`（真实输入跑通两次，结果都能给人看）。

**强制产物**：可运行的一条路径 + 真实运行证据（命令+原始输出+能证明什么/不能证明什么）+ 对应票据 `T-`。样例表见 https://main.luteos.com/tables-build.html。

**可失败检查**：

- 你自己用随手找的输入跑了一次，不是它准备好的样例。
- 换一个你没预想过的输入，也跑通了；两个都能跑才算跑通。
- 失败时报的是一句人话，且退出码非零；不是静默通过，也不是堆栈。

**Skills**：`anb-runnable`（核心）、`implement`、`implement-spec`、`tdd`、`ponytail`、`karpathy-guidelines`、`reuse-first`、`prototype`、`using-git-worktrees`、`swarm`、`principle-build-the-lever`、`principle-laziness-protocol`、`principle-subtract-before-you-add`、`deslop`。

### 2.5 验收阶段（04）

**定位**：整条链路唯一的硬门；这里不过，不许往下走。没有这一步，后面每一次改动都是无法测量的，产品会安静地变差，而所有人都以为在变好。

**核心规则**：

- 先写 5–10 条“什么样算好、什么样算坏”，每条要么能数、要么需要读一遍判断；顺序必须是先写检查再改产品，反过来检查只会描述现状。
- 一条从没失败过的检查不是检查。必须故意造一个违反它的结果，看它会不会红。
- 检查红了先问：是产品错了还是测试错了？实测三条红的三条全是测试自己写错；直接改代码迁就错的测试，会让测试变绿、产品变坏。
- 全绿但结果不好是另一类问题：机制可信 ≠ 产出可用；要问“有没有一条检查是关于结果对不对的”，并看三个真实输入的输出。
- 任何检查必须三种结果：通过、不通过、未能判断；第三种绝不能算通过。

**强制产物**：`work/evidence/` 的 `E-`（无状态、只增不改），每条证据 = 一条命令 + 原始输出 + 它能证明什么 + 不能证明什么。验收表一行是“一次检查”，不是“一项能力”；样例 24 个字段包括通过门槛、卡在哪、只有这种算通过、实际跑了、实际通过、对应开发/需求、怎么判、成本与步数上限、护栏级别、检查方式、用例从哪来、结果、跑的哪个版本、这一项验什么、重复次数、防止什么真实失败、验收对象、从哪个入口进、点下去该到哪、用哪个角色登录、最近一次跑。见 https://main.luteos.com/tables-verify.html。

**可失败检查**：

- 你亲眼看到过一条检查变红，并能说出是哪条抓到的；不是“应该有”，是“我看到了”。
- 被跳过的检查数为零，或者整体结论是“不完整”；“跳过”绝不能算通过。
- 成功 + 各种失败原因 = 总数；拆开加一遍，两分钟。

**Skills（硬门相关）**：`anb-judgeable`（唯一硬门）、`anb-check-break`、`anb-check-offline`、`anb-check-readback`、`anb-check-reconcile`、`anb-check-output`、`verification-before-completion`、`llm-evaluation`、`code-review`、`security-review`、`diagnosing-bugs`、`interrogate`、`principle-prove-it-works`、`principle-explain-the-number`、`blast-radius`、`thermos`。

### 2.6 交付阶段（05）

**核心问题**：别人拿到一个地址就能用，不需要你在旁边。开发时密钥、数据、权限、地址四件事在你这里全是配好的，在别人那里全是缺的；它们不会在开发时报错，因为开发时本来就没用到未配置的形态。

**分支**：`b-local`（只有你能打开的本地地址，不是交付）→ 换设备/换人；`b-wall`（别人一进来就撞墙：配额耗尽、权限不足、依赖没装、域名/证书）→ 提前算配额；`b-nobody`（能打开也能用但没人告诉你哪不好）→ 让一个人试，你只看不帮；`b-next`（换设备+换人）。

**强制产物**：`work/receipts/` 的 `REC-`（谁收到了什么）、部署清单、回滚步骤。样例表见 https://main.luteos.com/tables-ship.html。

**可失败检查**：

- 用手机打开这个地址；打得开才算交付。
- 另一个人在没有解释的情况下用了一次；他问的每一个问题都是一个缺陷，不是文档缺口。
- 所有密钥来自环境，不在任何文件里；全仓搜一次。

**Skills**：`anb-shipable`、`anb-check-otherdevice`、`pr`、`deploy-checklist`、`deployment-patterns`、`milestone-report`、`make-pr-easy-to-review`、`babysit`、`blast-radius`。

### 2.7 运营阶段（06）

**覆盖声明**：半个覆盖。`anb-observable` 覆盖技术侧观测（跑几次、花多少、为什么失败）；产品侧观测（有没有人用、用了之后有没有变好）需要业务埋点。页面明确说：“技术上的‘全部正常’和产品上的‘没人用’可以同时成立。”

**核心规则**：

- 先有三个数字：跑了多少次、失败多少次、为什么失败；没有观测就加功能，等于在黑暗里挪。
- 总数和分项对不上说明记录有洞：有请求开了头没结尾，或被算了两次。更隐蔽的版本：你去看仪表盘的那次请求，自己也被计入仪表盘；每看一次，数字就涨一次，而且只涨不跌。
- 动作：把总数拆开加一遍；什么都不做刷新五次，看数字会不会自己动。

**强制产物**：`work/artifacts/` 的 `ART-`（有持续成本的东西，登记 owner 与过期）、`work/incidents/` 的 `INC-`（计划外发生的事）、三个数字的观测面板/查询。样例表见 https://main.luteos.com/tables-operate.html。

**可失败检查**：

- 做三次，历史里有三条；做 N 次数 N 条。
- 故意弄坏一次，能在记录里找到它和原因；找不到就是记录有洞。
- 知道花了多少；API 配额与 token 两个都要能看清。

**Skills**：`anb-observable`、`observability-and-instrumentation`、`instrument-product-analytics`、`artifact-registry`、`tech-debt`、`deprecation-and-migration`、`repo-gc`、`ponytail-audit`、`show-me-your-work`、`ketchup`、`reflect`、`what-did-i-get-done`。

### 2.8 迭代阶段（07）

**核心问题**：迭代不是加功能，是去掉不该留的；判断标准是“上个产品用过吗”，不是“这个可能有用”。

**分支**：`b-add`（要加新功能）→ 先问它解决观测到的哪个问题；答不出就是猜；答出了落成 `R-` 或 `T-`。`b-template`（想抽通用模板）→ 判据不是“用了几次”，是“它的形状会不会随产品变”；测试运行器形状不变，抽两次就够；仓库骨架形状每次都变，抽出来是负担。`b-keep`（想保留但说不清理由）→ 删掉。`b-next`（有真实使用数据，知道该改什么）→ 回到需求。

**强制产物**：`work/requirements/` 的 `R-` 或 `work/tickets/` 的 `T-`；复盘项有 owner 和复查日期。样例表见 https://main.luteos.com/tables-iterate.html。

**可失败检查**：

- 每一项保留物都能说出“在哪个产品用过、用了几次”；答不出来的删掉。
- 用模板开第二个产品，计时比第一个快；更慢说明模板是负担。
- 复盘产出的每一项有 owner 和复查日期；没有归属的改进项等于没有。

**Skills**：`anb-reusable`、`retro`、`improve-codebase-architecture`、`triage`、`setup-matt-pocock-skills`、`consolidate-memory`。

### 2.9 管理（横跨七阶段）

管理不是第八个阶段，是横跨七阶段的地基。票据在需求时开，状态在开发时流转，证据在验收时落地，事故可能发生在任何一刻；把它抽成“第八步”，前七步就都在没有记录的情况下跑完了。

**八个寄存器**：

| 目录 | 放什么 | 流转 | ID | 谁写 |
| --- | --- | --- | --- | --- |
| `work/requirements/` | 需求：一句话承诺 | drafting → awaiting-verification → confirmed → dropped | `R-` | 需求 |
| `work/designs/` | 设计记录：四问的答案 | drafting → confirmed → superseded | `D-` | 设计 |
| `work/tickets/` | 执行票：跨会话的工作单元 | open → in-progress → awaiting-verification → done | `T-` | 开发–交付 |
| `work/incidents/` | 事故：计划外发生的事 | open → contained → closed | `INC-` | 任何阶段 |
| `work/artifacts/` | 有持续成本的东西 | active → expired | `ART-` | 运营 |
| `work/evidence/` | 证据：命令 + 原始输出 | 无状态，只增不改 | `E-` | 验收 |
| `work/receipts/` | 回执：谁收到了什么 | 无状态，只增不改 | `REC-` | 交付 |
| `docs/adr/` | 决策记录 | 无状态机，永久保留 | `ADR` | 设计 |

**三条管理铁律**：

1. 每一类信息只有一个家；可以被多处引用，不能被复制。复制不会立刻出错，它会先安静地存两份，等改了一个忘了另一个时才出问题。
2. 判断标准只有一个：它会不会变。会变→`work/`；不会变→`docs/`。ADR 接受后不改，所以住 `docs/adr/`；设计记录会起草、确认、被推翻，所以住 `work/designs/`。
3. 状态是目录，不是文字。票住在 `work/tickets/open/`、`work/tickets/done/`；移动文件就是改状态，状态无法与文件位置矛盾，`ls` 就是看板。代价是改状态要移动文件，所以有 `work-move` 先校验转移合法。

**证据定义**：一条命令 + 它的原始输出 + 它能证明什么 + 不能证明什么。最后两段是重点；“这条测试证明了解析器，不能证明供应商可达”是真话。票要标 done，`work-move` 会检查 `evidence:` 字段；没有就拒绝。

**CI 门禁**：`node scripts/work.mjs check`（ID 唯一、done 有证据、needs 指向存在）、`node scripts/layout.mjs`（文件位置）、`facts --check`（文档引用过时数字）、`naming check`（skill 把阶段写成编号）。都返回非零退出码，可直接当门禁。页面还自曝三次“没有抛错但给出自信错误输出”的经历：硬编码 `ticket` 而 schema 是 `tickets`，五张票全部不可见却报告“0 张票，一切正常”；正则只匹配 `[A-Za-z0-9_]` 导致 `in-progress`/`awaiting-verification` 被丢掉；`check` 漏掉 append-only 寄存器，五张票加三份证据只报“5 条记录”。三次都由“临时把 bug 注回去、看测试会不会红”锁住。

| --- | --- | --- |
| `b-local` | 只有你能打开（本地地址） | 不是交付；密钥、数据、权限、地址四件事在别人那里全是缺的 |
| `b-wall` | 别人一进来就撞墙 | 最常见：配额耗尽、权限不足、依赖没装、域名/证书；提前算配额 |
| `b-nobody` | 能打开能用但没人告诉你哪不好 | 让一个人试，你只看不帮；他卡住的第一步就是下一步工作 |
| `b-next` | 换设备打开过、另一个人用过 | 进入运营 |

### 运营（4）

| 分支 | 如果 | 处理 |
| --- | --- | --- |
| `b-blind` | 不知道跑了多少次、失败多少次 | 先补三个数字，再谈别的 |
| `b-reconcile` | 总数和分项对不上 | 记录有洞；拆开加一遍；刷新五次看数字会不会自己动 |
| `b-nouser` | 数字正常但不知道有没有人真的在用 | 产品侧观测需要埋点；技术观测答不了 |
| `b-next` | 能回答谁在用、用了多少次、哪里失败 | 进入迭代 |

### 迭代（4）

| 分支 | 如果 | 处理 |
| --- | --- | --- |
| `b-add` | 要加新功能 | 先问解决观测到的哪个问题；答不出就是猜；答出落 `R-`/`T-` |
| `b-template` | 想抽通用模板 | 判据不是用了几次，是形状会不会随产品变 |
| `b-keep` | 想保留但说不清理由 | 删掉 |
| `b-next` | 有真实使用数据，知道该改什么 | 回到需求，开始下一轮 |

### 管理（4）

| 分支 | 如果 | 处理 |
| --- | --- | --- |
| `m-file` | 打算做一件事且不止一次会话 | 开票；一次会话内做完并验证的不要开 |
| `m-file` | 发生了一件没计划的事 | 开事故，不是票；票是你打算做，事故是发生了 |
| `m-commands` | 文档数字和实际对不上 | 先跑 `facts`，再改文档；磁盘可能是意外的那个 |
| `m-status` | 记不清现在什么状态 | 状态就是目录，`ls` 一次比回忆可靠 |

## 4. “全栈”路线：架构、工具链、Agent 图谱

### 4.1 五层架构与三条死律

| 层级 | 核心包/目录 | 职责 | 硬性护栏/禁令 |

| L3 契约、适配与评测底座 | `packages/shared`、`packages/feishu`、`packages/evals` | shared：Zod 领域模型；feishu：事件验签解密、富文本/卡片格式化；evals：14 用例+15 确定性规则+Rubric 裁判 | `packages/shared` 不得 import 仓内任何包；新增工具必须同步写白名单 |
| L4 ANB 治理与数据矩阵层 | `work/`、`docs/product/`、`scripts/` | 八个寄存器；`matrix.json`（8×8）与 `tables.json`（13 张样张）；`build.mjs` 零孤儿页生成器 | 无检查器的契约只能标“约”不能标“验”；文档引用数字必须过 `facts.mjs --check` |
| L5 本地开发工具链 | Nowledge Mem、Lody、Magpie | 记忆注水与红线守门；4 机执行池/Worktree 隔离/异步回执；127.0.0.1:3425 三协议互转与 429 容灾 | 不介入生产部署运行时；不在 Nowledge Mem 存业务数据 |

**三条死律**：依赖单向不可逆（`apps/workbench` 与 `apps/bot-gateway` 严禁互相 import，只能单向调用 `packages/core` 或 `packages/consult`；`packages/shared` 零内部依赖）；三大唯一真源（领域对象在 `packages/shared` 的 Zod，四品牌护栏在 `packages/core/src/seed/brands.ts`，生命周期阶段在 `work/schema.yml`）；分层归因铁律（修复 Agent 质量问题严格按 `eval → data → tool → prompt` 顺序，严禁跳过底层数据与工具契约直接改提示词）。

### 4.2 四条跨模块调用流

| 业务流 | 调用路径 | 契约保障 |
| --- | --- | --- |
| 飞书群提问/TikTok 链接 | `apps/bot-gateway → packages/core` 或 `packages/consult` | 网关识别 TikTok 链接或 `/recipe` 指令走 core 异步生成管道（3s 回执+队列投递）；识别方法论/数据提问走 consult 返回五段式结论 |

### 4.3 工具链：Lody × Magpie × Nowledge Mem

**定位分工**：Magpie 管模型从哪来（本地路由网关，`127.0.0.1:3425`，OpenAI/Anthropic/Gemini 三协议互转，429 自动切换，本地用量账本）；Lody 管活怎么派（多机多 Agent 控制平面，Git worktree 隔离，ACP 托管 40+ CLI，长任务异步回执，Diff 行级评审）；Nowledge Mem 管昨天学到的怎么带到今天（会话启动注水、持久记忆 8 种 unit_type、Space 隔离、BM25+向量混合检索、对话蒸馏）。

**一条链**：记忆注水 → 调度派活 → 路由降本 → 验收回流 → 记忆沉淀。三个衔接点很薄：Nowledge Mem 的 hook 独立注入；`lody agent-config import-magpie` 一条命令导入路由组；验收会话产生的决策用 `nmem m add` 写回记忆。

**SOP（一个特性从想法到合并）**：01 开工 `nmem m search` 查旧账；02 人+Agent 写 spec，关键决策当场 `nmem m add`（importance 0.8+）；03 Lody 派子任务到远程 worktree，批量用 `chat_many`；04 Magpie 选路由组（探索用 free，正式生成用 opus）；05 人+Lody 逐行看 diff，意见写在行上回传；06 合并后蒸馏线程，重要教训写回记忆。

**两条红线**：第 1 步检索不能省（记忆库里的旧决策不查就是不存在，这是“找不到≠不存在”的镜像错误）；第 6 步写记忆前先检索去重（重复记忆会让检索质量退化，最终整条链失灵）。

**三个不要接**：不要让 Nowledge Mem 存业务数据（它是开发记忆，不是产品数据库）；不要让 Lody 管生产部署（它是开发态平台，产物走 Git PR 进 CI）；不要在生产环境依赖 Magpie 的订阅桥接（ToS 风险+本机单点）。

**什么时候这套组合是错的**：单人单机单任务；生产环境；对外产品内嵌多租户记忆；需要审计合规的团队。页面明确说这些情况下这套组合要重新评估。

### 4.4 Main Agent 图谱：4 轴、17 节点、11 条路线

**四条坐标轴**：

- 生命周期（7+1）：需求→设计→开发→验收→交付→运营→迭代→管理；回答“现在处在哪一步、这一步的关门条件是什么”。
- 数据产品层（8）：采集→存储→打标→指标→分析→呈现→结论→报告；回答“卡在哪一层、这一层的输入/输出/失败模式是什么”。
- 横切三柱（3）：口径/质量/血缘；回答“这个数字的定义、可信度、来路能不能说清”。
- Agent 交付车道：Incident / Exploration / Capability / Fast（G1–G5）；回答“这是能力问题还是确定性问题、最少要过哪几道门”。

**17 个能力节点**：能力导航、意图与决策、结论卡规范、指标契约、采集时点、存储与血缘、打标体系、分析与识别、呈现与下钻、报告与证伪、Agent 行为边界、评测质量、失败诊断、交付车道、方法治理、飞书网关、长任务处理。每个节点有 ID（如 `navigate-capabilities`、`data-conclusion-card`、`feishu-surface`、`long-running-tasks`）。

**路线**：页面导语说“14 条症状路线”，表里实际列出 11 条：`route-idea`、`route-attribution`、`route-metric-drift`、`route-collection-lag`、`route-label-version`、`route-report-theater`、`route-agent-quality`、`route-agent-scope`、`route-delivery-process`、`route-fake-green`、`route-feishu`。**14 与 11 的差额没有解释；G1–G5 也只有名字没有定义。**这是 Main 公开页面的未完成处，不能当作 Radar 可执行规范。

**执行链路**：用户提问 → 1 分类（匹配 17 节点与意图范围，低于阈值追问或礼貌拒绝）→ 2 路由（按 14 条症状路线选最经济首检）→ 3 检索（BM25 检索知识库 chunk，优先规范定义与事实依据）→ 4 成文（【结论/定位/依据/下一步/边界】五段式）→ 5 校验（禁止大模型生成无依据的路径与指令）。

### 4.5 “全栈”的边界

Main 的“全栈”覆盖的是从想法到可验收、交付、运营、迭代的**验证链路**，加上数据产品的 8 层工序与 3 个横切义务；它不覆盖市场发现、销售、财务、法务、安全合规、SLA、容量规划、多租户隔离、生产高可用。页面自己也把 L5 限定为“本地开发工具链”，并说“开发态工具链不介入生产部署运行时”。对 Radar 而言，不能因为 Main 有 `apps/bot-gateway` 的描述，就认为可以直接复用其生产架构；那是 Main 仓库的声明，不是我们的实现，也不是官方平台约束。

## 5. 8+3 数据层契约：八层、三柱、三不变量、八跳

### 5.1 八层完整契约

| 层级 | 输入契约 | 输出契约 | 典型失败模式 | 检查器 |
| --- | --- | --- | --- | --- |
| **采集层 (Collection)** | Apify actor / 第三方 API 原始返回 | `{raw, first_seen_at, fetched_at, source_task_id, schema_version, taxonomy_version, metric_version}` | 时滞跨区域不一致；抓取时点缺失；空抓不记录 | `collect-audit`（0=通过 / 1=失败 / 2=无法判断） |
| **存储层 (Storage)** | 采集层适配器输出的标准观察记录 | 按条目单行归档：`first_seen_at` 为最早一次，`raw` 为最新一次，保留所有历史原始快照 | `first_seen_at` 被重跑覆盖；字段迁移后旧版本数据无法读取 | `collect-store verify`（0=不变量成立 / 1=有结构性破坏） |
| **打标层** | 清洗后的文本载荷与媒体元数据 | 多维度标签值、置信度分数、`taxonomy_version` | 模型漂移导致打标标准不一致；Kappa 一致性不足 | `label-audit` |
| **指标层** | 明细数据与标注结果 | 规范化聚合指标、统计口径版本、计算周期 | 分子分母口径漂移；时间区间对不齐；缺失值填充错误 | `metric-card check` |
| **分析层** | 指标时间序列与控制变量面板 | 回归弹性系数、置信区间、诊断统计量 | 共线性过高；伪相关未剔除；置信区间跨 0 仍下结论 | `panel-fit` |
| **呈现层** | 分析模型输出与指标汇总 | 支持按维度下钻的可视化视图、明确标注的数据三态 | 图表截断坐标轴；空状态与错误状态混淆 | `ui-render-test` |
| **结论层** | 分析结果与业务事实 | 六项结论卡（主张、依据、区间、动作、证伪条件、失效期） | 主张无法被证伪；写出无动作含义的纯陈述 | `verify-conclusion` |
| **报告层** | 结构化结论卡集合 | 面向决策者的定期汇报文档或告警推送 | 未触发证伪告警；结论失效后未同步下线 | `report-audit` |

> 页面原话：“每一层要么有一个可执行的命令级检查器，要么它只是一句愿望。”（https://main.luteos.com/data-layers.html#all-layers）

### 5.2 三条不变量铁律

1. `first_seen_at` 不是可被修改的列，而是读侧计算的 `min()`，历史不可改写。
2. 空抓必须留存显式日志记录，明确区分“数据为空”与“抓取失败”。
3. 数据迁移是读侧的（追加 migration 规则），旧数据永远保持原样可查。

来源：https://main.luteos.com/data-layers.html#invariants

### 5.3 横切三柱的每层义务

| 柱 | 义务 | 对 Radar 的直接含义（D） |
| --- | --- | --- |
| **口径 (Definition)** | 每个数字的公式、时间窗、分子分母、异常值处理必须单一来源定义，修改必须升版本号 | 每个“声量/互动/情绪/GMV/ROI”指标一张指标卡；口径变更升版本、不重算历史；跨期比较必须能区分“口径变了”与“业务变了” |
| **质量 (Quality)** | 必须能够区分真实 0、抓取失败、未到抓取周期三态，不允许静默填补假数据 | 空结果必须显示“本次抓到 0 条”还是“抓取失败”还是“未到周期”；缺失值必须是 `null` 不是 `0` |
| **血缘 (Lineage)** | 任意一个报表上的数字，必须能够无歧义地回溯到对应的原始数据快照与处理代码版本 | 结论→指标（带版本）→标注（带 `taxonomy_version`）→记录→原始载荷，逐跳可查；断在哪一跳就停在哪 |

### 5.4 八跳衔接（8×8 矩阵的交接契约）

| 从 | 到 | 交的是什么 | 带哪些版本 | 下游怎么校验 | 断了会怎样 |
| --- | --- | --- | --- | --- | --- |
| 开发·采集 | 开发·存储 | 观察记录：`raw + first_seen_at + fetched_at + source_task_id` | `schema_version + fetched_at` | `source_task_id` 在账本里有对应 run；`first_seen_at ≤ fetched_at` | 没有 `first_seen_at` → 时间序列锚在抓取时刻，“抓得晚”被读成“更热” |
| 开发·存储 | 开发·打标 | 去重后的条目 + 四类归属命名空间 + 原始载荷 | `schema_version + taxonomy_version` | region 落在四值命名空间内；`unattributable` 至少两个冲突依据 | 归属摊派给 unknown → 分母完整但错，且看起来没有任何问题 |
| 开发·打标 | 开发·指标 | 标签 + 置信度 + `taxonomy_version` | `taxonomy_version + metric_version` | 读到的 `taxonomy_version` 不等于指标卡声明版本时报警，不许猜 | 标签改版后静默合并 → 去年的数和今年的数不是一个体系，而台阶看不见 |
| 开发·指标 | 开发·分析 | 数值 + 口径版本 + 分母规模 | `metric_version + produced_at` | 分母骤降时拒绝出结论；口径版本不同的两期不许直接相减 | 口径变更被读成业务变化——最贵的一种错误 |
| 开发·分析 | 开发·呈现 | β + 95% 区间 + 吸收了什么的说明 | 模型设定版本 + `produced_at` | 区间跨 0 的数字不进聚合视图；“关联不是因果”的标签必须跟着数走 | 交付一个识别不成立的看板，而它看起来完全正常 |
| 开发·分析 | 开发·结论 | C1–C4 + 区间 + 有效样本量 | 模型设定版本 + `upstream_versions` | 区间跨 0 → 该条结论不许落卡；样本不足 → 降级为描述性 | 结论卡带着一个什么都没有的区间发布 |
| 开发·结论 | 开发·报告 | 结论卡 + 证伪条件（可执行）+ status | 口径版本 + `taxonomy_version` | 证伪条件必须是已注册的函数名；未注册的名字算“无法判断”不算通过 | 证伪条件写成“如果结论错了” → 无法被触发，报告退化成 dashboard |
| 开发·报告 | 迭代·结论 | 证伪触发 → 旧结论转 `superseded` + 新结论 + 为什么推翻 | `produced_at` | 旧结论原件保留不删；新结论指回旧结论；`superseded` 不被再次告警 | 直接删掉旧结论 → 失去“我们错过什么”的记录 |

来源：https://main.luteos.com/matrix.html（“八跳衔接”表）

### 5.5 8×8 矩阵：验 vs 约

- 7 阶段 + 管理 × 8 层 = 64 格；49 格有内容；15 格“本来就该空”（需求阶段不选数据源，呈现层没有交付就没有运营）。
- 状态由脚本算出，不手填：“验”=有检查器且命令指向的脚本存在；“约”=三件事齐但没有检查器（契约在，执行不在）；“空”=三件事有缺或写了“同上”。
- 验收行 8 格里 6 格是“验”，开发行 8 格全是“约”；这说明“知道怎么检查”比“真的建出来了”进展更快。
- **矛盾点**：`data-layers.html` 为打标层指定了 `label-audit`、为呈现层指定了 `ui-render-test`，但 `matrix.html` 把这两格标为“约”（无检查器）。以矩阵的“脚本存在”判定为准，则这两层只有检查器名称、没有落地脚本。`tables-verify.html#acc-05` 也明确写“矩阵记录它没有检查器：正确，因为可达性只能点”。这是“命名了检查器 ≠ 检查器已接入”的直接证据。
- 迭代行“呈现/报告”为空，矩阵自认是“已知洞”；运营行是唯一 8/8 满行的阶段（数据产品没有终点）。

### 5.6 Momcozy 声量→GMV 归因案例（Main 的公开示范）

**设计顺序铁律**：自顶向下（与建造顺序相反）：结论层 → 指标层 → 打标层 → 采集/存储 → 呈现/报告。理由是试跑实测教训：自底向上建到一半才发现底层数据支撑不了上层决策，是数据产品最昂贵的死法。

**三个前置发现**：

- **F1 缺少预算自变量**：只有 GMV + 声量数据，能算“声量→GMV 弹性”，但算不出“预算→声量成本”；决策者拿到弹性仍不知道往哪投，因为弹性高可能获客成本极高。必须补齐“按区域×渠道的花费数据”才能做 C4 边际回报。
- **F2 面板固定效应吸收趋势**：声量与 GMV 均随时间上升，单序列必然产生 0.9 的假相关；决策单位转为“区域×周”的面板，引入周固定效应吸收全球增长趋势与算法变动，识别变异集中在“同周内 A 区域声量超常增长是否带来 GMV 超常增长”。
- **F3 全球效应不可识别**：周固定效应消除伪相关的同时，也吸收了全球共性变化；一次全球品牌大事件或平台大促的影响无法归因到特定区域声量。这是模型的前提约束，必须在结论卡中明确声明。

**四级结论卡**：

| 层级 | 商业问题 | 交付物与指标 | 失效/证伪条件 |
| --- | --- | --- | --- |
| C1 基础关联与存在性 | 区域声量与 GMV 之间是否存在统计显著的正向关联 | 弹性系数 β、95% 置信区间、样本量、观测周数 | 置信区间跨 0，或控制促销/缺货后 β 降为 0 → 停止归因 |
| C2 时滞与衰减周期 | 声量增长后 GMV 第几周达峰、影响持续几周 | 滞后 1–4 周弹性系数与脉冲响应曲线 | 滞后各期系数均无统计显著性 → 失效 |
| C3 区域差异与弹性对比 | 哪些区域高声量敏感、哪些低响应 | 分区域弹性分档表（高/中/低）+ 基线规模对照 | 区域分类连续两季度波动超 50% → 失效 |
| C4 预算边际回报决策 | 各区域追加 1 万元预算预计撬动多少增量 GMV | 区域边际投入产出比（ROI）+ 推荐预算增减比例 | 未获得各区域真实获客成本/投放花费数据 → C4 不做产出 |

**模型**：

```
ln(GMV)_{r,t} = β · ln(声量)_{r,t-k}
              + 区域固定效应 α_r
              + 周固定效应   λ_t
              + 控制变量     X_{r,t}   (促销折扣、价格变动、断货天数、竞品大促)
              + ε_{r,t}
```

来源：https://main.luteos.com/data-design.html#discoveries、#conclusions、#model

### 5.7 对 Radar 的直接含义（D 草案）

- Radar 如果先做“飞书问答/洞察”，不一定立刻需要完整 8 层；但只要输出任何数字，就至少要落“采集时点、存储不变量、指标口径、结论证伪”四层，否则数字不可复核。
- 如果 Radar 要做“区域声量→GMV”类归因，Main 的 F1–F3 必须作为设计前置发现，不得跳过；C4 在没有预算/花费数据前明确不做产出。
- 如果 Radar 只做“舆情监控/内容洞察”，也应把“结论卡六项”降维成“主张、依据、区间/置信、动作、证伪条件、失效期”，哪怕区间是“样本不足，仅描述”。
- 飞书回复中的每个数字都应能下钻到原始帖子/评论与抓取时点；做不到就不要在回复里给数字，改为“查不到/数据不足/无法判断”。

## 6. 安全与误判分类：七类、11 个案例、两分钟自检

### 6.1 七类误判（四类来自系统，三类来自你自己）

| 类 | 名称 | 案例 | 它怎么骗你 | 你怎么自己发现 | 纪律 |
| --- | --- | --- | --- | --- | --- |
| 一 | 它把“坏了”报成“好了” | 1 安全检查把服务挂了算成成功拦住；2 需要人判断的部分一次没实现却被算通过 | 判定条件写成“没有产出 并且 运行没有成功”，崩溃与拒绝同形；跳过被算通过，报告只让你看最后那个词 | 把外部依赖弄断（密钥改错/删掉）再跑，正确结果是“无法判断”；逐条念结果，必须听到跳过了几条、为什么 | 任何检查必须有通过/不通过/未能判断三态，第三态绝不能算通过；跳过的检查必须占一格并让总体结论“不完整” |
| 二 | 它测的不是你的产品 | 3 所有测试通过，但真实运行时第一步必失败 | 假环境比真实环境更宽松：真实会报错的地方，假环境静默通过；样例被特判 | 问“这个测试用的是真数据还是假数据”；用自己随手找的真实输入跑一次 | 假环境必须比真实环境更严格；同一套检查既跑假的也跑真的 |
| 三 | 保护机制在，但永远不会启动 | 4 成本上限检查等一个永远不会来的值 | “当前花了多少”只在整次运行结束才填，每轮读到 0；代码、注释都在，没人看赋值位置 | 不问“有没有做保护”，问“它上次拦下来是什么时候，给我看那次记录”；拿不出证据就当没有 | 保护机制必须配一条“它真的会拦住”的测试；测不出拦截等于没有 |
| 四 | 两个地方各写一遍，然后对不上 | 5 截到 2000 字，多加 26 字符提示变 2026，上限 2000；6 群里 @ 任何人机器人都当叫自己 | 存不进去被兜住，用户看到“运行成功”，历史记录少一条；机器人把同事间 @ 当任务 | 连做三次去历史里数；自己制造一次“不该触发”（@ 同事）看它响不响 | 同一个限制只能有一个定义；截断长度和允许长度来自同一个数字；“什么情况下不该动”比“什么情况下该动”更需要测试 |
| 五 | 找不到，不等于不存在 | 7 “目录里没有”被读成“这东西不存在”（63 个工具 vs 目录 34 个，42 个由另一处提供） | 系统什么都没给，你把空白填成最省事的结论：“没有/做不到/不支持”；还配一段听起来有说服力的推理 | 把“找不到”拆成三种：目录里没有、本身不存在、存在但你现在用不了；逐个排除；说清你查了什么、没查什么 | 说“不存在”之前，必须先说清查了什么、没查什么；只查一处只能说“我只在这一处找到 34 个” |
| 六 | 测量本身产生了信号 | 8 每看一次仪表盘，数字就变一次（总数 6，成功 1，失败归因 4） | 有些页面只加总数不记结局；看指标那次请求自己也被计入；数字越看越多，你越看越相信它在涨 | 把总数拆开加一遍；什么都不做连续刷新五次，看数字动不动 | 观测动作不能改变被观测的东西；任何总数必须能拆成互不重叠的几项且相加相等 |
| 七 | 你数的那个东西，不是你以为的那个 | 9 `grep -c '<tr id='` 得 7，实际 108；10 `git status` 报 120 个改动但 `git diff` 为空；11 `tar` 给短文件补 4096 个 NUL | `grep -c` 数的是“包含匹配的行数”不是“匹配出现次数”；HTML 整张表一行；git stat 缓存假设失效；tar 按块补零 | 换一种算法再数一遍；先数一个你知道答案的东西；同一问题用两个工具查，结论不一致时查为什么 | 数之前先说出你要数的到底是什么，以及这个命令数的是什么；任何“搬运”之后都要验证目的地 |

来源：https://main.luteos.com/originals/failure-atlas.html

### 6.2 两分钟自检表（每次 agent 说“全部通过”之后）

| 问它 | 答不上来意味着 | 你自己做什么 |
| --- | --- | --- |
| 上次有检查失败是什么时候？给我看那次记录 | 可能是第一类：从没失败过的检查 | 翻历史，找不到失败就是没有失败过 |
| 这次结果里跳过了几条？为什么跳过？ | 第一类：跳过被算成通过 | 要求逐条念，不接受合并成一句 |
| 把密钥改错/断网，再跑一次 | 它能跑，就说明它不依赖外部 | 正确结果必须是“无法判断” |
| 这个测试用的是真数据还是假数据？ | 第二类：测的不是你的产品 | 换一个自己随手找的真实输入 |
| 成本上限上次拦住是什么时候？ | 第三类：保护机制没启动过 | 任何保护都这么问，不限成本 |
| 同一条规则在几个地方各写了一遍？ | 第四类：迟早对不上 | 改其中一个，看另一个跟着变不变 |
| 做三次，历史里有几条？ | 第四类：有记录在静默丢失 | 做 N 次数 N 条，一样就对了 |
| 制造一次不该触发的情况 | 它乱动了，就是判定条件写宽了 | @ 别人、输错内容、重复提交 |
| 你说“没有”的时候，查了几个地方？ | 第五类：把“我查的这一处没有”当成“不存在” | 去它的来源处再查一次；说清查了什么没查什么 |
| 总数加得起来吗？成功 + 各种失败 = 总数？ | 第六类：有请求开了头没结尾 | 拆开加一遍；再连续刷新五次，看数字会不会自己动 |
| 这个数字，换一种方法再算一遍是多少？ | 第七类：你在数容器，却以为在数东西 | 两个独立算法给出同一个数，才可信 |

### 6.3 四条质量问句（七问句漏掉的一整类：产出可用度）

来自第二次实测的修正：七问句能抓“假信号”，但抓不到“机制可信、产出不可用”。补的四条是：

1. 给我看三个真实输入的输出——不是你挑的样例，是我随手找的。
2. 这个你会拿给客户看吗？
3. 有没有一条检查是关于结果对不对的，还是全是关于程序有没有崩的？
4. 最常见的输入会发生什么？

来源：https://main.luteos.com/originals/atlas-test-report.html（“七个问句漏掉的那一类”）；https://main.luteos.com/originals/decision-tree.html（“你怀疑有东西在骗你”）

### 6.4 “有些验收，你做不到”

失败图鉴专门用一节讲：第一步要“找一个不懂技术的人听我讲”，第四步要“用另一台设备打开，让另一个人试”，作者两处都做不到（调不起第二个人，也没有第二台设备）。正确做法不是跳过、不是用相似动作代替，而是明确写下：“这一步的验收动作需要 X，我没有 X，所以这一步未通过。”然后继续做下一步，但必须写下来，因为“这一步没验”和“这一步验过了”在后来的记忆里会混成一个。

作者给了一个便宜的替代品：让 agent 扮演陌生人，只给页面、不给解释，看它卡在哪；这能发现一部分问题，但 agent 会比你聪明地猜测意图，而真人在不懂时会放弃。**所以它算“部分验证”，要照实标注。**

来源：https://main.luteos.com/originals/failure-atlas.html（“有些验收，你做不到”）

### 6.5 读信号规则：红、绿、空都不能直接读成结论

- 测试红了——先问是产品错了还是尺子错了（红不等于坏）。实测三条红的三条是测试自己写错。
- 检查全绿——先问这个检查上次什么时候失败过（绿不等于好）。
- 记录是空的——先问是查了一处还是查了所有地方（空不等于没有）。

## 7. 审查者与发布门：Main 实际给了什么

### 7.1 Main 没有“角色审批模型”

Main 的七阶段页只定义“谁来验，怎么验”的动作，不定义组织角色。实际出现的“审查者”只有四类：

1. **你自己**：每个阶段亲手做动作；做不了就记未通过。
2. **一个不做这行的人**：需求阶段复述用途/对象/产物；交付阶段在没有解释的情况下用一次。注意：这是“另一个真人”，不是 agent 角色扮演；agent 只能算部分验证。
3. **机器检查/skills**：`anb-check-*`、`interrogate`、`code-review`、`security-review`、`thermos` 等是工具审查，不是人类批准。
4. **Operator/审查台（仅架构描述）**：`apps/workbench` 调用同一个 `createRuntime().run()`，与飞书端共享提示词/工具契约；这是产品形态描述，不是发布门定义。

> 对 Radar 的治理含义（D）：必须另建人类角色与签核链；agent 审查结果不能冒充人类批准。这是我们的扩展，Main 没有。

### 7.2 分阶段发布门（Main 明文 + Radar 适配）

| 门 | Main 明文条件 | Radar 适配（D 草案） |
| --- | --- | --- |
| G0 业务发现门（OUR extension） | Main 无此门；Main 明说答不了市场 | 业务 owner 签核问题、用户、当前替代方案、停止信号、数据可访问性；见 8.2 |
| G1 需求门 | 六句/五句能复述；否定条件可测量且产品可判断；参与者写明 | R- 记录 + 能力清单；业务方“已确认”不能为空（tables-need 样张里多条是“未确认”，这是红旗） |
| G2 设计门 | 四块写全或写明跳过；agent 猜点 ≤3；跨块冲突为空；拒绝清单输入→动作；权限三档+数字额度 | D- 记录 + 8 层契约卡（至少采集/存储/指标/结论四层）+ 飞书动作权限表（读/回/发/发群/写数据） |
| G3 开发门 | 两个真实输入（含一个没预想过的）都能跑；错误是人话+非零退出 | 一条真实飞书消息端到端；事件重复/空抓/超时/无权限四条错误路径 |
| G4 验收门（唯一硬门） | 5–10 条检查；亲眼见红；断网=无法判断；跳过=不完整；总数对账；三个真实输出 | 加数据层检查器（collect-audit 0/1/2、collect-store verify、metric-card check、verify-conclusion、report-audit）+ 飞书事件检查；具体见 8.4 |
| G5 交付门 | 手机打开；另一个人无解释使用；密钥来自环境；配额算清楚 | 另一名同事在手机飞书 @ 机器人完成一次真实问答；密钥/租户/权限/回滚四项清单；配额算到第几个用户 |
| G6 运营门 | 做 N 次记 N 条；故意弄坏能找到；成本可见 | 另加产品侧信号：谁在用、问了几次、哪一步放弃、答案是否被采纳/追问/转人工 |
| G7 迭代门 | 保留物有使用记录；模板第二个产品更快；复盘项有 owner/日期 | R-/T- 回流；证伪触发旧结论转 superseded；模板抽取按“形状是否随产品变” |
| G8 管理门 | `work check`/`layout check`/`facts --check`/`naming check` 非零即拒 | 加 `matrix-check`、数据契约版本检查、飞书事件幂等表检查 |

## 8. Main → Radar 生命周期适配（草案，D 级）

### 8.1 适配原则

1. **保留 Main 的 7+1 骨架**：需求→设计→开发→验收→交付→运营→迭代，管理横跨。不要因为 Radar 是“飞书 Agent + 工作台”就另造一套阶段名；阶段名一致，证据才能对照。
2. **补一个 B0 业务发现阶段，并明确标注 OUR extension**：Main 的“需求”阶段解决的是“意图可验收”，不解决“市场有没有人要”。Radar 面向 Momcozy 跨境业务，必须先做业务发现；但不要把 B0 说成 Main 的方法。
3. **把 8+3 契约按“最小可用层”落地**：不是所有 Radar 功能都要 8 层；但凡输出数字/结论，至少落采集、存储、指标、结论四层；呈现/报告按交付形态逐步加。
4. **人类门与机器门分离**：Main 的 `anb-check-*` 是机器证据；业务 owner、产品 owner、发布 owner 的签核是人类门。Agent 审查不能冒充人类批准。
5. **先窄后宽**：第一条端到端路径只做“一条真实飞书消息 → 一条真实数据 → 一条可核对结论 → 一条用户可用的回复/卡片”；不做大而全工作台。
6. **所有 Radar 建议标 D**：本文的 B0、角色、门禁编号、数据层落点都是草案；经人类决策后才升级为项目规范。

### 8.2 B0 业务发现（OUR extension，不是 Main 声明）

**为什么必须补**：Main 首页边界原话“能让你不骗自己，不能让你不骗市场。产品有没有人要，这套方法答不了。”运营页也说“技术上的‘全部正常’和产品上的‘没人用’可以同时成立。”第二次实测更直接：“六步走完，产品仍然没有被人用过一次。所有检查都是我自己在验自己。这一步手册答不了。”

**B0 的输入**：

- Momcozy 品牌与业务目标：哪些区域/品类/渠道/团队；今年的增长/效率/风险目标。
- 用户与场景：品牌、市场、商分、社媒、客服、达人运营、内容团队；他们在飞书里怎么工作；现在用什么替代方案（人工翻主页、Excel、第三方看板、周报）。
- 需求证据阶梯：看过→收藏→留邮箱→回消息→试用→验收→预付→续费；没有最高成本信号前，不要把曝光写成 PMF（来自 Main 作战手卡 `05-01`，但用法是业务发现，不是 Main 的需求阶段）。
- 数据可访问性：TikTok/IG/Facebook/Reddit/小红书等平台的数据获取方式、配额、时滞、合规；飞书应用权限与事件订阅能力。
- 约束：预算、人力、上线时间、安全/隐私/品牌合规、飞书租户与可见范围。
- 停止信号：什么可测量事件说明“不该做/该停”。

**B0 的产物**：

- `B0-问题定义 memo`：谁、什么场景、现在怎么疼、替代方案、为什么现在做、做完哪个动作会不同。
- `B0-需求证据日志`：每条证据的来源、成本、日期、结论；区分“兴趣”与“付出”。
- `B0-数据可行性 memo`：每个数据源的访问方式、时滞、字段、配额、合规风险、空抓语义。
- `B0-飞书交互契约`：群 @ / p2p / 卡片 / 3 秒回执 / 长连接 / 幂等 / 权限范围；以飞书官方文档为准（B 级），不能拿 Main 的描述当平台约束。
- `B0-停止信号与成功指标`：至少一个可测量否定条件 + 一个业务成功指标。

**B0 的可失败检查（D）**：

- 找 3 个真实目标用户/业务方，分别复述“问题、产物、什么时候不该做”；复述不一致就说明问题没定义清楚。
- 对每个关键数据源做一次真实探测（不是文档阅读）：能否拿到、延迟多少、字段缺什么、空结果长什么样；探测失败就记“不可用”，不要用“应该可以”代替。
- 把“需求证据阶梯”每一级写成可观察事件；没有最高成本信号前，不允许进入 G1。
- 业务 owner 在 `B0-问题定义 memo` 上签核；没有签核就记“未确认”，不能进入设计。

### 8.4 Radar 特有的验收检查（D 草案）

**飞书事件/会话**：

- 同一事件重复投递 3 次，只产生 1 次业务动作，回复不重复；幂等键可查。
- 群里 @ 别人（不是 @ 机器人）不触发；p2p 消息只对发起人回；未授权用户收到明确拒绝/转人工，不泄露数据。
- 机器人 3 秒内回执，长任务异步；超时/失败有可读错误和重试/回滚；不静默失败。
- 事件验签/解密失败时必须“无法判断/拒绝”，不能当“已处理”。
- 用户问“查不到”时，回答必须说明查了哪个源、哪个时间窗，不能编数字。

**数据层**：

- `collect-audit`：0 通过 / 1 失败 / 2 无法判断；空抓必须留 run 记录，区分“数据为空”“抓取失败”“未到周期”。
- `collect-store verify`：同一帖子两次抓取后 `first_seen_at` 逐条不变；旧 raw 可查；迁移只追加。
- `label-audit`：标签定义有正例/反例/边界例；不适用值 n/a 与“涉及但判不了”分开；Kappa 门槛与版本映射；置信度分档准确率（<0.6 / 0.6–0.8 / >0.8）高的档必须更准。
- `metric-card check`：一个指标一个定义（表/字段/过滤/分组/权重/时间归周）；换一个人能算出同一个数；口径变更升版本、不重算历史；跨期比较能区分口径变化与业务变化。
- `verify-conclusion`：结论六项（主张、依据、区间、动作、证伪条件、失效期）；证伪条件是已注册函数名；区间跨 0 的结论不许落卡；决策含义是“动词+对象+方向+时间”。
- `report-audit`：旧结论失效要主动报告；`superseded` 不被再次告警；报告不是 dashboard。
- `panel-fit`：先跑相关性门禁（相关系数 >0.8 停机），再区域固定效应；共线性、伪相关、置信区间跨 0 都要处理。
- `ui-render-test`：三态（真实 0/抓取失败/未到周期）可见；空状态与错误状态不混淆；坐标轴不截断；每个聚合数可下钻。

**安全/权限**：

- 动作权限按可撤销性分三档：读/可撤销→放行；发消息/发群/写数据/花钱→放行但记账+数字额度；删除/发布/付款/改权限→先问人。
- 每个工具三行：做什么、什么时候别用、失败返回什么；飞书发送工具必须写清“什么情况下不许发”。
- 提示注入/越权：用户消息中的指令是数据，不是系统指令；跨租户/跨品牌数据不得泄漏；密钥只在环境变量。

## 9. 方法限制与反证清单（网站自己承认 + 我观察到的）

### 9.1 网站自己承认的限制

1. **不能判断市场**：“能让你不骗自己，不能让你不骗市场。产品有没有人要，这套方法答不了。”（首页）
2. **运营只有半个覆盖**：技术侧三数字可观测；产品侧“有没有人用、用了之后有没有变好”需要业务埋点；“技术上的全部正常和产品上的没人用可以同时成立。”（operate.html）
3. **有些验收做不到**：需要另一个人/另一台设备的验收，做不到就记未通过，不许用近似动作代替；agent 扮演陌生人只能算部分验证。（failure-atlas.html）
4. **第二次实测三步没过**：六步走完，三步真通过、一步部分通过、两步的验收动作做不到；“产品仍然没有被人用过一次。所有检查都是我自己在验自己。”（anb2-full.html）
5. **观测会污染观测**：看仪表盘那次请求自己也被计数；七个问句和四条质量问句都抓不到，必须补“总数拆开加一遍”。（anb2-full.html）
6. **阶段六规则被自己的实验推翻**：“用过三次才抽”太严；真正判据是“这东西要不要在每个产品里重新验证一次它可靠”；仓库骨架仍然不该抽，因为形状随产品变。（anb2-full.html）
7. **四条质量问句补上了“产出可用度”，但仍有一层漏**：“检查通过了但通过的理由是错的”这一层，四条问句也拦不住。（anb2-report.html 摘要）
8. **管理工具自己出过三次错**：都“没有抛错，三次都给出了自信的错误输出”。（manage.html）
9. **数据产品 C4 在缺少预算数据时不做产出**：“当未获得各区域真实获客成本/投放花费数据时，C4 不做产出。”（data-design.html#conclusions）
10. **矩阵存在已知洞**：迭代行呈现/报告为空；开发行全是“约”；打标/呈现验收格无检查器；`collect-store verify` 对不存在的账本文件返回 exit 0“不变量成立”，页面自己说“这个也要先修”。（matrix.html；tables-verify.html#acc-11）

## 12. 下一步需要人类决定的事

1. **是否采用 Main 的 7+1 阶段作为 Radar 的生命周期骨架？** 还是只采用其中的验收/证据部分，另建 Radar 自己的阶段？这是第一个必须拍板的分叉。
2. **B0 业务发现是否单独立阶段、由谁 owner、产出什么签核？** Main 明确不覆盖市场；如果跳过 B0，Radar 会重复“产品没被人用过”的风险。
3. **Radar 的首发窄路选哪一条？** 建议候选：① 飞书群 @ 机器人回答“某区域/某品类/某竞品最近声量如何”，带来源与时间窗；② 飞书 p2p 接收 TikTok/Reddit 链接并产出结构化洞察卡；③ 工作台单页“声量异动+下钻”。只能选一条先走通。
4. **Radar 是 Agent only 还是 Agent + 工作台？** 工作台的首屏/权限/数据下钻是否纳入第一版？决定 8 层中“呈现/报告”是否立即落地。
5. **8+3 契约裁剪到哪几层？** 首发是否只做采集/存储/指标/结论，打标/分析/呈现/报告后置？如果输出数字，至少四层不能省。
6. **人类门角色怎么设？** 业务 owner（B0/G1）、产品 owner（G2）、技术 lead（G3）、QA/Eval owner（G4）、发布 owner（G5）、运营 owner（G6）、PMO（G8）分别是谁？Main 不提供角色模型，这是我们的治理扩展。
7. **飞书应用配置与权限范围由谁确认？** 长连接 vs Webhook、事件订阅、群 @ 与 p2p 权限、可见范围、3 秒回执、幂等表；需要飞书官方文档（B 级）与平台管理员确认。
8. **数据源与合规由谁确认？** TikTok/IG/Facebook/Reddit/小红书等采集方式、配额、时滞、字段、空抓语义、隐私/品牌合规；没有真实探测不得进入 G1。
9. **是否复用 Main 仓库的 `apps/*`/`packages/*`？** 还是独立架构？如果复用，先验证代码/脚本/评测是否真实存在；如果不复用，不要把 Main 的包名写进 Radar 架构图。
10. **证据保留与 CI 门禁怎么落地？** 是否采用 `work/` 八寄存器、`work check`、`matrix-check`、`facts --check`？谁维护？证据保留多久？
11. **已知检查器缺口怎么处理？** 打标/呈现的检查器是先补还是先标“约”？`collect-store verify` 对缺失账本返回 0 的 bug 是否列为 Radar 采用前的阻塞项？
12. **是否接受“有些验收做不到就记未通过”的纪律？** 如果团队文化不接受“未通过/不完整”的结论，Main 的方法会被用成“全部通过”的装饰。

## 14. 给 Radar 的一句话建议

**把 Main 当成“验收脚手架”而不是“开发路线图”**：用它的 7+1 阶段和 8+3 契约来设计证据与门禁；用我们自己的 B0 业务发现补上它明确不覆盖的市场问题；用飞书官方文档补上它不提供的平台约束；用人类签核补上它没有的角色模型。第一条端到端窄路走通之前，不建大而全工作台。
