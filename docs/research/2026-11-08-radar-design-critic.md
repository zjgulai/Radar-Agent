## 0. 总判定

**成立、应保留的部分：**

- 一个事务型事实库、通道与事实分离、入站先持久化、outbox/unknown、批准绑定具体动作/目标版本/参数、默认拒绝、权限在模型外执行、外部内容不可信、SSRF 连接时校验、未知为一等状态。
- 明确不承诺跨系统 exactly-once、不承诺业务 ROI、不默认自动外联/付款/签约/发布。
- 采用**常驻** Feishu Gateway，而不是把长连接放进短生命周期 serverless/请求处理器；这点正确，应作为硬约束保留。
- 交付笔记把 elapsed、person-effort、external waiting 分开，并声明区间不是承诺；方向正确。

**不成立、尚未证明的部分：**

- 飞书平台能力（卡片回调是否走长连接、`event_id` 稳定性、发送超时能否查询对账、现有应用能否切换事件模式）被写进拓扑和验收，但只有“多连接语义”被明确标注待确认。
- MVP 切片缺 `brief`、缺业务决定对象；`candidate` 与 `opportunity` 混用；PMO 的“IP 合作计划制定”被排到最后一个增量。
- 授权材料状态机把“材料受理、审核结论、有效期、授权范围、具体使用许可”压成一个状态；“verified”可能被下游读成“已经可以合法使用”。
- 架构笔记 MVP 的 S01–S14 与交付笔记 P4 的三切片/24–56 直接人周不是同一范围，无法相互校验。
- 27–46 周总区间不能由分段区间和 FTE 区间按独立区间复算；外部等待不在上限。
- 三套决策编号、两套阶段命名、两套切片编号并存；父级综合直接合并会制造“计划真相”冲突。

按当前状态，两份候选笔记只能称为**待评审的候选方案集合**，不能称为“连贯的已批准计划”。

## 4. P0 缺口的展开与修正

### P0-1 业务切片：技术上纵向，业务上未闭环

架构笔记 §17 的 MVP 是“主页/账号链接 → 可追溯背调 → 人工判断 → 候选认领 → 授权材料登记”。领域笔记 §1–2 明确“候选机会”是**合作对象与某个品牌 brief 之间**值得复核的建议，并在场景 A 中要求展示“与当前 brief 的关联”。但架构 §3.2/§7.3 的 `candidate` 没有 `brief_id`，`claim` 只是责任分配，不是业务决定；没有 `shortlist / reject / request_more_info / defer` 的决定记录。结果是：

- 任务可以在没有业务决定的情况下达到 `completed_with_evidence`；这只是技术任务完成，不是业务决策完成。
- 评测笔记 §1 要求“业务人员作出候选判断”，但该判断没有可追踪对象。
- “减少背调时间/提高决策质量”的价值假设无法测量，且没有当前流程基线。

**修正：**

1. 增加 `brief`（品牌、市场、品类、目标、预算/时程约束）与 `assessment/partnership_decision`（决定、理由、证据版本、决定人、时间、政策版本）；`claim` 保持独立。
2. 如果 MVP 有意只做研究包，则把“候选/机会”改名为 `creator_assessment`，删除“决策支持”表述，并在后续增量再引入 opportunity。
3. P1 出口加入基线：同一流程的步骤、耗时、角色、返工、证据缺口；至少 3 条近 12 个月脱敏案例。没有基线，不得声称效率或质量提升。
4. 定义 minimum evidence set：关键字段大面积不可得时，切片应判为“不可行”，而不是把空泛的 unknown 包装成完成。

**责任：** 产品/BA + BD；D02–D04。**风险：** 若业务访谈发现用户并不从主页链接发起，整个 MVP 需要重定，而不是继续优化卡片。

### P0-2 授权材料：不要把“登记/审核/范围/许可”压成一个状态

Arch §7.3 的状态是 `draft/missing → submitted → under_review → verified | limited | rejected | expired | revoked`。这里至少混了四个维度：

- `verified/rejected` 是审核结论；`limited` 是授权范围；`expired/revoked` 是生命周期；它们可以同时存在。
- “verified”没有说明验证了什么：签字人、权利主体、代理权限、地域、渠道、用途、期限、素材范围。
- 没有 per-use clearance：同一材料可能允许 organic repost，但不允许 paid ads 或 whitelisting；一个“verified”状态无法表达。
- 没有到期/撤回后的 owner、通知、下游使用暂停流程。

**修正：**

- `intake_status`：missing / draft / submitted。
- `review_status`：pending / under_review / verified / rejected，并记录验证范围与复核人。
- `validity`：valid_from / valid_to / revoked_at / revocation_reason。
- `scope`：权利主体、代理人授权链、地域、渠道、媒体、使用类型、期限、排他性。
- `usage_clearance`：按每次 intended use 计算，默认 deny；只有 review + validity + scope 同时满足才允许。
- UI/API 在 D08 批准前一律显示“材料登记，不代表法务通过或已生效”；不要用 `verified` 作为对外文案。
- 登记到期/撤回的 owner、通知对象、下游暂停动作写入 runbook。

**责任：** 法务 + 品牌资产 owner；D08。**风险：** 把“登记”读成“可用授权”会导致素材误用，属于高影响合规风险。

### P0-3 飞书平台：把“可能”写成了“如何实现”

Arch §2.1–2.3 把“卡片回调入队”“快速 ACK”“单活跃长连接”“消息查询对账”写进 Gateway 责任；§4.1–4.3 进一步把 `(app_id,event_id)`、`message_id`、outbox unknown 写成设计不变量。笔记只对“多连接语义”标注了“待飞书官方文档与 PoC 确认”，其余平台行为被默认为可用。

**修正：** D06 PoC 必须至少覆盖第 3 节表中的十项；每项给出“通过/不通过/降级”判据。特别是：

- 若卡片 action 不能走长连接，需要一个公网 HTTPS 回调端点；这会改变拓扑、网络暴露面、签名校验和限流设计。
- 若发送超时无法按消息查询，`unknown` 只能进入人工对账，不能承诺自动恢复。
- 若现有应用已被其他集成占用事件模式，不能直接切换；先审计应用归属、权限、版本和可用范围，再决定是否新建专用应用。

**责任：** 飞书管理员 + 安全；D06。**风险：** 在 PoC 前冻结 Gateway/API/schema，会把未验证的平台假设固化进架构。

### P0-4 范围与估算：S01–S14 与 P4 三切片不是同一范围

Arch §16–17 的 MVP 包含 S01 契约/迁移、S02 Gateway、S03 队列、S04 RBAC、S05 证据、S06 状态机、S07 SSRF/connector、S08 背调、S09 认领/材料、S10 批准完整性、S11 工作台、S12 对象页、S13 管理/审计、S14 评测。Delivery §2.4/§5.2 的 P4 只列 S1 入口、S2 证据/背调、S3 认领/材料，加“工作台最小、审计、错误/未知、契约测试”，估算 8–14 周、24–56 直接人周。

**判定：** 如果 P4 真的覆盖 S01–S14，24–56 人周偏紧；如果只覆盖三切片，架构的“MVP core”就比交付的 MVP 大。两种读法不能同时成立。

**修正：** 建一张 WBS 对照表，列为 `S01–S18`、`对应 P 阶段`、`MVP must/should/later`、`角色`、`人周区间`、`依赖 Dxx`。父级综合只使用对照后的范围；在此之前不要写“MVP 已定义”。

**责任：** 技术负责人 + 产品；D04、D09、D12。

### P0-5 治理真相：三套编号、两套阶段名

- 决策：D01–D12（Decision Register）、H01–H12（Arch §18）、DC-01–DC-12（Delivery §11.1）。
- 阶段：Arch 的 MVP/M1/M2 与 Delivery 的 P0–P6/M1–M4 并存；M1 在两份笔记中分别指“监测”和“MVP”。
- 切片：S01–S18 与 S1–S3 并存。

**修正：**

1. 只保留一个 `decision_register`，新增决策用 D13+；H/DC 表改成“视图/检查清单”，不再独立编号。
2. 统一阶段词汇：建议 `Phase A（MVP 候选）`、`Phase B（监测）`、`Phase C（计划）`、`Phase D（整合）`；在术语表里定义一次。
3. 父级综合引用决策时只写 D 编号；引用切片时写 `A-S1`/`A-S2` 或 `MVP-S1`，避免与 S01 混淆。
4. 每个 H/DC 项映射到 D；不能映射的（如 DC-01 Main 映射）应升级为正式 D 项，而不是留在候选笔记里。

**责任：** 发起人/PMO；D01、D12。**风险：** 三套编号会让“哪个决策已关闭”无法审计，也会让父级综合误把 H/DC 当成批准。

## 5. P1 缺口的展开

### 5.1 群聊/私聊泄漏

Arch §8.1 的 RBAC 表把“查看受限报价/合同/私聊”授予 BD、Reviewer、Legal Reviewer 和 Service（○ = 仅限被授权资源）。这是最明显的泄漏风险：**私聊不是工作区的一种普通资源**，它属于会话参与者。即使有资源 ACL，也没有说明谁有权授权、是否取得参与者同意、法务访问走什么独立流程。

**修正：**

- 私聊内容默认不进入工作区事实库；只有参与者显式“附加到任务/分享到群”时才生成一个带同意记录的投影。
- 每个任务/产物带 `audience_scope`：`p2p:<user>`、`group:<chat>`、`workspace:<id>`、`restricted:<acl>`；默认继承来源作用域；扩大作用域需要单独批准并生成新投影。
- 群卡片只展示群安全摘要，不展示完整档案；深链不授予访问权，登录后仍按工作区/资源 ACL 判定。
- 法务/合规访问私聊内容走独立审批与审计，不作为普通 RBAC 能力。
- 群内非 @ 消息只保留最小元数据（或哈希），不持久化全文；否则“未 @ 不分析”仍可能读取和存储了不该读的内容。
- 多品牌群必须显式选择品牌上下文，不能按群默认品牌；补外部租户/guest、转发卡片、线程/话题群测试。

**责任：** 产品 + 安全 + 法务；D07。**判定：** 原则正确，但按当前 RBAC 表实现会出问题。

### 5.2 27–46 周不是资源可复算的区间

| 计算 | 低 | 高 | 说明 |
|---|---:|---:|---|
| P0–P6 elapsed 简单相加 | 28 | 50 | 2+4+3+4+8+4+3 / 4+7+7+6+14+6+6 |
| 笔记给出的总区间 | 27 | 46 | 只减少 1/4 周，未体现所述“P1/P2 部分并行、P3 与 P2 尾部并行” |
| 直接人周相加 | 55 | 117 | 与笔记一致 |
| 平均 FTE = 人周/elapsed | 2.0（55/27） | 2.5（117/46） | 只在“低人周配低 elapsed、高人周配高 elapsed”的对角配对下成立 |
| 交叉配对 | 1.2（55/46） | 4.3（117/27） | 若外部延迟或赶工导致交叉，2.0–2.5 不成立 |
| P4 峰值 | 3.0（24/8） | 4.0（56/14） | 同样依赖对角配对；56/8=7，24/14=1.7 |

此外：

- 外部等待 0–6 周/关键项**不在** 27–46 上限内；两个关键项串行各 6 周，就应再加 12 周，区间变成 27–58+。 headline 应改为“内部 elapsed，不含外部审批”。
- 岗位容量合计 5.7–7.4 FTE，与 P4 峰值 3–4 直接 FTE 之间没有角色 × 阶段的加载表；“按共享/部分投入折算”无法审计。
- 低区间条件包含“复用现有基础设施和身份体系”，但项目是空目录，未验证这些资产可用；若不可用，需加平台搭建人周。

**修正：** 要么删除总区间，只给分段区间、依赖和外部等待带；要么做容量加载的关键路径模型，列出每阶段角色 FTE、周数、并行窗口和外部等待。父级综合不得单独引用 27–46 周。

**责任：** 项目负责人 + 财务；D12。

### 5.3 PMO 与 Main 映射：有表，但没有可核对的来源

- Domain §2 明确说 PMO 三项能力名称是“建议落为场景”，不是完整原文；Arch §17 和 Delivery §5.1 各自给出映射，但都没有 PMO 原文定位单元。
- 两份映射不一致：Arch 把 MVP 说成“最小候选识别”，Delivery 把 M1 说成“合作机会识别”的输入；场景 A 到底是一项能力还是三项能力的 enabler，没有定义。
- Delivery §2 明确 P0–P6 不是 Main 阶段，DC-01 待做；Arch 完全未展开 Main。用户要求参照 Main 全栈路线，但当前计划还不能称为 Main 对齐。
- “IP 合作计划制定”被排在最后，而它是 PMO 页面上的 Radar 能力之一；这个排序没有业务证据，只是架构依赖推断。

**修正：**

1. 增加 `PMO capability (verbatim)` / `source locator` / `project interpretation` / `MVP coverage` / `not covered` / `owner confirmation` 六列表；未填前标“未验证假设”。
2. 把场景 A 标为“证据与授权 enabler”，不要直接映射成“合作机会识别”；只有带 `brief_id` 的 opportunity 才能算机会识别。
3. 在 DC-01 完成前，所有对外材料写“Main 映射待完成”，不得写“按 Main 阶段执行”。
4. 让 PMO/业务 owner 对三能力的排序签字；如果计划能力优先，考虑一个 thin planning slice（一个 brief、2–3 个候选、草案计划），但不要在没有业务输入时自行加范围。

**责任：** PMO + 研究负责人 + 业务 owner；D01、D04、DC-01。

### 5.4 Exactly-once 与幂等：没有直接承诺，但测试措辞要收窄

两份笔记都明确不承诺跨系统 exactly-once，这一点应保留。残余风险在：

- Eval §4 的“同一消息重复投递：仅创建一次业务任务”是测试断言，容易被引用成平台保证；应限定为“在已测试的重复投递模式下”。
- Arch §4.1 的 inbox 唯一约束依赖 `event_id` 稳定；若平台重试产生新 ID，仍需 `message_id`/内容哈希兜底。
- Arch §4.4 的“已完成步骤通过幂等键/检查点跳过”在“外部动作成功、检查点未写”时仍可能重复；需要 intent/outcome 两条记录和对账。
- Arch §4.3 的 unknown 对账依赖消息查询能力；若平台不提供，只能人工对账，不能承诺自动恢复。

**修正：** 在技术方案里写一张 delivery semantics 表：内部数据库=事务原子；入站=at-least-once + 去重；出站=at-most-once，除非对账确认；跨系统=不做 exactly-once 承诺。补 `event_id` 变化、消息编辑、重复卡片、发送超时无查询能力、worker 在外部成功后崩溃五类测试。

**责任：** 技术 + QA；D09、D11。

### 5.5 出站动作：外联已禁用，但 Feishu 发送仍缺统一策略

Arch §9.1 的 `message.enqueue` 会把回执、卡片、背调摘要发到 Feishu；Delivery §6.3 的恢复流程还会发“更正说明”；P5 试点会向真实群发消息。`outreach.send` 默认禁用是正确的，但 Feishu 出站仍是外部可见动作，当前缺：

- 模板与内容类白名单：哪些内容可以进群，哪些只能在工作台看。
- 模型生成文本的审核：不能把未经证据校验的模型摘要直接发群。
- 作用域与收件人：群、P2P、试点名单；禁止向未授权用户主动私聊。
- 速率、去重、kill switch、发送登记与更正审批。

**修正：** 增加 `outbound_policy` 表和发送登记；每次发送检查 channel/scope/template/content_class/approver/rate_limit/kill_switch；保留消息 ID 与对账状态。首次试点由业务 + 安全批准模板，不由工程临时拼文案。

**责任：** 产品 + 安全 + 业务；D07、D11。

### 5.6 验收：没有基线，也没有可执行的脚本

- Delivery P4 退出写“三条切片按验收脚本通过”，但脚本未定义；P1 的基线是交付物，不是退出证据。
- Eval 的指标是候选，明确不设阈值，这是对的；但“通过”仍需要一个可复核的证据定义，否则会退化成演示通过。
- 没有 minimum evidence set，P2 允许“字段明确不可得”，可能导致一个几乎全是 unknown 的背调也被判“完成”。

**修正：** P1 出口加基线；P4 前为 S1/S2/S3 各写 acceptance script（输入、预期状态、证据、失败/未知/越权分支）；定义 minimum evidence set 和 no-go；把 Eval 的 case 映射到 L1–L8 或 S14。D11 批准前不设数值接受线，但必须定义“什么证据算数”。

**责任：** 产品 + QA + 业务；D11。

## 6. 尝试反证但未成立的部分

以下项目**没有**发现候选笔记违反其自身边界，父级综合不要过度纠正：

- **Serverless 长连接：** 未发现违规。Arch §2.2/§14.1 明确采用常驻 Gateway + 容器；长连接需要长生命周期进程，任何 scale-to-zero 或短请求时限的 FaaS/edge 都不适合承载 Gateway。保留该约束。
- **Exactly-once 承诺：** 未发现明确的跨系统 exactly-once 声明；只有测试措辞和平台依赖需要收窄。
- **指标承诺：** 未发现“已达 95%”或目标值；Eval 明确 `human_gold_claim_count = 0`。保留“不设阈值”的克制。
- **未批准的外联：** 外部达人外联、付款、签约、发布均默认禁用；保留。残余风险是 Feishu 内部发送与更正通知。
- **供应商冻结：** 未冻结云、模型、数据区域；但具体库名和“建议默认”写法仍应降级为候选。
- **运行时双事实源：** Arch 明确 PostgreSQL 单一业务事实源，Feishu/工作台是投影；运行时数据模型方向正确。残余风险是 `task_event`/`audit_event` 和对象语义的归属。
- **授权登记：** 文字上反复声明“登记不等于法务通过/合同生效”；问题在状态机和权限表，不在文字态度。
- **群/私聊隔离：** 原则和测试意图正确；问题在 RBAC 的“私聊”授权、同意模型和平台语义未验证。
